# 제품 불변 규칙

> TechRadar가 코드가 바뀌어도 꼭 지키는 불변 규칙 6가지(사람 승인, 수집 오류, 멱등, 기존 값 보존, 권한, 실제 기록 흐름)와 각 규칙을 확인하는 시험·QA 행. (출처: CLAUDE.md 3절)

## 한눈에
- 불변 규칙은 코드를 바꿀 때 시험으로 확인한다. (출처: CLAUDE.md 3절 제목)
- 데이터에서 각 규칙이 지켜지는 곳은 데이터설계 5절 표에 있다. (출처: docs/데이터설계.md 5절)
- 아래 시험 파일 이름은 그 파일 안에 해당 불변 번호가 적힌 것만 골랐다. QA 행은 행 이름에 불변 번호가 적힌 것이다. (출처: lib/**/*.test.ts, docs/qa.md, docs/qa-c.md)

## 불변 1. 사람이 승인하기 전에는 아무 조치도 없다
- 사람이 판단(적용 후보·보류)을 저장하기 전에는 어떤 조치도 실행하지 않는다. 관리자도 건너뛸 수 없다. (출처: CLAUDE.md 3절 불변 1)
- 관리자는 자기 알림에는 판단할 수 있지만, 남의 알림을 대신 판단하거나 건너뛸 수는 없다. 문장은 그대로 두고 이렇게 읽는다. (출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것)
- 데이터에서는 `judgments`를 본인 알림에만 만들 수 있게 막는다. (출처: docs/데이터설계.md 5절)
- 적용 시나리오는 조치가 아니라 참고 자료라 판단 전에도 요청할 수 있다. (출처: docs/adr/0010-적용-시나리오는-참고-자료.md)
- 시험: `lib/server/judgments.test.ts`, `lib/server/no-service-judgments.test.ts`, `lib/admin/admin-guard.test.ts`, `lib/demo/demo-guard.test.ts`. (출처: 각 파일 안 "불변 1" 표기)
- QA 행: "RLS·불변 1·3·4·5 (P-2)", "판단 저장 (P-8 …, 불변 1·4·5)", "M0 끝까지, 실제 DB (… 불변 1·3·4·5·6)". (출처: docs/qa.md 10·24·41줄)

## 불변 2. 수집 실패는 "수집 오류"로 남긴다
- 수집이 실패하면 "수집 오류"로 기록한다. "변화 없음"이나 "삭제됨"으로 단정하지 않는다. (출처: CLAUDE.md 3절 불변 2)
- 데이터에서는 `run_steps`의 오류 종류와 `my_technologies`의 수집 오류 표시로 남긴다. 실패한 실행은 수집 자료를 만들지 않는다. (출처: docs/데이터설계.md 5절)
- 다운로드 수집이 404를 받아도 0으로 읽지 않는다. (출처: docs/flow.md 2절 fetch_downloads 행)
- 시험: `lib/schedule/run-batch.test.ts`, `lib/server/collect-fetch.test.ts`, `lib/server/downloads-fetch.test.ts`, `lib/server/registry-fetch.test.ts`, `lib/server/first-read.test.ts`, `lib/domain/requirements-txt.test.ts`, `lib/domain/github-repo.test.ts`. (출처: 각 파일 안 "불변 2" 표기)
- QA 행: "불변 2 수집 실패 흐름 (P-3 보강)", "OSV 404·응답 모양·본문 읽기 오류 (P-3, 불변 2)". (출처: docs/qa.md 21·28줄)

## 불변 3. 같은 변경을 다시 읽어도 두 번 생기지 않는다 (멱등)
- 같은 변경을 다시 읽어도 사건·조치가 두 번 생기지 않는다. 멱등은 "여러 번 해도 결과가 한 번 한 것과 같다"는 뜻이다. (출처: CLAUDE.md 3절 불변 3)
- 데이터에서는 `changes`의 중복 막기 키, `alerts`의 사람 + 변경 하나, `my_technologies`의 프로젝트 + 기술 키 하나로 막는다. (출처: docs/데이터설계.md 5절)
- 흐름에서는 같은 변경이 이미 있으면 새로 만들지 않고 그 변경에 잇는다. (출처: docs/flow.md 2절 save_change 행)
- 시험: `lib/domain/keys.test.ts`, `lib/server/collect-osv.test.ts`, `lib/server/collect-registry.test.ts`, `lib/server/collect-downloads.test.ts`, `lib/server/collect-github.test.ts`. (출처: 각 파일 안 "불변 3" 표기)
- QA 행: "알림 만들기·알림 화면 읽기 (P-7 …, 불변 3)", "보안 알림 대상: 버전·긴 목록·기록 실패 (P-7 보강, 불변 3)". (출처: docs/qa.md 23·35줄)

## 불변 4. 거절·저장 실패 때 기존 값을 지킨다
- 승인이 거절되거나 저장이 실패하면 기존 값을 그대로 두고 "처리 완료"로 표시하지 않는다. (출처: CLAUDE.md 3절 불변 4)
- 데이터에서는 `judgments` 저장과 `alerts` 상태 변경을 한 거래로 묶는다. (출처: docs/데이터설계.md 5절)
- 흐름 화면의 저장 실패 시연에서는 조치 상자가 빨강이고 알림은 판단 대기 그대로다. (출처: docs/flow.md 4절)
- 시험: `lib/server/collect-osv.test.ts`, `lib/server/collect-downloads.test.ts`, `lib/server/collect-github.test.ts`, `lib/server/local-import.test.ts`, `lib/server/my-tech.test.ts`. (출처: 각 파일 안 "불변 4" 표기)
- QA 행: "실제 DB에서 저장 실패 → 조치 기록 failed, 가짜 줄 지우기 (불변 4·6)". (출처: docs/qa.md 43줄)

## 불변 5. 권한은 화면·서버·DB 세 곳에서 검사한다
- 권한 검사는 화면뿐 아니라 서버와 DB(RLS)에서도 한다. (출처: CLAUDE.md 3절 불변 5)
- 사용자는 본인이 공개한 것 말고는 본인 데이터만, 관리자 데이터는 관리자만 본다. 공개는 "쓰고 있어요"의 별명과 수뿐이고 설정에서 숨길 수 있다. (출처: CLAUDE.md 3절 불변 5, docs/adr/0009-알파는-설치-프롬프트-공개-목록.md)
- 흐름 기록의 건수도 남의 사용 규모가 드러나지 않게 시작한 사람 기준으로 남긴다. (출처: docs/flow.md 2절 notify 행)
- 시험: `lib/admin/admin-guard.test.ts`, `lib/server/first-read.test.ts`, `lib/server/judgments.test.ts`, `lib/server/notify-owner.test.ts`, `lib/server/my-tech.test.ts`. (출처: 각 파일 안 "불변 5" 표기)
- DB 시험: `supabase/tests/rls_m0.sql`, `supabase/tests/rls_m1.sql`. (출처: docs/qa.md 10·17줄)
- QA 행: "RLS·불변 5 (P-30 M1 테이블 7개)", "내 기술 insert 열 제한 (불변 5)", "C7. 로그인 전 관리자·실행 기록 주소 막기", "H2. 일반 계정 막힘". (출처: docs/qa.md 17·46줄, docs/qa-c.md 31·47줄)

## 불변 6. 흐름 화면은 실제 실행 기록으로만 칠한다
- 흐름 화면은 실제 실행 기록(`runs`, `run_steps`)을 읽어 그린다. 미리 그린 가짜 불빛은 안 된다. (출처: CLAUDE.md 3절 불변 6)
- 데이터에서는 `runs`·`run_steps`만 읽는다. (출처: docs/데이터설계.md 5절)
- 시험: `lib/flow/counts.test.ts`, `lib/flow/status.test.ts`, `lib/server/first-read.test.ts`. (출처: 각 파일 안 "불변 6" 표기)
- QA 행: "알림 run_id와 조치 기록 (불변 5·6)", "C4. P-6·P-20 흐름 색·배치·건수·상세·실행 목록", "H4. 흐름 화면이 실제 기록으로 칠해짐". (출처: docs/qa.md 36줄, docs/qa-c.md 28·49줄)
