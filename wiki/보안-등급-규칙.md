# 보안 등급 규칙

> 보안 등급(위험·주의·통과·찾지 못함) 규칙 SPEC-1, 위험 패턴 P1~P3 SPEC-2, 보안 경고·적용 기회 사건 기준 SPEC-3. (출처: docs/spec.md 1·2·3절)

## 등급은 코드 규칙으로 (SPEC-1)
- 위에서부터 먼저 걸리는 등급을 매기고, 같은 입력에는 늘 같은 등급이 나온다. (출처: docs/spec.md 1절, docs/adr/0003-보안-점검은-규칙-평판은-참고.md)
- 등급마다 쉬운 이유와 근거 링크(어느 취약점, 어느 파일 몇째 줄)를 붙인다. (출처: docs/spec.md 1절)
- v1의 취약점 출처는 OSV 하나다. (출처: docs/adr/0003-보안-점검은-규칙-평판은-참고.md 개정 2026-11-18)

| 등급 | 조건 (하나라도 맞으면) | 출처 |
|---|---|---|
| 위험 | ① 지금 버전에 OSV HIGH·CRITICAL 취약점이 있고 고친 버전보다 낮음 ② 위험 패턴 P1, 또는 P2의 가까운 짝(15줄 안) | 출처: docs/spec.md 1절 SPEC-1 |
| 주의 | ① OSV MODERATE·LOW ② 12개월 넘게 커밋·릴리스 없음 ③ 라이선스 없음 ④ 출처에서 중단·사라짐 ⑤ P3, 또는 P2의 먼 짝 | 출처: docs/spec.md 1절 SPEC-1 |
| 통과 | 위에 해당하지 않고 OSV 조회와 저장소 정보 확인을 실제로 마침 | 출처: docs/spec.md 1절 SPEC-1 |
| 찾지 못함 | 근거를 하나도 확인하지 못함(이름만 직접 추가 등) | 출처: docs/spec.md 1절 SPEC-1 |

- 심각도는 OSV가 주는 값을 그대로 쓰고 팀이 판단하지 않는다. (출처: docs/spec.md 1절)
- 버전을 모르면 HIGH·CRITICAL이 하나라도 열려 있으면 위험, 모두 고쳐졌으면 주의로 본다. (출처: docs/spec.md 1절)
- 수집에 실패하면 등급을 바꾸지 않고 "수집 오류 (마지막 확인 날짜)"를 함께 보여 준다. (출처: docs/spec.md 1절, 불변 2)
- 개념(하네스 등)에는 등급이 없다. (출처: docs/spec.md 1절)
- 고친 버전은 지금 버전의 HIGH·CRITICAL 문제를 모두 고치는 가장 낮은 버전이다. 하나라도 고친 버전이 없으면 "아직 고친 버전이 없어요". (출처: docs/spec.md 1절, 10절 2026-11-18 다시 조회)
- 위험한 버전은 적용 후보가 될 수 없고, 보안 경고의 적용 후보는 "고친 버전으로 올리기"다. (출처: docs/adr/0012-M0-확인-범위와-보안-경고의-적용-후보.md)

## 기술 상태와 주의 근거 (ADR 0021)
- 기술 상태(활동 중·쉬는 중·중단·사라짐)는 여러 수집기가 정해서, 정한 출처를 `status_by`에 `<출처>:<상태>`로 적는다. (출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md 정한 것)
- GitHub 수집기는 활동 중인 기술과 자기가 정한 상태만 건드린다. (출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md 정한 것)
- "사라짐"은 그 저장소를 찾은 적이 있고, 성공한 읽기에서 404가 2번 연속이고, 첫 404에서 12시간이 지나야 정한다. (출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md "출처에서 사라짐")
- 12개월·404 두 번·12시간은 팀 추정이다. (출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md 확인하지 못한 것)

## 위험 패턴 (SPEC-2)
- 스킬 폴더 파일과 MCP 저장소 코드에서 문구로 찾고, 찾으면 파일과 줄 번호를 이유로 보여 준다. (출처: docs/spec.md 2절)

| ID | 이름 | 찾는 것 (요약) | 등급 | 출처 |
|---|---|---|---|---|
| P1 | 원격 실행 | 내려받은 것을 바로 셸·`eval`로 실행하는 모양 | 위험 | 출처: docs/spec.md 2절 P1 |
| P2 | 비밀값 밖으로 보내기 | 비밀값을 읽는 코드와 바깥으로 보내는 코드가 15줄 안에 함께 있음 | 위험(15줄 안), 주의(같은 파일에서 더 멀 때) | 출처: docs/spec.md 2절 P2 |
| P3 | 넓은 권한 | 모든 셸 명령 허용, 홈 폴더 전체 읽기·쓰기 | 주의 | 출처: docs/spec.md 2절 P3 |

- 화면에 한계를 적는다: 검사가 찾은 것만 표시하고, 못 찾았다고 안전하다는 뜻이 아니다. (출처: docs/spec.md 2절)
- 2000자가 넘는 줄은 검사하지 않고 따로 세며, 그런 줄이 있거나 읽은 파일이 없으면 "찾지 못함"으로 둔다. (출처: docs/spec.md 2절)
- v1 구현이 아직 못 찾는 모양(주소에 붙여 보내기, 다른 이름의 요청 객체, 문장 지시 등)이 있다. 15줄은 제안값이다. (출처: docs/spec.md 2절 P-10)
- 패턴 목록은 관리자가 더할 수 있고 `audit_logs`에 남는다. 검사 주기는 새 버전·커밋이 생겼을 때 + 주 1회. (출처: docs/spec.md 2절)

## 사건(변경) 기준 (SPEC-3)
- 보안 경고: 두꺼운 기술의 등급이 위험이 아닌 것 → 위험으로 바뀔 때. 위험 → 고쳐짐 → 다시 위험이면 회차가 올라 새 변경이 된다. (출처: docs/spec.md 3절 SPEC-3.1)
- 처음 확인한 위험: 처음 읽기·다시 읽기에서 새로 들어온 내 기술이 이미 위험일 때. 알림 키는 사람 + 기술 + 버전 + 원인이라 같은 사람에게 두 번 생기지 않는다. (출처: docs/spec.md 3절 SPEC-3.1)
- 그 기술을 쓰는 사람마다 알림 1개가 생긴다. 같은 취약점의 별칭(CVE·GHSA·PYSEC)은 같은 원인으로 본다. (출처: docs/spec.md 3절 SPEC-3.1)
- 적용 기회: ① 같은 역할로 확정(관리자 확인만) ② 내가 등록한 뒤 들어옴 ③ 새 기술이 위험이 아님 — 셋이 모두 맞을 때만. (출처: docs/spec.md 3절 SPEC-3.2, ADR 0014·0015)
- 적용 기회 조건 ②의 예외: 레지스트리 첫 전체 읽기(대량 채우기)로 들어온 기술은 "들어온 날"이 새로 나온 날이 아니라서 ②로는 맞지 않고, 같은 역할 확정 조건만 본다. (출처: docs/spec.md 3절 SPEC-3.2 조건 2, 2026-11-20 `I-P-12d-new-bulk`)
- 모델 지원 종료(SPEC-3.3)는 3순위로 **만들었다**(PR #201). 첫 시연에는 넣지 않는다는 spec 머리 문장은 그대로다. (출처: docs/spec.md 3절 SPEC-3.3, docs/plan.md 4절 P-22)
  - 공식 표: Anthropic·OpenAI·Google 지원 종료 쪽의 모델 이름·종료일·공식 추천 대체만 옮긴다. 날짜가 없거나 자동으로 새 모델로 넘어가는 모델은 넣지 않는다. 표가 바뀌면 파일을 고쳐 배포해야 반영된다. (출처: docs/spec.md SPEC-3.3 "공식 표")
  - 찾기: 내 저장소 코드·설정 파일 100개까지 열고, 따옴표로 감싼 문자열이 표의 이름과 **똑같을 때만** 잡는다. 한 파일에 종료 모델이 5개 넘으면 목록·가격표로 보고 뺀다. (출처: docs/spec.md SPEC-3.3 "코드 읽기"·"찾기")
  - 알림: 보안 경고와 같은 길(쓰는 사람마다 하나), 같은 모델·같은 종료일은 다시 읽어도 늘지 않는다(불변 3). 대응안 초안은 만들지 않는다. (출처: docs/spec.md SPEC-3.3 "기록·알림")
  - 못 읽으면: 파일 목록을 못 읽으면 그 프로젝트의 모델 줄 모두, 일부 파일만 못 봤으면 다시 보지 못한 모델 줄만 "수집 오류"(불변 2). (출처: docs/spec.md SPEC-3.3 "못 읽으면")

| 사건이 아닌 것 | 처리 | 출처 |
|---|---|---|
| 같은 값을 다시 읽음 | 수집 기록만, 아무것도 안 만듦 | 출처: docs/spec.md 3절 SPEC-3.4 |
| 통과 ↔ 주의 | 등급만 바꾸고 알림 없음(v1은 위험만 알림) | 출처: docs/spec.md 3절 SPEC-3.4 |
| 위험 → 고쳐짐 | 알림 없음, 기존 알림 상세에 "지금은 고쳐졌어요" | 출처: docs/spec.md 3절 SPEC-3.4 |
| 수집 실패 | "수집 오류", 사건 아님 | 출처: docs/spec.md 3절 SPEC-3.4 |
| 일반 소식·추천 | 알림이 아님 | 출처: docs/spec.md 3절 SPEC-3.4 |

- 시뮬레이터의 가짜 변경은 "시뮬레이터" 표시를 달고, 알림은 시연 계정에만 만든다. (출처: docs/spec.md 3절 SPEC-3.5)

## 문서끼리 다른 곳
- ADR 0003 본문은 취약점 출처에 deps.dev·GitHub Advisories를 넣고 보안 사고 제보를 "주의"로 올린다고 쓴다(출처: docs/adr/0003-보안-점검은-규칙-평판은-참고.md 본문) / 같은 파일의 개정 줄은 v1 출처는 OSV 하나, 제보로 올리지 않음, 등급은 찾지 못함까지 네 가지라고 쓴다(출처: docs/adr/0003-보안-점검은-규칙-평판은-참고.md 개정 2026-11-18).
- spec 2절은 "패턴을 바꾸면 규칙 버전을 올린다"고 쓴다(출처: docs/spec.md 2절) / P2를 15줄 기준으로 바꾼 기록은 규칙 버전(v1) 올리기를 보류했다고 쓴다(출처: docs/spec.md 바뀐 기록 2026-11-18 SPEC-2 P2).
