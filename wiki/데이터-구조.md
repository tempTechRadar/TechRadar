# 데이터 구조

> TechRadar DB(Supabase)의 테이블별 한 줄 설명과 접근 규칙(RLS) 요약. 칸·값의 정본은 `docs/erd.md`이고, 두 문서가 다르면 erd를 따른다. (출처: docs/데이터설계.md 머리말 5줄, docs/erd.md 0·2·4절)

## 공통 규칙
- 모든 테이블의 기본키는 `id uuid`이고, `profiles.id`는 Supabase 로그인 사용자 id와 같다. (출처: docs/erd.md 0절)
- 정해진 값은 DB enum 대신 `text` + `check`로 둔다. 값을 바꾸기 쉽게 하려는 것이다. (출처: docs/erd.md 0절)
- 시각은 모두 UTC로 저장하고 화면에서만 한국 시간으로 보인다. (출처: docs/erd.md 0절)
- 사용자 데이터는 지우지 않고 `archived_at`·`hidden_at`으로 숨긴다. (출처: docs/erd.md 0절)
- 시뮬레이터가 만든 가짜 줄에는 `is_simulated = true`를 단다. (출처: docs/erd.md 0절)
- `run_steps`의 요약·오류는 저장 전에 비밀값을 가린다. (출처: docs/erd.md 0절)
- RLS는 모든 테이블에 켠다. 판단 저장은 사용자 로그인 토큰으로만 한다. (출처: docs/erd.md 0절)

## 어떻게 이어지나
- 사람 → 내 프로젝트 → 내 기술 → (기술 키) → 공용 기술 카탈로그. (출처: docs/데이터설계.md 0절)
- 출처 → 실행 기록 → 수집 자료(바뀐 값만) → 변경(공용) → 알림(사람마다) → 판단(알림당 하나). (출처: docs/데이터설계.md 0절)
- 바깥 변화는 변경 한 줄로 한 번만 저장하고, 그 기술을 쓰는 사람마다 알림을 만든다. (출처: docs/데이터설계.md 1절 원칙 4, docs/erd.md 5절)

| scenarios | 적용 시나리오(참고 자료). 요청할 때만 | 출처: docs/erd.md 2.5절 |

| grade_views | 등급 이유를 연 기록(주 숫자 계산용) | 출처: docs/erd.md 2.6절 |
| audit_logs | 바꾼 기록. 덧붙이기만 | 출처: docs/erd.md 2.6절 |
| ai_calls | Claude 호출 기록. 같은 입력은 다시 보내지 않음 | 출처: docs/erd.md 2.6절 |
| chat_logs | 위키 챗봇 기록(팀원·관리자만). 답 800자 안 | 출처: docs/erd.md 2.6절 |

- 판단 저장과 `alerts.status = done`은 DB 함수 하나의 한 거래로 한다. (출처: docs/erd.md 2.5절 judgments 아래)
- 등급이 두 곳(`technologies`, `my_technologies`)에 있는 이유: 취약점은 버전마다 달라서 내 목록·알림은 내 버전 등급을 본다. (출처: docs/erd.md 2.2절 "왜 등급이 두 곳에")
- 알림 없는 판단은 DB 함수 `set_tech_mark` 하나로만 쓴다. 적용 후보·보류면 그 기술의 본인 판단 대기 알림도 함께 판단하고, 표시와 기록까지 한 거래로 남긴다(하나라도 실패하면 모두 그대로, 불변 4). 같은 값이면 기록이 늘지 않는다(불변 3). (출처: docs/erd.md 2.5절 tech_marks 아래)

## 실제 DB와 맞춰 본 결과
- 2026-11-20 3차 중간 대조: 운영 DB의 공개 표 26개가 erd 2절의 26개와 같고, 표마다 칸 이름이 모두 일치하며, RLS는 26개 모두 켜져 있다. 비교한 것은 표·칸 이름, 칸 수, 정책 수, RLS 켜짐뿐이다. (출처: docs/erd.md 7절 3차 대조)
- 팀이 대조한 사람·날짜 칸은 아직 비어 있다. 최종 대조는 코드 동결 직후 다시 한다(동결은 11-21에 18:00 → 21:00으로 바뀜). (출처: docs/erd.md 7절 3차 대조, docs/plan.md 월 마무리 표)

- 2026-11-23 4차 대조(동결 전 미리 보기): 운영 DB의 공개 표 34개가 erd 2절의 34개와 같고, RLS는 34개 모두 켜져 있다. 빠져 있던 `technologies`의 한국어 개요 3칸(`one_liner_ko` · `one_liner_ko_src` · `one_liner_ko_at`)은 erd에 더했다. (출처: docs/erd.md 7절 4차 대조, 2.3절)
- 칸이 아닌 변경도 4차에서 맞췄다: `ai_calls.purpose` 허용 값 7개, 청사진 graph의 `sections`, 섹션 공통 기술도 공개 목록을 검사하는 `template_unlisted_techs`, 관리자 지정 · 되돌리기 함수. 세 사람의 서명은 동결 뒤 최종 대조에서 한다. (출처: docs/erd.md 7절 4차 대조, 2.6절, 4절, 바뀐 기록 11-23)
- 로그인 전 지도의 공개 칸에 한 줄 설명의 출처 주소와 한국어 개요 3칸이 더해졌다. 모두 공개 한 줄 소개에서 나온 값이라 새 개인 정보가 없다. (출처: docs/adr/0029-로그인-전-지도는-RLS를-열지-않고-서버가-공개-칸만-읽는다.md 결정 3, docs/adr/0045-AI를-쓰는-두-곳-청사진-프롬프트-진단-기술-한국어-개요.md 결정 2)

## 문서끼리 다른 곳
- 챗봇 "한 사람 하루 20개" 한도를 어느 표를 세서 거는지가 두 문서에서 다르다. 한쪽으로 정리하지 않고 둘 다 적는다. (출처: docs/데이터설계.md 146줄, docs/erd.md 366줄)
- 문서 A: 데이터설계는 `ai_calls`로 하루 호출 한도를 걸고, 챗봇의 하루 20개 한도는 `chat_logs`를 세서 건다고 적었다. (출처: docs/데이터설계.md 2절 H, 146줄)
- 문서 B: erd는 `ai_calls` 설명 바로 아래에 "하루 한도(SPEC-9)는 이 테이블을 세서 건다"고 적었고, SPEC-9의 한도 표에는 위키 챗봇 "사람당 하루 20번"이 들어 있다. (출처: docs/erd.md 2.6절 ai_calls, 366줄, docs/spec.md 9절 261줄)
- 참고: 데이터설계 머리말은 "칸·값은 erd가 정본"이라고 적었지만, 이 한도를 어느 표로 세는지가 칸·값에 드는지는 원문에 없다. (출처: docs/데이터설계.md 5줄)
- 사실(코드, PR #125 합친 뒤 · 11-23 고침): 챗봇 코드는 두 표를 모두 센다. 한 사람 하루 20개는 `chat_logs`(본인 줄)에 Claude 호출이 실패해 `ai_calls`에만 남은 본인 줄을 더해 세고, 서비스 전체 하루 200번은 `ai_calls`로 센다. 문서끼리의 차이는 그대로 남아 있다. (출처: lib/server/chat.ts 2·63–67줄, lib/ai/decide-ai-call.ts 17–18줄)
