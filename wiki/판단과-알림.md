# 판단과 알림

> 판단(승인) 규칙 SPEC-4와 알림 내용 SPEC-5: 적용 후보·보류, 관리자는 자기 알림만 판단 가능, 보안 경고·첫 점검·적용 기회 알림 문구. (출처: docs/spec.md 4·5절)

## 판단 상태 (SPEC-4.1)
| 지금 상태 | 할 수 있는 일 | 다음 상태 | 출처 |
|---|---|---|---|
| 판단 대기 | 적용 후보 / 보류(이유 필수) | 완료 | 출처: docs/spec.md 4.1절 |
| 판단 대기 · 완료 | 적용 시나리오 만들기(요청) | 그대로 | 출처: docs/spec.md 4.1절 |
| 완료 | 기록 보기 | 그대로 | 출처: docs/spec.md 4.1절 |

- 판단과 상태 바꾸기는 한 거래로 저장한다. 실패하면 둘 다 그대로이고 "저장하지 못했어요. 다시 시도해 주세요". (출처: docs/spec.md 4.1절, 불변 4)
- 불변 4의 "승인 거절"은 우리 말로 보류다. 알림 "완료"는 판단을 마쳤다는 뜻이지 조치를 실행했다는 뜻이 아니다. (출처: docs/spec.md 4.1절, ADR 0010)
- 보류 이유는 5자 이상이다(팀 추정 숫자). (출처: docs/spec.md 4.1절, 11절)
- v1에서는 판단을 고칠 수 없다. 같은 기술에 새 변경이 오면 새 알림으로 다시 판단한다. (출처: docs/spec.md 4.1절, 12절 SQ1)

## 관리자와 판단
- 관리자도 자기 알림에는 다른 사용자와 같은 규칙으로 판단(적용 후보·보류)을 저장할 수 있다. (출처: docs/spec.md 4.1절, docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것)
- 관리자도 남의 알림에는 판단을 만들거나 건너뛸 수 없다. 화면·서버·DB 모두에서 막는다. (출처: docs/spec.md 4.1절, docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것)
- 화면: 관리자 알림 현황(IA-14)에는 판단 버튼이 없다. 이것은 모든 회원의 알림 목록 화면 이야기다. (출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 결과, docs/ia.md 4절 IA-14)
- DB: 함수 `save_judgment`는 "본인 알림인가"만 확인한다. (출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md, supabase/migrations/202611181400_P-2_m0_tables.sql 297줄)
- 시험 `admin_judge_other_blocked`가 남의 알림 판단이 막히는 것을 본다. 관리자 본인 알림 판단이 되는지 보는 시험은 없다. (출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 결과)
- 팀 CLAUDE.md 불변 1("관리자도 승인을 건너뛸 수 없다")은 남이 대신 건너뛰는 것을 막는 규칙으로 읽고, 문장은 바꾸지 않는다. (출처: CLAUDE.md 3절 불변 1, docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것)
- 흐름 설정 값도 같다: `admin_can_judge_own` 참, `admin_can_judge_others` 거짓. (출처: flow/flow.json 40줄)

## 적용 시나리오 (SPEC-4.2)
- "적용 시나리오 만들기"를 누를 때만 만들고, 사용자당 하루 5번이다. (출처: docs/spec.md 4.2절)
- 비교표, 적용 단계, 위험과 되돌리는 방법, 출처가 들어간다. 출처가 없으면 "찾지 못함". (출처: docs/spec.md 4.2절)
- 설치 명령은 카탈로그의 공식 설치 명령만 쓴다. (출처: docs/spec.md 4.2절, ADR 0009)
- 시나리오는 참고 자료라 판단 전후 언제든 만들 수 있고, 조치는 판단 저장이다. (출처: docs/spec.md 4.2절, ADR 0010)

## 설치 프롬프트와 같은 역할 (SPEC-4.3·4.4·4.5)
- 설치 프롬프트에는 세 출처(저장소에서 읽은 것 / 값 검사를 통과한 가져오기 / 공식 이름과 정확히 같은 카탈로그 적용 후보)만 넣는다. (출처: docs/spec.md 4.3절)
- 위험한 버전은 어떤 경우에도 넣지 않고, 보안 경고에서 적용 후보로 판단한 것은 고친 버전으로 고정한다. (출처: docs/spec.md 4.3절, ADR 0012)
- 같은 역할은 후보 → 관리자 확인으로만 확정된다(담당자·시각·사유). 자동 확정은 3순위다. (출처: docs/spec.md 4.4절, ADR 0015)
- 비슷한 과거 판단은 규칙으로 찾는다: 같은 기술 → 같은 역할 → 같은 작은 갈래 순, 각각 최근 것부터 3개까지. (출처: docs/spec.md 4.5절)

## 알림 내용 (SPEC-5)
- 알림은 앱 안에서만 보인다. 값이 없으면 "찾지 못함". (출처: docs/spec.md 5절)

| 알림 | 담는 것 (요약) | 버튼 | 출처 |
|---|---|---|---|
| 보안 경고 (5.1) | 기술 이름과 이전 등급 → 위험, 무엇이 바뀌었나(출처·시각), 쉬운 이유, 내 프로젝트·파일, Claude 대응안 초안, 비슷한 지난 판단 | 고친 버전으로 올리기(적용 후보) / 보류(이유) / 적용 시나리오 만들기 | 출처: docs/spec.md 5.1절 |
| 처음 확인한 위험 (5.2) | "지금 위험이에요", 이유와 출처, 고친 버전(없으면 "아직 없음"). 지도 띠에 "첫 점검: 위험 n · 주의 n" | 5.1과 같음 | 출처: docs/spec.md 5.2절 |
| 적용 기회 (5.3) | 같은 역할 새 기술, 비교 5항목(하는 일·보안 등급과 이유·최근 업데이트·사용량·라이선스, 항목마다 출처), 같은 역할 확정 날짜 | 적용 후보 / 보류(이유) / 적용 시나리오 만들기 | 출처: docs/spec.md 5.3절 |

- 보안 경고의 적용 후보는 고친 버전 번호를 판단과 함께 저장한다(`judgments.fixed_version`). (출처: docs/spec.md 5.2절 아래 문단)
- 고친 버전이 없으면 판단 버튼은 [보류]만 보이고, [적용 시나리오 만들기]는 그대로 있다. (출처: docs/spec.md 5.2절 아래 문단)
- 대응안 초안은 변경마다 1번(공용)이다. (출처: docs/spec.md 9절 SPEC-9)

## 문서끼리 다른 곳
- 문서점검 D-6은 spec·데이터설계·flow.json이 "관리자는 판단을 아예 만들 수 없다"(`admin_can_judge: false`)고 했다고 적는다(출처: docs/문서점검-20261118.md 28줄 D-6) / 지금 spec 4.1과 flow.json은 관리자도 본인 알림은 판단할 수 있다고 쓴다(출처: docs/spec.md 105줄, flow/flow.json 40줄, docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md).
- 관리자 시연 화면 안내 문구는 "관리자는 판단할 수 없으니 시연 계정으로 로그인해 판단하세요"라고 쓴다(출처: app/admin/demo/page.tsx 54줄) / ADR 0016은 관리자도 자기 알림에는 판단할 수 있다고 쓴다(출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것).
- 팀 불변 1 문장은 "관리자도 승인을 건너뛸 수 없다"로 넓게 쓰여 있다(출처: CLAUDE.md 3절 불변 1) / ADR 0016은 이것을 "남의 알림" 한정으로 읽고 문장은 바꾸지 않는다고 쓴다(출처: docs/adr/0016-관리자도-본인-알림은-판단할-수-있다.md 정한 것).
