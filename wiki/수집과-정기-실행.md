# 수집과 정기 실행

> 수집 출처 4개(OSV, GitHub, MCP 레지스트리, npm·PyPI 다운로드), 순서와 시간 예산, 매일 06:00(한국 시간) 정기 실행과 관리자 "지금 한 번 실행", 수집 오류 기록. (출처: docs/spec.md 8절 SPEC-8)

## 언제 도나
- 정기 실행은 매일 06:00(한국 시간) 하루 1번이고, 관리자의 "지금 한 번 실행"도 있다. (출처: docs/spec.md 236줄 SPEC-8, docs/prd.md PRD-F8)
- Vercel Hobby는 정기 실행이 하루 1번까지이고 시각이 지정 시각부터 59분 안 어디서든이라, 실제로는 06:00~06:59 사이 어느 때 돈다. (출처: docs/spec.md 236줄, 323줄 SQ4)
- 그래서 시연 때 정각을 약속하지 않는다. (출처: docs/spec.md 바뀐 기록 2026-11-18 열린 질문 사실 확인)
- `vercel.json`의 예약은 `/api/cron/daily`, 시각은 UTC `0 21 * * *`(한국 시간 06:00)이다. (출처: vercel.json, flow/flow.json 13줄 `cron_utc`)
- 시각은 DB에 UTC로 저장하고 화면에서만 한국 시간으로 보여 준다. (출처: docs/erd.md 14줄)
- Hobby 함수는 최대 300초라 실행을 짧은 단위로 나눈다. (출처: docs/spec.md 236줄, 323줄 SQ4)
- 정기 실행과 "지금 한 번 실행"은 같은 수집기 목록(`SCHEDULE_COLLECTORS`)을 부른다. (출처: lib/schedule/collectors.ts 머리 주석, docs/plan.md P-17)
- 관리자 "지금 한 번 실행"은 수집 실행과 오류 화면(IA-15)에 있다. (출처: docs/ia.md 4절 IA-15, docs/prd.md PRD-F27)
- 첫 예약 실행은 2026-11-20 06:07(한국 시간)에 성공했다(운영 `runs` 1건, schedule, 2,300건). (출처: docs/제출물-체크리스트.md 정기 실행 행, docs/worklog.md I-qa-c-1120 행)
- 정기 실행과 "지금 한 번 실행"은 겹쳐 돌지 않는다: 시작 전에 최근 6분 안에 시작해 아직 도는 정기·지금 실행이 있으면, 새 묶음은 실행 기록 없이 "이미 돌고 있어요" 이유만 돌려준다(PR #181). (출처: docs/intent.md I-run-batch-overlap 기대 결과, docs/worklog.md I-run-batch-overlap 행)
- 한계: 마이그레이션 없이 고친 것이라 거의 같은 순간에 둘이 시작하면 둘 다 돈다. 확인 조회가 실패하면 막지 않고 실행한다. 실제 DB에서 두 번 눌러 보기는 확인하지 못했다. (출처: docs/intent.md I-run-batch-overlap 제약·결과)

## 배포는 누가 부르나
- main의 production 배포는 GitHub Actions `production 배포`가 부른다: 병합 뒤 20분 잠잠하면, 운영에 올라간 커밋(`/api/version`) 뒤로 앱 파일이 바뀌었을 때만 Deploy Hook을 한 번 부른다. 이 결정(ADR 0023)의 상태는 **제안**이다. (출처: docs/adr/0023-production-배포는-GitHub-Actions가-부른다.md 상태·정한 것, CLAUDE.md 10절)
- 그래서 `vercel.json`은 main의 Git 자동 배포를 끄고(`main: false`) `ignoreCommand`를 지웠다. 정기 실행 예약(`/api/cron/daily`, `0 21 * * *`)은 그대로다. (출처: vercel.json, docs/adr/0023-production-배포는-GitHub-Actions가-부른다.md 정한 것)

## 정기 실행 주소의 비밀값
- 정기 실행 주소에는 환경변수 `CRON_SECRET`이 필요하다. 값이 비어 있으면 누구에게나 401을 돌려준다(의도된 동작). (출처: docs/debug-note.md 2026-11-19 행, lib/schedule/cron-auth.ts)
- 2026-11-19 첫 정기 실행 뒤 정기 실행 기록이 0줄이었고, 원인은 운영 환경변수에 `CRON_SECRET`이 없던 것이다. (출처: docs/debug-note.md 2026-11-19 행)
- 환경변수는 새 배포부터 적용되어, 넣은 뒤 운영 배포를 한 번 해야 한다. (출처: docs/debug-note.md 2026-11-19 행)
- 11-19에는 `CRON_SECRET`이 없어 돌지 않았고, 11-20 06:07 첫 예약 실행이 성공했다. (출처: docs/제출물-체크리스트.md 정기 실행 행)

## 레지스트리 읽기
- 처음 한 번은 전체를 읽고, 그다음부터는 지난번 이후 바뀐 것만 읽는다. (출처: docs/spec.md 8절 251줄)
- 최신 서버가 66,788개·668쪽이라, 한 실행 20쪽 안팎이면 첫 전체 읽기에 약 33일 걸린다(어림). 대책은 팀 결정으로 남았다. (출처: docs/spec.md 8절 251줄)
- 한 실행에 다 못 읽으면 다음 쪽 커서를 `sources`에 적고 다음 실행이 이어 읽는다. (출처: docs/spec.md 8절 251줄, docs/flow.md 2절 fetch_registry)

## OSV 다음 쪽 읽기
- OSV 결과가 쪽으로 나뉘면 `next_page_token`을 이어 받는다(최대 10쪽, 쪽 사이 1초). 404·모양이 다른 응답·본문 읽다 끊김·같은 표시 되풀이·10쪽 초과는 그 기술만 수집 오류다. (출처: docs/data-sources.md 0절 OSV 행, `I-P-3-osv-next-page`)

## 다른 도구 설정과 연동 서비스·개념 (SPEC-7.1·7.4, 3순위)
- 다른 AI 도구의 MCP 설정 `.cursor/mcp.json`(Cursor)·`.vscode/mcp.json`(VS Code)·`.gemini/settings.json`(Gemini CLI)을 `.mcp.json`과 같은 규칙으로 읽는다. 인자는 패키지 이름 모양만 기술로 봐서 옵션 값·토큰이 기술 이름이 되지 않는다. (출처: docs/spec.md 7절 SPEC-7.1 "11-20 구현", PR #201)
- 연동 서비스는 공식 MCP가 있는 서비스만이다. 레지스트리에서 회사 도메인·조직으로 인증된 서버를 확인한 13개(Supabase·Vercel·Stripe 등)이고, SDK 의존성이 먼저, 없으면 설정 파일로 찾는다. (출처: docs/spec.md 7절 SPEC-7.4 "연동 서비스"·"찾는 법")
- 개념(작업 방식)은 등급·알림이 없는 지도 노드다: 하네스(`CLAUDE.md`·`AGENTS.md`·`GEMINI.md`), 서브에이전트, 슬래시 명령. 모델·연동 서비스·개념은 설치 프롬프트 목록에서 뺀다. (출처: docs/spec.md 7절 SPEC-7.4 "개념")
- 파일 목록을 못 읽으면 이번에 다시 보지 못한 모델·서비스·개념 줄은 "수집 오류"다(불변 2). (출처: docs/spec.md 7절 SPEC-7.4 "못 읽으면")

## 실패와 수집 오류 기록
- 재시도: 실행 단위로 총 3번 시도(2분·4분 뒤). 지금 코드는 다음 시도 시각만 `runs.next_retry_at`에 적고, 실제로 다시 돌리는 일은 관리자 "지금 실행"이 한다(자동 재시도는 아직 없음). (출처: docs/spec.md 8절 247줄)
- 같은 출처가 3번 연속 수집 오류면 관리자 화면(IA-15)에 강조한다. (출처: docs/spec.md 8절, docs/uj.md 5절 UJ-M1)
- 오류 종류는 시간 초과 / 네트워크 / 한도 초과 / 상태 코드 / 해석 실패다. 요청 사이 간격은 1초 이상. (출처: docs/spec.md 8절)
- 실행 기록과 오류 메시지는 저장 전에 비밀값처럼 보이는 문자열을 `***`로 가린다. (출처: docs/spec.md 8절 252줄)
- 수집 실패는 "수집 오류"로 기록하고 "변화 없음"·"삭제됨"으로 단정하지 않는다. (출처: CLAUDE.md 3절 불변 2)
- 다운로드는 일부 기술이 실패하면 이전 값을 그대로 두고 오류 건수로 세며, 404를 0으로 읽지 않는다. (출처: docs/flow.md 2절 fetch_downloads)
- 정기 수집은 `collect_error` 상자를 단계로 기록해 흐름 화면에서 켜진다. (출처: docs/flow.md 2절 collect_error)

## 흐름에서의 자리
- 카탈로그 수집 길: 예약 또는 지금 실행 → 바깥 출처 → 같은 모양 → 이전 값과 비교 → 등급 → 사건인가. (출처: docs/flow.md 1절)
- 예약은 `runs.trigger=schedule`, 지금 실행은 `manual`로 남는다. (출처: docs/flow.md 2절, flow/flow.json 13·14줄)
- 다운로드·GitHub·레지스트리의 바뀐 값은 수집 자료로만 남고 등급 계산으로 넘어가지 않는다. (출처: docs/flow.md 바뀐 기록 2026-11-18 P-9·P-9b·P-9c)

## 문서끼리 다른 곳
- spec 8절 표와 flow.json은 OSV를 "묶음 조회"(`batch: true`)로 적는다(출처: docs/spec.md 240줄, flow/flow.json 20줄) / spec 바뀐 기록과 flow.md는 정기 OSV가 (기술, 버전)마다 한 번 묻고 묶음 조회는 하지 않는다고 쓴다(출처: docs/spec.md 342줄, docs/flow.md 2절 fetch_osv).
- ADR 0021 머리의 결정은 "기술당 1번: 저장소 정보"다(출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md 상태 줄) / 같은 ADR의 코드 검토 반영과 spec 8절 표는 저장소마다 1번이라고 쓴다(출처: docs/adr/0021-기술-상태는-정한-출처를-적고-자기가-정한-상태만-되돌린다.md 코드 검토 반영, docs/spec.md 242줄).
- debug-note는 11-19 기준 운영에 `CRON_SECRET`이 없었고 고친 뒤 확인은 "아직 확인 전"이라고 쓴다(출처: docs/debug-note.md 2026-11-19 행) / plan은 `CRON_SECRET` 넣기를 11-19 "끝남"으로 적고, 첫 확인 기회를 11-20 06:00~06:59로 둔다(출처: docs/plan.md 155줄, 128줄).
