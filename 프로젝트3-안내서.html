비공개 초안입니다. 수강생에게 보이지 않는 로컬 파일이며 배포하지 않았습니다.

프로젝트 3: 바깥 세상의 변화를 지켜보다가, 일이 생기면 움직이는 서비스

세 명 정도가 한 팀입니다. 사용자의 문제 하나를 정하고, 바깥에서 바뀌는 것을 지켜보다가, 중요한 변화가 생기면 알리고, 사람이 확인해서 처리하고, 기록으로 남기는 웹서비스를 함께 만듭니다.

★프로젝트 개요

  • 한 문장으로: 바깥 세상의 변화를 지켜보다가, 중요한 변화가 생기면 알리고, 사람이 확인해 처리하고, 기록으로 남기는 웹서비스를 팀이 함께 만듭니다.
  • 왜 하나요: 지금까지 배운 것(웹앱, DB, 로그인, 자동화, 서브에이전트, RAG, LLM 위키, GitHub 협업)을 한 서비스에 모아 쓰고, 그 과정을 기록과 포트폴리오로 남깁니다.
  • 누가 하나요: 세 명 정도가 한 팀입니다. 팀 과제와 별도로 각자 포트폴리오와 이력서를 만듭니다.
  • 가장 중요한 것: 문제 정의입니다. 누구의 어떤 문제인지 사람을 만나 확인하고, 그 근거로 무엇을 만들지 정합니다.
  • 무엇이 남나요: 배포한 서비스 주소, 발표 슬라이드 주소, 팀 저장소(문서, 코드, 위키), 개인 포트폴리오와 이력서, vibelog 기록입니다.
  • 기간과 배점: 기간과 제출 기한은 공지에 따르고, 배점은 강사 평가표에서 안내합니다.

서비스는 이렇게 돕니다 (채용 공고 예시)

  1. 가져오기: 정해진 시간마다 관심 공고의 제목, 주소, 마감일을 읽어 옵니다. 사람이 버튼을 누르지 않아도 돕니다.
  2. 비교하기: 저장해 둔 마감일과 새 마감일을 비교합니다. 20일에서 18일로 앞당겨졌다면 "확인할 변화"로 올립니다.
  3. 사건 만들기: 기준을 넘는 변화만 사건 한 건으로 만듭니다. 사건은 사고가 아니라 사용자가 확인하고 처리해야 할 변화입니다.
  4. 알리기: 사용자에게 알리고, 지원 일정 수정안을 함께 보여 줍니다.
  5. 사람이 승인: 사용자가 승인해야 일정이 바뀝니다. 승인 전에는 아무것도 바꾸지 않습니다.
  6. 기록하기: 무엇이 바뀌었고 어떻게 처리했는지 남기고, 다음에 비슷한 일이 생기면 과거 기록을 찾아 보여 줍니다.
  7. 보여 주기: 이 모든 단계가 도는 모습을 흐름 화면에서 상자와 화살표로 봅니다.

다른 주제를 고르면 공고, 마감일, 지원 일정을 우리 서비스에 맞게 바꿉니다. 여기에 팀이 고른 알파 하나(예: 메신저 알림, 외부 캘린더 반영)를 더합니다.

꼭 들어갈 여덟 가지

방법은 팀이 고릅니다. 아래 여덟 가지가 서비스 안에서 하나의 흐름으로 이어지는 것이 가장 중요합니다. 여기에 팀이 고른 알파 하나를 더합니다.

1 문제 정의

누가 무엇을 놓쳐 어떤 손해를 보는지 인터뷰 근거와 함께 한 장으로 씁니다.

2 지켜보기

서로 다른 출처의 실시간 데이터를 2개 이상 정해진 간격으로 저절로 모아 같은 모양으로 맞춥니다.

3 사건

어떤 변화가 사건인지 기준을 적고, 기준을 넘으면 사건이 만들어집니다. 사건 종류는 2개 이상입니다.

4 대응

알림 케이스 2개 이상. 종류마다 알림이 가고, 사람이 승인해야 조치가 나갑니다.

5 기록과 찾기

끝난 사건을 기록으로 쌓고, 새 사건에서 비슷한 과거 사건을 찾아 보여 줍니다.

6 확인

가짜 사건으로 전체 흐름을 보여 주고, 감지가 맞는지 채점하는 파일이 있습니다.

7 웹앱

로그인하고, 직접 입력하고, 대시보드와 관리자 페이지에서 확인합니다.

8 흐름 화면

돌아가는 구조를 상자와 화살표로 보여 줍니다. 실행하면 상자가 켜지고, 실패한 곳과 이유가 보입니다.

+ 알파

우리 사용자에게 도움이 되는 기능 하나. 예: 메신저 알림, 외부 캘린더 반영.

1무엇을 만드나요

두 이름은 제품이 아니라 우리 서비스가 하는 두 가지 일입니다. 한 앱 안에서 이어 붙입니다.

마켓워치인시던트봇
한 문장바깥 자료를 계속 살펴보고 중요한 변화를 찾는다찾은 변화를 알리고, 승인받아 처리하고, 기록한다
사용자의 질문무엇이 바뀌었나요?이제 무엇을 해야 하나요?
하는 일정기 수집, 이전 값과 비교, 중요한 변경 판단사건 등록, 알림과 대응안, 승인 또는 거절, 처리와 기록
남는 것이전 값, 현재 값, 발견 시각, 출처승인 상태, 실제 조치와 결과, 처리한 사람과 시각

둘 사이에는 변경 기록 한 건이 넘어갑니다. 무엇이 언제 어디서 어떻게 바뀌었는지가 들어 있으면 됩니다. 칸 이름은 팀이 정합니다. 여기서 사건은 사고가 아니라 사용자가 확인하고 처리해야 할 변화 한 건입니다.

예시: 관심 채용 공고의 마감이 앞당겨졌다

인물과 날짜는 모두 가상입니다. 다른 주제를 고르면 공고와 마감일 자리에 우리 자료를 넣습니다.

  • 변화가 없으면 수집 기록만 남기고 사건은 만들지 않습니다.
  • 같은 변경을 다시 읽어도 사건이나 조치가 두 번 생기지 않습니다.
  • 읽기에 실패하면 수집 오류로 표시합니다. "변화 없음"이나 "공고 삭제"로 단정하지 않습니다.
  • 모든 변경이 사건은 아닙니다. 사용자가 확인해야 할 변화만 사건으로 보고, 기준은 팀이 정합니다.
  • 비교, 저장, 권한 검사는 코드로 만듭니다. 모든 단계에 AI가 필요하지는 않습니다.
앱 여덟 개를 만드는 것이 아닙니다. 위 흐름이 한 서비스 안에서 끊기지 않고 이어지면 됩니다. 처음에는 자료 한 곳, 사건 한 종류, 조치 한 가지로 끝까지 연결하고, 그다음에 알파를 더합니다.

2꼭 만들 화면과 데이터

바깥에서 가져온 자료뿐 아니라 사람이 직접 입력한 데이터도 DB에 저장해서 씁니다. 대시보드와 관리자 페이지도 꼭 만듭니다. 팀의 알파를 대신하지 않는 공통 필수입니다.

만들 것채용 공고 예시끝났다고 볼 기준
직접 입력 화면과 DB 저장사용자가 관심 공고, 목표일, 중요도, 메모를 등록하고 고칩니다작성자와 시각이 저장되고, 새로고침이나 다시 로그인해도 남습니다. 잘못된 입력은 막습니다.
외부 자료와 입력 연결직접 등록한 공고와 수집한 공고를 식별번호나 주소로 이어 줍니다그 공고의 마감 변경이 그 사용자의 목록, 사건, 대응안에 나타납니다. 두 데이터를 따로 보여 주기만 하면 안 됩니다.
사용자 대시보드내 관심 공고 수, 변경 수, 승인 대기와 완료 수, 최근 변경실제 DB 값으로 보여 주고 기간과 상태로 거를 수 있습니다. 숫자를 누르면 목록으로 이동합니다. 데이터 없음과 조회 실패를 구분합니다.
관리자 페이지회원별 입력, 수집 자료, 사건과 처리 현황, 수집 실패 확인일반 사용자는 주소나 API로 직접 요청해도 관리자 데이터를 볼 수 없습니다. 관리자가 고치면 담당자, 시각, 사유가 남습니다.
  • 사용자 화면에서는 내 데이터만 보고 고칩니다. 권한 검사는 화면뿐 아니라 서버와 DB에서도 합니다.
  • 관리자도 사람 승인 단계를 건너뛰고 처리할 수 없습니다.
  • DB 설계에는 사용자, 직접 입력, 수집 자료, 사건, 승인과 처리 기록이 어떻게 이어지는지, 누가 읽고 고칠 수 있는지를 적습니다.

흐름 화면: 돌아가는 구조를 눈으로 보여 줍니다

수업에서 만든 노드 캔버스처럼, 우리 서비스가 어떤 단계를 거쳐 도는지 한 화면에 상자(노드)와 화살표로 보여 줍니다. 이 화면이 이번 프로젝트의 핵심 시연입니다. 설명 그림이 아니라 실제로 도는 모습이어야 합니다.

흐름 화면은 이런 모습입니다 (그림 예시)

수업의 노드 캔버스와 같은 화면입니다. 왼쪽 시작 노드(예약, 지금 실행 버튼, 시뮬레이터) 중 누른 것에서 출발해 어떤 API가 불렸는지, 어디서 갈라졌는지, 어디서 사람을 기다리는지가 한 장에 보입니다. 지금 그림은 "지금 실행 버튼"을 눌러 승인 대기에서 멈춘 모습입니다.

보여 줄 것끝났다고 볼 기준
시작(트리거) 노드예약, "지금 실행" 버튼, 시뮬레이터(또는 웹훅)가 각각 시작 노드로 보입니다. 버튼을 누르면 그 노드에서 출발한 길만 굵게 켜지고, 실행 목록에도 "무엇으로 시작했는지"가 남습니다.
API 호출 노드공공 API, Firecrawl, Claude API, 메일 같은 바깥 서비스를 부르는 노드에 작은 표시가 붙습니다. 노드를 열면 호출 주소(키는 가림), 응답 코드, 걸린 시간, 받은 건수가 보입니다.
흐름 그림가져오기, 같은 모양으로 바꾸기, 비교, 사건인가(분기), 요약, 알림, 사람 승인, 조치와 기록처럼 우리 코드의 실제 단계가 노드와 화살표로 보입니다. 분기는 "예 3건 / 아니오 9건"처럼 갈래마다 건수가 보입니다. 단계를 더하거나 빼면 그림도 바뀝니다.
실행하면 상자가 켜집니다상자 색이 대기, 실행 중, 성공, 실패, 승인 대기로 바뀌고 화살표 위에 넘어간 건수가 보입니다. 예약 실행, "지금 실행" 버튼, 시뮬레이터 입력이 모두 같은 화면에 나타납니다.
상자를 누르면설정, 들어온 데이터, 나간 데이터, 호출 내용(주소, 응답 코드, 걸린 시간), 오류가 보입니다. 비밀값과 개인정보는 가립니다.
실행 목록언제, 어떻게 시작했는지, 성공인지 실패인지, 걸린 시간과 처리한 건수. 새로고침해도 남습니다.
실패어느 상자에서 왜 멈췄는지 빨간 상자와 오류 기록으로 보입니다. 일부러 실패시켜 보여 줍니다.
사람 승인승인 대기에서 멈춰 보이고, 승인하면 이어서 조치와 기록으로 갑니다. 승인 전에는 조치 상자가 켜지지 않습니다.
  • 화면은 그림이 아니라 실행 기록에서 그려집니다. 미리 그려 둔 가짜 불빛은 안 됩니다. 단계가 끝날 때마다 실행(runs)과 단계별 기록(run_steps: 상자 이름, 상태, 들어온 것과 나간 것의 요약, 부른 API 주소와 응답 코드(비밀 제외), 걸린 시간, 오류 메시지, 시각)과 runs에 "무엇으로 시작했는지"을 DB에 저장하고, 화면이 그것을 읽어 그립니다.
  • 노드와 연결은 파일 하나(예: flow/flow.json)에 둡니다. 노드마다 종류(시작, API 호출, 변환, 분기, 사람 승인, DB 저장)와 이름, 연결 조건을 적습니다. 시작 노드를 하나 더 달면 화면에도 시작 노드가 하나 더 보여야 합니다.
  • 만드는 방법은 팀이 고릅니다. 수업의 노드 캔버스 뼈대를 가져와 우리 서비스에 연결해도 되고, 그래프 그리기 라이브러리를 써도 되고, SVG로 직접 그려도 됩니다. 단 내 컴퓨터에서만 열리는 화면이 아니라 배포한 서비스 안(관리자 페이지의 한 탭)에서 보여야 합니다. 일반 사용자는 자기 실행만 봅니다.
  • docs/flow.md에 상자 목록, 상자마다 들어오고 나가는 데이터, 실패했을 때 어떻게 되는지를 적고 화면 캡처를 붙입니다.

방법이럴 때 맞습니다직접 해 볼 것조심할 것

자동으로 도는 일이렇게 확인합니다

  • 발표에서는 몇 시간을 기다릴 수 없습니다. 정기 실행을 지금 한 번 실행하는 버튼이나 명령을 만들어 두고 실행 기록을 보여 줍니다.
  • 일정 수정이나 메시지 발송처럼 실제로 무언가를 바꾸는 일은 사람이 승인한 뒤에만 실행합니다.

"왜 이 사용자의 이 문제를 풀기로 했나"를 근거로 설명합니다

이 프로젝트에서 가장 크게 보는 부분입니다. 기능이 많아도 인터뷰, 자료, 관찰과 이어지지 않으면 문제를 풀었다고 설명하기 어렵습니다. 발표에서도 문제를 고르고 좁힌 과정을 먼저 보여 줍니다. 점수는 평가표에서 따로 안내합니다.

  1. 최근의 실제 장면 듣기. "마지막으로 놓친 때가 언제였나요? 어떻게 알았고, 그 뒤에 무엇을 했나요?"라고 묻습니다. "이 앱 필요하죠?"는 묻지 않습니다. 남길 것: 날짜, 익명 대상, 질문과 답. 직접 들은 말과 팀의 해석을 나눠 적습니다.
  2. 지금의 해결법 보기. 알림, 엑셀, 캘린더 등 지금 쓰는 방법을 확인하고, 그것으로 충분한 사람도 찾습니다. 남길 것: 현재 하는 순서, 불편한 지점.
  3. 손해와 빈도 확인하기. 얼마나 자주 어떤 손해가 생기는지 묻고 기록으로 확인합니다. 기억에 의존한 숫자는 그렇다고 표시합니다. 남길 것: 실제로 잰 것, 당사자 말, 팀 추정을 나눈 숫자.
  4. 외부 자료와 맞춰 보기. 관련 공고와 변경 이력을 직접 열어 보고 샘플을 구합니다. 자료가 있다고 해서 사용자가 원한다는 증거는 아닙니다.
  5. 반대 근거로 범위 좁히기. "기존 알림이면 충분하다", "마감 변경은 드물다" 같은 답도 기록합니다. 접은 후보와 이유, 아직 확인하지 못한 가정을 적습니다.
  6. 사건, 조치, 확인 방법 잇기. 어떤 변화를 찾아야 손해가 줄고, 승인한 뒤 무엇을 바꿀지 정합니다. 근거 → 요구사항 → 사건 기준 → 조치 → 확인 방법이 이어지게 씁니다.

AI 인터뷰는 사용자에 대한 가설이고, 가짜 데이터는 기능을 검사하는 재료입니다. 둘 다 실제 수요의 증거를 대신하지 못합니다. 실제 사람을 못 만났다면 공개 자료로 확인한 사실과 아직 확인하지 못한 가설을 나눠서 냅니다. AI가 만든 인터뷰, 통계, 성과를 실제 조사 결과처럼 쓰지 않습니다.

인터뷰는 사람 먼저, 어려우면 AI로

  • 가능하면 실제 사람 2명 이상. 가족, 친구, 아는 사장님, 같은 반 사람도 좋습니다. 이름과 연락처는 적지 않고, 기록해도 되는지 먼저 허락을 받습니다.
  • 사람이 어려우면 프로젝트 2의 AI 고객 인터뷰 방식 그대로 합니다. 질문지는 팀이 함께 만들고, 팀원이 페르소나를 나눠 맡아 묻습니다. 이번에는 같은 집단 다섯 명이 아니라 서로 다른 사용자 세 명 이상입니다.
  • 해결책을 묻지 않고 지난번에 실제로 겪은 일을 듣습니다.
  • 사람 인터뷰와 AI 인터뷰는 기록에서 구분합니다. 사람 한 명에게라도 확인하면 좋습니다.

어떤 문제를 고르면 좋을까

우리가 만날 수 있는 사용자가 있고, 바깥 변화 한 가지를 놓쳐 손해를 보며, 발견한 뒤에 할 행동이 있는 문제가 좋습니다. 산업 전체보다 한 사람의 반복 업무에서 시작합니다. 아래는 가상 예시입니다. 그대로 골라도 되고 우리 경험에 맞게 바꿔도 됩니다. 수집이 가능한지 확인한 목록은 아니므로, 주제를 정하기 전에 공개 자료 한 건을 직접 읽어서 저장해 봅니다.

사용자와 문제지켜볼 변화 → 사건사람이 확인한 뒤 할 조치
취준생이 저장한 공고의 마감 변경을 놓친다관심 공고의 마감일이 앞당겨짐근거를 보고 지원 일정 수정안을 승인하고 저장
소상공인이 지원사업 신청 조건 변경을 늦게 알아 준비를 다시 한다제출 서류나 마감이 바뀜변경 전후를 보고 준비 체크리스트 수정안을 승인하고 저장
행사 담당자가 날씨 변화에 대응이 늦다행사 지역 예보가 정한 기준을 넘음예보 근거를 보고 실내 전환 준비 작업을 승인하고 등록
구매 담당자가 품목 가격 상승을 늦게 알아 견적을 다시 만든다같은 규격과 단위의 가격이 정한 폭 이상 오름단위와 가격을 확인하고 견적 재검토 작업을 승인하고 등록
교육 담당자가 일정이나 준비물 변경을 놓쳐 잘못 안내한다교육 공지의 날짜나 준비물 문구가 바뀜원문과 대조하고 안내문 수정안을 승인하고 저장
제품 담당자가 리콜 공지를 뒤늦게 발견한다공지의 모델 번호가 가상 취급 제품 목록과 일치모델 일치를 확인하고 점검 작업을 승인하고 등록
승인이 필요한 이유가 없는 주제에 승인 버튼만 붙이지 않습니다. 처음 조치는 앱 안에서 수정안이나 작업을 확정하고 저장하는 정도로 시작해도 됩니다. 실제 메일 발송이나 외부 일정 변경을 더한다면 승인 대상과 실행 결과도 보여 줍니다.

팀원끼리 먼저 이야기해 볼 질문

주제를 정하기 전에 팀이 함께 답해 봅니다. 한 사람이 답을 기록하고, 모르는 것은 "아직 모름"이라고 적습니다. 그 기록이 docs/문제정의.md의 근거가 됩니다. 20분 정도면 충분합니다.

1. 누구의 문제인가

  1. 우리 각자 아는 사람 중에 이런 일로 불평한 사람이 있나요?
  2. 그 사람은 지금 이 문제를 어떻게 버티고 있나요? 엑셀, 메모, 알림 중 무엇을 쓰나요?
  3. 그 사람을 이번 주 안에 만나서 물어볼 수 있나요?

2. 놓치면 무엇을 잃나

  1. 놓쳤을 때 잃는 것은 돈, 시간, 기회 중 어느 쪽인가요?
  2. 지난 한 달에 실제로 몇 번 놓쳤나요? 숫자로 말할 수 있나요?
  3. 늦게 알았을 때와 일찍 알았을 때 결과가 어떻게 달라지나요?

3. 무엇을 어디서 지켜보나

  1. 바뀌는 것이 어디에 공개돼 있나요? 공개 API, 게시판, 가격 페이지 중 어디인가요?
  2. 오늘 샘플 한 건을 직접 저장해 볼 수 있나요? 못 한다면 왜 못 하나요?
  3. 그곳은 얼마나 자주 바뀌나요? 우리가 얼마 간격으로 확인해야 하나요?
  4. 그 사이트의 이용 약관과 robots 안내를 읽어 봤나요?

4. 무엇을 사건으로 보나

  1. '바뀌었다'를 숫자나 문구로 어떻게 적을까요? 몇 퍼센트, 며칠, 어떤 단어인가요?
  2. 사건이 너무 자주 나오면 사용자가 알림을 꺼 버릴 텐데 기준을 어디에 둘까요?
  3. 사건이 아닌 것(변화 없음, 사소한 변화)을 가짜 데이터로 어떻게 보여 줄까요?

5. 사람이 무엇을 승인하나

  1. 알림을 받은 사람이 실제로 할 행동은 무엇인가요?
  2. AI가 혼자 해도 되는 일과 사람이 꼭 눌러야 하는 일의 경계는 어디인가요?
  3. 승인한 결과를 어디에 저장하고 어떻게 보여 줄까요?

6. 우리 팀이 해낼 수 있나

  1. 정해진 기간 안에 이 한 흐름을 끝까지 만들 수 있나요?
  2. 가장 먼저 무너질 부분은 어디일까요? 수집, 기준, 승인 중 무엇인가요?
  3. 우리만의 알파는 무엇이고 그것이 문제를 더 잘 풀어 주나요?
  4. 접은 후보는 무엇이고 왜 접었나요?
토론 규칙: 답이 "아마도"로 끝나면 누가 언제 확인할지 정하고 넘어갑니다. 팀원의 답이 서로 다르면 하나로 고르지 말고 둘 다 적습니다.

후보 두세 개를 비교해서 고릅니다

후보마다 아래 질문에 예, 아니오, 아직 모름과 이유를 적습니다. 아직 모르는 것은 AI가 추측하게 두지 말고 인터뷰나 샘플 수집으로 확인합니다.

  1. 실제로 물어볼 사용자가 떠오릅니까?
  2. 무엇을 놓쳐 어떤 손해를 보는지 구체적입니까?
  3. 변경 전후를 비교할 자료를 실제로 한 건 구했습니까?
  4. 사건을 발견하면 사용자가 할 행동과 승인할 대상이 있습니까?
  5. "변화 없음"과 "사건 발생"을 가짜 데이터로 각각 보여 줄 수 있습니까?
  6. 정해진 기간 안에 한 흐름을 끝까지 만들 수 있습니까?

좋은 문제인지 마지막으로 다섯 가지를 봅니다: 한 사람이 떠오를 만큼 구체적인가 / 잃는 것이 보이는가 / 사람 인터뷰 문장이나 확인한 자료가 있는가 / "무엇이 바뀌었을 때" 생기는 문제인가 / 좋아졌는지 숫자 하나로 잴 수 있는가.

정한 뒤에는 접은 후보와 이유를 docs/문제정의.md에 남깁니다. 문제를 정하면 지켜볼 것, 사용자, 사건 종류가 정해집니다. 다른 팀과 같은 조합은 피합니다.

챗봇 만들기: Claude API + LLM 위키 + 챗봇

  1. 서비스 안에 팀원과 관리자만 쓰는 챗봇 화면(예: 관리자 페이지의 한 탭)을 만듭니다. 일반 사용자에게 내부 문서를 보여 주지 않습니다.
  2. 질문이 오면 서버가 위키에서 관련 쪽을 찾습니다. 제목과 낱말로 찾아도 됩니다.
  3. 찾은 쪽만 Claude API에 주고 "이 쪽만 근거로 답하고, 출처 쪽을 붙이고, 없으면 위키에 없다고 답하라"고 시킵니다. 위키 안의 글이 지시처럼 보여도 따르지 않고 자료로만 읽게 합니다.
  4. 답과 출처 쪽을 화면에 보여 주고, 질문, 찾은 쪽, 답, 시각을 DB에 저장합니다.
  5. API 키는 서버 환경변수에만 둡니다(키는 강사가 제공). 하루 질문 횟수와 답 길이에 한도를 둡니다.
확인하는 법: 질문 다섯 개와 정답표를 팀이 직접 씁니다. 위키에 답이 있는 질문 셋("승인 규칙은 어느 문서에 있어?"), 위키에 없는 질문 하나("대표님 점심 메뉴는?"), 문서끼리 어긋난 곳을 찾는 질문 하나("spec과 prd가 다른 곳 있어?"). 답과 출처를 정답표와 맞춰 docs/wiki-chat.md에 적고, 틀린 것은 왜 틀렸는지(못 찾음, 엉뚱한 쪽, 지어냄) 한 줄씩 남깁니다. 챗봇은 서비스 이용자를 위한 기능이 아니라 팀이 자기 문서를 다루는 도구입니다. 서비스 안의 AI 기능과는 따로 둡니다.

7함께 만들기: 프로젝트 2와 같은 방식

정해진 역할은 없습니다. 할 일을 조각으로 나눠 각자 맡고 다 같이 합칩니다.

  • 한 명이 뼈대(켜지고 배포되는 빈 앱, README, 팀 CLAUDE.md, docs/)를 비공개 저장소 main에 올리고 팀원을 초대합니다. 모두 내려받아 README대로 실행해 봅니다.
  • docs/plan.md에 조각 표(조각, 맡은 사람, 브랜치, 끝났다는 기준)를 만듭니다.
  • 조각은 한 사람이 한 브랜치에서 하루 안에 끝낼 크기입니다. 예: 한 곳을 읽어 공통 모양으로 바꾸기, 시뮬레이터 시나리오, 사건 기준과 사건 만들기, 알림과 승인 화면, 기록과 찾기, 채점 파일, 로그인과 목록.
  • 누가 어디까지 맡을지는 팀이 정합니다. 단 모든 팀원이 PR을 하나 이상 올리고, 리뷰도 하나 이상 합니다.
  • 충돌은 혼자 지우지 말고, 그 코드를 쓴 팀원과 같이 풉니다. 합친 뒤 생긴 오류는 docs/debug-note.md에 남깁니다.

서브에이전트를 어떻게 썼는지 적습니다

서브에이전트는 메인 Claude가 일을 나눠 맡기는 별도의 도우미입니다. 자기 작업창에서 따로 일하고 결과만 돌려줍니다. 팀이 쓴 서브에이전트를 docs/agents.md에 하나씩 적습니다.

칸적을 것
이름과 역할예: spec-checker, 문서가 서로 맞는지 보는 검토자
맡긴 일어떤 입력을 주고 무엇을 하라고 했는지
받은 결과어떤 모양으로 무엇이 돌아왔는지

근거해당 PR, QA 기록, 실행 결과 링크
  • 직접 만든 서브에이전트는 .claude/agents/의 파일을 그대로 두고, 기본으로 있는 것을 쓰면 이름과 부른 방법을 적습니다.
  • 만드는 도우미와 검토하는 도우미를 나누면 좋습니다. 같은 도우미가 만들고 자기 결과를 검토하면 놓치기 쉽습니다.
  • 서로 다른 파일을 맡는 일은 동시에 시키고, 같은 파일을 고치는 일은 나눠서 맡기지 않습니다.
  • 돌아온 결과를 그대로 합치지 않습니다. 사람이 읽고 확인한 흔적(PR 리뷰, QA 기록)을 남깁니다.
  • 서브에이전트를 쓰지 않은 큰 일이 있으면 이유를 한 줄 적습니다. 쓴 개수가 많다고 좋은 것은 아닙니다.

8기록: GitHub와 vibelog

두 곳에 남깁니다. GitHub는 코드의 기록, vibelog는 여정의 기록입니다.

GitHub

이슈, PR, 리뷰가 팀원별 기여의 근거입니다. 기여는 커밋 개수가 아니라 한 일의 무게로 봅니다. 인터뷰에 참여한 것, 시나리오를 쓴 것, 막힌 팀원을 도운 것처럼 GitHub에 안 남는 일은 발표의 기여 표에 적습니다.

vibelog (vibelog.kr)

각자 프로젝트 기간 내내 기록하는 것이 의무입니다. 하루가 끝날 때 날짜, 제목, 한 줄 메모, 화면 하나를 남기고, 막힌 일과 푼 방법, 정한 일과 그 이유, 인터뷰한 날의 내용(신원은 쓰지 않음)도 적습니다. Claude Code를 연결해 두면 작업 요약이 자동으로 들어오고, 연결 방법은 수업에서 같이 합니다. 자동으로 들어온 기록도 내가 읽고 내 판단을 덧붙입니다.

비밀키, 비밀번호, 개인 정보, 인터뷰 대상의 신원은 어디에도 올리지 않습니다.

10개인 과제: 포트폴리오와 이력서

팀 프로젝트와 나란히 각자 만듭니다. 팀 결과물이 "우리가 만든 서비스"라면, 이것은 "나는 이 여정에서 무엇을 어떻게 해냈는가"입니다. 바이브코딩 기초부터 프로젝트 3까지 전체 여정을 어떻게 담았는지를 봅니다.

  • 내는 것: 개인 저장소에 포트폴리오(HTML 한 페이지)와 이력서(1~2장)를 둡니다. 재료는 vibelog 기록입니다. 개인 정보는 팀 저장소에 넣지 않습니다.
  • 담는 법: 도구 이름을 나열하지 않고 내가 달라진 과정을 씁니다. 모든 주장에 증거(PR, 커밋, 인터뷰 문장, 시연 화면, 채점 결과)를 붙입니다. 내가 한 일, Claude가 한 일, 팀이 한 일을 나눠 쓰고, 팀의 일을 혼자 한 것처럼 쓰지 않습니다.
  • 이력서 문장: 문제, 내가 한 일, 결과 순서로 씁니다. 숫자는 실제로 잰 것만 씁니다.

하는 순서의 예: vibelog 기록과 증거 링크를 모읍니다 → Claude에게 초안을 받습니다 → 문장마다 증거와 맞춰 보고 부풀린 곳을 고칩니다 → 포트폴리오에서 뽑아 이력서를 줄입니다 → 팀원 한 명에게 읽혀 여정이 이해되는지 확인합니다.

11발표: HTML 슬라이드를 Vercel에 올립니다

slides/index.html 한 파일로 만들고 장은 팀이 나눕니다. Vercel에 배포해서 주소 하나로 발표합니다. 서비스 배포 주소와 별개로 슬라이드 주소가 하나 더 있습니다. 발표 전날 다른 기기에서 열어 보고, 인터넷이 끊길 때를 대비해 파일도 하나 챙깁니다.

  1. 문제 (가장 크게). 어떤 인터뷰, 자료, 관찰로 문제를 골랐고 무엇을 접거나 바꿨는지, 근거의 한계는 무엇인지. 누가 언제 무엇을 놓쳐 얼마나 잃는지. 들은 말 그대로(사람인지 AI인지 표시). 지금 쓰는 방법과 숫자 하나.
  2. 지켜본 곳과 데이터. 어디를 얼마 간격으로 어떻게 읽었는지, 어떻게 같은 모양으로 맞췄는지, 막혔을 때 어떻게 했는지.
  3. 직접 입력과 운영 화면. 입력한 데이터가 DB에 저장되고 외부 자료와 이어지는 모습, 대시보드, 관리자 페이지와 권한 구분.
  4. 사건과 대응. 사건 기준, 알림, 사람 승인, 조치.
  5. 시연. 시뮬레이터로 가짜 사건을 쏘면 흐름 화면의 상자가 차례로 켜지며 사건, 알림, 승인, 기록이 쌓이는 장면. 일부러 실패시켜 빨간 상자와 오류 기록을 보여 주는 장면. 과거 사건을 찾아 근거로 보여 주는 장면.
  6. 확인. 감지가 얼마나 맞는지 채점 결과, 합친 뒤 잡은 오류.
  7. 커넥터 활용. 서로 다른 서비스 2개 이상을 어디에 썼고 무엇이 남았는지.
  8. 문서 위키와 챗봇. 문서가 어떻게 연결됐는지 연결 지도로 보이고, 챗봇에 물어 출처와 함께 답을 받는 장면, 틀린 답 한 가지와 고친 방법.
  9. 서브에이전트 활용. 어떤 서브에이전트에게 어떤 일을 맡겼고, 결과를 어떻게 확인해 반영했는지, 잘 안 된 점 한 가지.
  10. 하네스 활용. 규칙과 스킬을 고른 이유, 적용한 작업, 실제 결과와 검증, 그 뒤의 개선.
  11. 팀원별 기여. 맡은 조각, PR과 리뷰 번호, 함께 잡은 오류.
  12. 다음에 해 볼 것. 사람 인터뷰로 확인할 것, 다음 개선 하나와 이유.
