# 단계별 산출물 점검 (stage-check)

안내서(`프로젝트3-안내서.html`)는 110KB라 매번 읽기 무겁다. 그래서 단계별 요건을 `references/requirements.md`에 뽑아 두었다. 이 스킬은 그 요건을 저장소의 실제 파일과 맞춰 보고 **보고만 한다.** 고칠지는 사람이 정한다(팀 규칙: 점검은 표로만 보고).

점검 방식은 두 가지다.
- **단계 점검** (기본): 단계별 요건 + 상시 기록 + 위험 신호
- **작업 점검**: "이 PR 점검해줘", "PR #n 확인", "올리기 전에 확인"이면 `requirements.md`의 "작업(PR)별 점검" 표로 그 PR 하나만 본다. 안내서는 intent, PR 설명의 요구 출처, 리뷰, 기록을 작업마다 남기라고 한다. 단계 점검만으로는 작업 하나가 빠뜨린 것이 합계에 묻힌다.

## 순서

0. **최신 상태 맞추기:** `git fetch origin`을 먼저 하고, main은 `origin/main`으로 본다(`git show origin/main:<경로>`, `git ls-tree -r --name-only origin/main`). 팀원이 합친 파일이 내 브랜치에는 없을 수 있다. 보고서 첫 줄에 요건 파일 버전(`git log -1 --format=%h -- .claude/skills/stage-check`)을 적어, 다른 날 점검과 비교할 수 있게 한다.

1. **기준 읽기**
   - `references/requirements.md` (단계별 요건)
   - `docs/adr/` 전체: 안내서와 다르게 가기로 한 결정. ADR로 바꾼 요건은 실패가 아니라 ➖(해당 없음)이고 ADR 번호를 근거로 단다. 단 **ADR 0001**("안내서는 참고 기준")은 범위가 넓어 무엇이든 빼는 핑계가 될 수 있으므로, ➖의 근거로 쓰지 않는다. 그 요건을 콕 집어 바꾼 ADR(0002 이후)만 인정한다.
   - 요건마다 붙은 출처(`[안내서 n장]` / `[팀 규칙]`)를 보고서 "요건" 칸에 그대로 적는다. 팀 규칙 미달과 안내서 요건 미달은 무게가 다르다.
   - `docs/제출물-체크리스트.md`: 팀이 직접 적은 상태. 참고만 하고, **판정은 실제 파일로** 한다. 체크리스트 항목은 requirements.md와 묶음이 1:1이 아니므로, 상태 표시가 실제와 **분명히** 다를 때만(예: ⬜인데 실제로 결과물이 있음) 어긋남으로 보고한다.

2. **점검할 단계 정하기**
   - 사용자가 단계를 말하면 **사용자가 말한 범위가 우선**이다. 그 단계만 보고, 위험 신호는 짧게(한 줄씩) 덧붙인다. "상시 기록도"라고 하면 그때 넣는다.
   - "전체", "제출 전", "최종"이면 모든 단계를 본다.
   - 말하지 않으면 현재 단계를 추정한다. 파일이 있는지가 아니라 **내용이 채워졌는지**로 본다: 항목 대부분이 ✅인 마지막 단계의 다음 단계가 현재 단계다. 파일은 있어도 🟡가 많으면 그 단계가 아직 현재 단계다. 추정 근거를 한 줄로 밝히고, 현재 단계 + 바로 앞 단계 + 상시 기록을 본다.
   - 범위를 말하지 않았을 때는 0단계(준비)도 다 끝나기 전까지 함께 본다. 저장소 공개 여부와 README는 처음부터 제출까지 걸리기 때문이다.

3. **항목마다 실제로 확인하기**
   - 파일이 있는지(Glob), 요건이 말하는 내용이 들어 있는지(Grep/Read로 해당 절·표·숫자 확인).
   - "있다"만으로 통과시키지 않는다. 내용이 일부만 있으면(예: "아직 없음", "TODO", 가설 상태) 🟡이다.
   - 기록 파일(agents, connectors, debug-note, qa 등)이 표 머리만 있고 **기록이 0건이면 ❌**이다. 틀을 만든 것은 진행이 아니어서, 🟡로 세면 요약 숫자가 실제보다 좋아 보인다.
   - GitHub(PR·리뷰)는 이렇게 확인한다. 저장소 주소는 `git remote get-url origin`에서 뽑는다. 먼저 `gh pr list --state all --json number,title,author,body,reviews,state,files`를 쓴다(인증 필요). `body`가 있어야 "PR 설명에 어느 문서의 어느 요구"를, `reviews`가 있어야 "팀원마다 리뷰 1개 이상"(누가 리뷰했는지)을 셀 수 있다. 안 되면 공개 API(`.../pulls?state=all`, 리뷰는 `.../pulls/<n>/reviews`)를 쓴다. 둘 다 안 되면 ❔다. 비공개로 바꾸면 공개 API는 막힌다.
   - QA는 `docs/qa.md` 표 대신 QA 시트를 써도 된다(안내서 12장). `qa.md`에 시트 링크와 남은 문제 요약이 있으면 표가 없다고 ❌로 하지 않는다.
   - vibelog처럼 저장소로 볼 수 없는 사람 기록은 ❔로 두고, `requirements.md`의 "남길 것" 목록을 그대로 붙여 사람에게 확인을 요청한다.
   - 1단계의 팀 토론 기록과 후보 비교는 `docs/` 전체에서 찾는다(`grep -rl "후보 비교\|팀 토론\|아직 모름" docs/`). 찾은 파일을 근거로 적는다.
   - 판정은 **로컬 작업 폴더 + origin/main**을 기준으로 한다. 합치지 않은 PR에만 있는 산출물은 판정에 넣지 않고, "빠진 것" 칸에 "PR #n에 있음(미합침)"으로 적는다.
   - 앱·배포·DB처럼 파일로 확인할 수 없는 것은 연결된 커넥터나 배포 주소로 확인하고, 못 했으면 "확인하지 못함"으로 적는다. 추측으로 ✅를 주지 않는다.
   - 근거는 `파일:줄` 또는 명령 결과로 단다.

4. **늘 함께 보는 위험 신호** (어느 단계든)
   - AI 인터뷰·가짜 데이터가 실제 근거처럼 쓰였는지 (`interviews/`의 사람/AI 표시, 근거 표의 칸 구분)
   - 비밀값이 저장소에 있는지: `.env`가 추적되는지(`git ls-files`), 키처럼 보이는 문자열(`sk-`, `ghp_`, `service_role`, `eyJ` 로 시작하는 긴 토큰). 검색 대상은 `git ls-files -co --exclude-standard`(올라갈 파일)이고, `.claude/skills/`는 뺀다(이 스킬의 설명 글이 걸리기 때문).
   - 인터뷰 대상의 이름·연락처가 적혔는지. 열린 PR에 인터뷰 파일이 있으면 그 파일도 본다(합치면 바로 저장소에 남기 때문). 발표 자료(`slides/`)와 제출용 문서의 개인 연락처·주소도 본다.
   - 커넥터로 외부 일정·알림·자료를 바꾼 기록이 있으면 테스트 자료였는지.
   - 팀 저장소 공개 여부 (안내서는 비공개 요구, 단 ADR 0004로 제출 직전까지 공개 허용 → 9단계 전까지는 ➖, 9단계에서는 비공개 여부를 꼭 확인). `curl -s -o /dev/null -w "%{http_code}" https://api.github.com/repos/<owner>/<repo>` 가 200이면 공개다.

5. **보고** (아래 양식 그대로)

## 판정 기호

| 기호 | 뜻 |
|---|---|
| ✅ | 요건을 채움 (근거 있음) |
| 🟡 | 일부만 채움, 틀만 있음, 가설 상태 |
| ❌ | 없음 |
| ➖ | ADR로 하지 않기로 함 (ADR 번호 필수) |
| ❔ | 확인하지 못함 (이유 필수) |
| ⚪ | 조건 없음: 이번 범위에 그 일이 없었음 (예: 테이블을 안 바꿨으니 erd 바뀐 기록 불필요). 요약 숫자에 세지 않는다 |

## 보고 양식

```
# 산출물 점검 — YYYY-MM-DD · <점검 범위>
현재 단계 추정: <단계> (근거: …)  ·  최종 발표까지 D-<n>

요건 파일 버전: <커밋>
**요약:** ✅ a · 🟡 b · ❌ c · ➖ d · ❔ e (⚪는 세지 않음)

## <단계 이름>
| 항목 | 안내서 요건 | 판정 | 근거 | 빠진 것 |
|---|---|---|---|---|

## 위험 신호
| 신호 | 결과 | 근거 |

## (작업 점검일 때) PR #n
| 항목 | 출처 | 판정 | 근거 | 빠진 것 |

## 체크리스트와 실제가 다른 곳
(없으면 "없음")

## 다음에 할 일 (우선순위 3개)
1. … (왜 먼저인지 한 줄, 누가: 사람/Claude)
```

"다음에 할 일"은 발표 날짜(`requirements.md` 맨 위)까지 남은 날을 생각해, **시연과 채점에 직접 걸리는 것**을 먼저 둔다. 사람만 할 수 있는 일(인터뷰, 계정·저장소 설정, vibelog)은 "사람"이라고 표시한다.

## 하지 않는 것

- 파일 수정, 체크리스트 상태 갱신, 커밋. 사용자가 따로 요청하면 그때 한다.
- 요건에 없는 "있으면 좋은 것" 제안. 점검은 안내서 요건과 ADR 기준으로만 한다.
