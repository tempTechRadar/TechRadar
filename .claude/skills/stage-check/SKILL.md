# 단계별 산출물 점검 (stage-check)

안내서(`프로젝트3-안내서.html`)는 110KB라 매번 읽기 무겁다. 그래서 단계별 요건을 `references/requirements.md`에 뽑아 두었다. 이 스킬은 그 요건을 저장소의 실제 파일과 맞춰 보고 **보고만 한다.** 고칠지는 사람이 정한다(팀 규칙: 점검은 표로만 보고).

## 순서

1. **기준 읽기**
   - `references/requirements.md` (단계별 요건)
   - `docs/adr/` 전체: 안내서와 다르게 가기로 한 결정. ADR로 바꾼 요건은 실패가 아니라 ➖(해당 없음)이고 ADR 번호를 근거로 단다.
   - `docs/제출물-체크리스트.md`: 팀이 직접 적은 상태. 참고만 하고, **판정은 실제 파일로** 한다. 체크리스트 항목은 requirements.md와 묶음이 1:1이 아니므로, 상태 표시가 실제와 **분명히** 다를 때만(예: ⬜인데 실제로 결과물이 있음) 어긋남으로 보고한다.

2. **점검할 단계 정하기**
   - 사용자가 단계를 말하면 그 단계 + "상시 기록"을 본다.
   - "전체", "제출 전", "최종"이면 모든 단계를 본다.
   - 말하지 않으면 현재 단계를 추정한다. 파일이 있는지가 아니라 **내용이 채워졌는지**로 본다: 항목 대부분이 ✅인 마지막 단계의 다음 단계가 현재 단계다. 파일은 있어도 🟡가 많으면 그 단계가 아직 현재 단계다. 추정 근거를 한 줄로 밝히고, 현재 단계 + 바로 앞 단계 + 상시 기록을 본다.
   - 0단계(준비)는 다 끝나기 전까지 어느 범위에서든 함께 본다. 저장소 공개 여부와 README는 처음부터 제출까지 걸리기 때문이다.

3. **항목마다 실제로 확인하기**
   - 파일이 있는지(Glob), 요건이 말하는 내용이 들어 있는지(Grep/Read로 해당 절·표·숫자 확인).
   - "있다"만으로 통과시키지 않는다. 내용이 일부만 있으면(예: "아직 없음", "TODO", 가설 상태) 🟡이다.
   - 기록 파일(agents, connectors, debug-note, qa 등)이 표 머리만 있고 **기록이 0건이면 ❌**이다. 틀을 만든 것은 진행이 아니어서, 🟡로 세면 요약 숫자가 실제보다 좋아 보인다.
   - GitHub(PR·리뷰)는 이렇게 확인한다. 저장소 주소는 `git remote get-url origin`에서 뽑는다. 먼저 `gh pr list --state all --json number,title,author,reviewDecision,files`를 쓰고(인증 필요), 안 되면 공개 API(`curl -s https://api.github.com/repos/<owner>/<repo>/pulls?state=all`)를 쓴다. 둘 다 안 되면 ❔다. 비공개로 바꾸면 공개 API는 막힌다.
   - 판정은 **로컬 작업 폴더 + main**을 기준으로 한다. 합치지 않은 PR에만 있는 산출물은 판정에 넣지 않고, "빠진 것" 칸에 "PR #n에 있음(미합침)"으로 적는다.
   - 앱·배포·DB처럼 파일로 확인할 수 없는 것은 연결된 커넥터나 배포 주소로 확인하고, 못 했으면 "확인하지 못함"으로 적는다. 추측으로 ✅를 주지 않는다.
   - 근거는 `파일:줄` 또는 명령 결과로 단다.

4. **늘 함께 보는 위험 신호** (어느 단계든)
   - AI 인터뷰·가짜 데이터가 실제 근거처럼 쓰였는지 (`interviews/`의 사람/AI 표시, 근거 표의 칸 구분)
   - 비밀값이 저장소에 있는지: `.env`가 추적되는지(`git ls-files`), 키처럼 보이는 문자열(`sk-`, `ghp_`, `service_role`, `eyJ` 로 시작하는 긴 토큰). 검색 대상은 `git ls-files -co --exclude-standard`(올라갈 파일)이고, `.claude/skills/`는 뺀다(이 스킬의 설명 글이 걸리기 때문).
   - 인터뷰 대상의 이름·연락처가 적혔는지. 열린 PR에 인터뷰 파일이 있으면 그 파일도 본다(합치면 바로 저장소에 남기 때문).
   - 팀 저장소 공개 여부 (안내서는 비공개 요구). `curl -s -o /dev/null -w "%{http_code}" https://api.github.com/repos/<owner>/<repo>` 가 200이면 공개다.

5. **보고** (아래 양식 그대로)

## 판정 기호

| 기호 | 뜻 |
|---|---|
| ✅ | 요건을 채움 (근거 있음) |
| 🟡 | 일부만 채움, 틀만 있음, 가설 상태 |
| ❌ | 없음 |
| ➖ | ADR로 하지 않기로 함 (ADR 번호 필수) |
| ❔ | 확인하지 못함 (이유 필수) |

## 보고 양식

```
# 산출물 점검 — YYYY-MM-DD · <점검 범위>
현재 단계 추정: <단계> (근거: …)  ·  최종 발표까지 D-<n>

**요약:** ✅ a · 🟡 b · ❌ c · ➖ d · ❔ e

## <단계 이름>
| 항목 | 안내서 요건 | 판정 | 근거 | 빠진 것 |
|---|---|---|---|---|

## 위험 신호
| 신호 | 결과 | 근거 |

## 체크리스트와 실제가 다른 곳
(없으면 "없음")

## 다음에 할 일 (우선순위 3개)
1. … (왜 먼저인지 한 줄, 누가: 사람/Claude)
```

"다음에 할 일"은 발표 날짜(`requirements.md` 맨 위)까지 남은 날을 생각해, **시연과 채점에 직접 걸리는 것**을 먼저 둔다. 사람만 할 수 있는 일(인터뷰, 계정·저장소 설정, vibelog)은 "사람"이라고 표시한다.

## 하지 않는 것

- 파일 수정, 체크리스트 상태 갱신, 커밋. 사용자가 따로 요청하면 그때 한다.
- 요건에 없는 "있으면 좋은 것" 제안. 점검은 안내서 요건과 ADR 기준으로만 한다.
