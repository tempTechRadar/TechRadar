# 단계별 요건 (프로젝트3 안내서에서 뽑음)

## 읽는 법
- **출처 표시:** `[안내서 n장]`은 안내서 요건, `[팀 규칙]`은 팀 `CLAUDE.md`·ADR에서 온 요건이다. 보고할 때 출처를 함께 적는다. 팀 규칙이 빠진 것은 "안내서 요건 미달"이 아니라 "팀 규칙 미달"이다.
- **단계 번호 0–9는 팀이 정한 진행 순서다.** 안내서는 "순서는 팀이 정한다"고 한다. 순서가 달라도 요건이 채워졌으면 통과다.
- **날짜 [팀 정보]:** 최종 발표 2026-11-23(월). 중간 점검은 주제 컨펌으로 끝남(2026-11-16). 안내서는 "공지에 따름"이라고만 한다.
- **용어:** 안내서의 "사건" = 우리의 **알림**(적용 기회 / 보안 경고), "사람 승인" = **판단**(적용 후보 / 보류), "조치" = **판단 저장**(적용 후보 기록 → 설치 프롬프트 기본 포함 / 보류 사유 기록). 적용 시나리오는 판단 전에도 만들 수 있는 참고 자료(ADR 0010), "직접 입력" = **내 프로젝트 등록**(필요 등록은 가설 C, `docs/GLOSSARY.md`).
- **➖(해당 없음)는 구체적인 ADR로만** 준다(0002 이후). ADR 0001("안내서는 참고 기준")만으로는 어떤 요건도 ➖로 만들지 않는다.

## 1. 문제 정의 [안내서 5장]

| 항목 | 끝 기준 |

## 4–5. 서비스 흐름

### 필수 8가지 중 흐름 부분 [안내서 0–4장]

증거 기준 [안내서 12장]: 실시간 데이터 2개 이상(서로 다른 출처), 알림 케이스 2개 이상(종류마다 기준·알림·승인)이 **실행 기록과 가짜 데이터로 보임**.

| 항목 | 끝 기준 |
|---|---|
| 지켜보기 | 서로 다른 출처 **2개 이상**의 실시간 데이터를 정해진 간격으로 저절로 모아 같은 모양(시각, 대상, 지표, 값, 바뀐 정도, 출처)으로 맞춤. 세 방법 중 **한 가지 이상을 직접 구현**. 코드 `watch/`, 저장 샘플은 **실수집/가상 표시** |
| 사건 | 기준을 적고, 넘으면 사건 생성. **종류 2개 이상**. 모든 변경이 사건은 아님. **변화가 없으면 수집 기록만 남기고 사건은 안 만듦**. 같은 변경을 다시 읽어도 사건·조치가 두 번 안 생김 |
