## 4–5. 서비스 흐름: 필수 8가지 (안내서 0장, 1–4장)

| 항목 | 끝 기준 |
|---|---|
| 지켜보기 | **서로 다른 출처 2개 이상**의 실시간 데이터를 정해진 간격으로 저절로 모아 같은 모양(시각, 대상, 지표, 값, 바뀐 정도, 출처)으로 맞춤. 코드: `watch/` |
| 알림(사건) | 알림 기준을 적고, 기준을 넘으면 알림 생성. **종류 2개 이상**. 같은 변경을 다시 읽어도 두 번 생기지 않음 |
| 대응 | 알림 케이스 2개 이상, 종류마다 알림이 가고 **사람이 판단해야** 조치가 나감. 판단 전에는 아무것도 안 바뀜. 코드: `incident/` |
| 기록과 찾기 | 끝난 판단을 기록으로 쌓고, 새 알림에서 비슷한 과거 판단을 찾아 보여 줌. 코드: `knowledge/` |
| 실패 처리 | 읽기 실패는 "수집 오류"로 기록("변화 없음" 아님). 관리자 페이지에서 수집 오류 확인 |
| 정기 실행 | **배포한 앱에서도** 정해진 간격으로 돎(Vercel cron, Supabase 예약 함수 등). 실행 기록이 간격대로 쌓임. "지금 한 번 실행" 버튼 |
| Claude API | 쓰는 곳에 출처·기록을 함께 보여 줌, 키는 서버 환경변수 |
| 직접 입력 화면 | 사용자가 등록하고 고침. 작성자와 시각 저장, 새로고침·재로그인 후에도 남음, 잘못된 입력 막음 |
| 외부 자료와 입력 연결 | 등록한 프로젝트와 수집한 기술이 식별자로 이어져, 그 사용자의 목록·알림·시나리오에 나타남(따로 보여 주기만 하면 안 됨) |
| 사용자 대시보드 | 실제 DB 값, 기간·상태로 거르기, 숫자 누르면 목록으로, "데이터 없음"과 "조회 실패" 구분 |
| 관리자 페이지 | 회원별 입력, 수집 자료, 알림·판단 현황, 수집 실패. 일반 사용자는 주소·API로 요청해도 못 봄. 관리자가 고치면 담당자·시각·사유 남음. 관리자도 판단 단계를 못 건너뜀 |
| 권한 | 사용자 데이터는 본인만, 관리자 데이터는 관리자만. 화면뿐 아니라 서버와 DB에서도 검사 |
| 커넥터 | 서로 다른 서비스 2개 이상을 실제 일에 씀 (`docs/connectors.md`) |

## 6. 시연 장치 (안내서 2장 흐름 화면, 8번 묶음)

|---|---|

| 흐름 화면 | 배포 서비스 안(관리자 탭). 시작 노드(예약, 지금 실행, 시뮬레이터) 각각 보임. 상자 색(대기·실행 중·성공·실패·판단 대기), 화살표 위 건수, 분기 갈래별 건수, API 노드에 호출 주소(키 가림)·응답 코드·시간·건수 |

| 시뮬레이터 | `sim/`: 가짜 입력, 시연 실행과 초기화 방법. 샘플은 실수집/가상 표시 |
| 채점 | `eval/`: 검사 코드, 정답 샘플, 결과(맞힌 알림, 놓친 알림, 잘못 울린 알림 수). 정상 외에 변화 없음, 수집 실패, 판단 거절, 저장 실패, 중복 입력 경우 |
