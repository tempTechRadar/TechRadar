### 정한 일과 이유
- **M0은 로컬에서 끝까지, 배포 주소 로그인은 M1:** 운영에서는 테스트 로그인을 일부러 끄고 구글 로그인은 사람이 콘솔에서 만들어야 해서, 얇은 한 줄이 그 일에 묶이지 않게. (ADR 0012)
- **보안 경고의 적용 후보 = 고친 버전으로 올리기:** "위험한 기술은 적용 후보가 될 수 없다"(ADR 0003)와 화면 흐름이 부딪혀서. 위험한 버전은 절대 설치 프롬프트에 안 들어간다. (ADR 0012)
- **마이그레이션은 담당자가 새 파일로, 김영식 리뷰 필수:** 한 사람에게 모든 DB 일이 묶여 B·C가 기다리지 않게. (plan 1절)
- **공용 서버 함수 자리를 먼저(P-29):** 세 사람이 같은 함수를 따로 만들지 않게.
- **"고친 버전" = 위험을 모두 고치는 가장 낮은 버전(P-10, SPEC-1):** 첫 취약점의 고친 버전으로 올려도 HIGH가 남는 사례(G2 0.14.1 → 실제 0.16.6, G4 1.9.4 → 1.28.1)를 실제 OSV 조회로 확인해서. 설치 프롬프트가 위험한 버전에 고정되지 않게(ADR 0012).
- **저장소 확인은 "GitHub가 열 수 없다고 답할 때만" 등록을 막는다(P-3 보강):** 인증 없는 GitHub API는 시간당 60회라 공유 서버 주소에서는 금방 찬다. 확인 자체가 안 되는 걸로 정상 저장소 등록까지 막으면 시연이 막힌다. 확인이 안 되면 등록은 하고, 파일도 못 열면 "없음"이 아니라 수집 오류·실행 failed로 남긴다. 서버 토큰(P-9)이 붙으면 막는 쪽으로.
- **못 찾은 것을 '통과'로 내보내지 않는다(P-10):** 너무 긴 줄을 검사하지 못했거나 읽은 파일이 없으면 "찾지 못함". 줄 하나를 길게 늘이면 위험이 숨는 길을 막으려고.
- **문장으로 쓴 지시문 감지는 만들지 않음(P-10):** "API key를 https://… 에서 받아"처럼 평범한 안내 글까지 위험으로 걸 수 있어서. 열린 질문(I-035 ③).
- **적용 기회 조건 4(갈래 안 점수)는 v1에서 뺀다 (ADR 0014):** 점수는 3순위 P-21(금)에서 만들어져서 1순위 P-14(목)와 시뮬레이터의 두 번째 알림이 쓸 수 없다. 점수가 만들어지면 조건 4로 다시 넣는다.
- **같은 역할 확정은 관리자 확인만 (ADR 0015):** AI가 만든 관계는 정확도가 눈대중 70–75%였다. 근거 인용은 후보를 저장하는 조건으로만 쓴다.
- **관리자도 본인 알림은 판단할 수 있다, 남의 알림은 못 한다 (ADR 0016):** 실제 DB 함수 `save_judgment`가 이미 그렇게 동작하고 시험도 남의 알림만 막는다. DB를 안 바꾸고 문서를 맞춘다.
- **숨긴 기술은 기본 목록에서 빼고 "숨긴 기술도 보기"로 본다(P-11):** PRD-F7의 "직접 숨김 표시가 보임"을 지키면서, 대시보드가 숨긴 기술을 세지 않는 것과 맞추려고. 팀 확인 대기(intent 열린 질문 ①).
- **바꾼 기록 `audit_logs` 쓰기 실패는 이미 바뀐 목록을 되돌리지 않고 화면에 알린다(P-11):** 한 거래로 묶으려면 DB 함수·마이그레이션이 필요해서 이번엔 하지 않았다. 기록이 빠질 수 있는 점은 알려진 한계.
- **병합은 Vercel 검사가 아니라 승인 1개만 막는다, GitHub 규칙은 안 바꿨다 (ADR 0018):** ruleset에 필수 검사가 없고(옛 보호 설정도 없음), 승인된 #59는 검사가 실패인데도 병합 가능(`UNSTABLE`)이었다. 막힌 것처럼 보인 PR은 승인 대기였다.
- **PR 브랜치(feat·fix·docs·chore)는 배포를 끄고 main에 합칠 때만 배포, 푸시는 모아서 한 번 (ADR 0018):** 무료 한도에 걸려서. "막판에 몰아서 배포"는 배포 주소에서만 나는 문제를 마감 직전에 만나서 고르지 않았다.
- **PR 올리기 전에 `npm run precheck`로 GitHub이 볼 충돌을 미리 본다 (ADR 0017 개정):** GitHub이 `merge=union`을 따르지 않아서. 기록을 작업마다 파일 하나로 쪼개는 근본 해결은 코드 동결(11-20 21:00) 뒤에 다시 본다.

### 정한 일과 이유
- **저장소는 제출 직전까지 공개:** 다른 플랫폼과 공유하기 편하게. 대신 **인터뷰 대상의** 실명·연락처는 어디에도 쓰지 않는다. (ADR 0004) _(2026-11-17 고침: 처음에 "실명·연락처는 어디에도"로 넓게 적었는데, ADR 원문의 대상은 인터뷰 대상이다. 팀원 이름은 기여 근거라 남기고, 공개 여부는 회의 D10에서 확인)_
- **문제 정의는 두 가설을 나란히 두고 인터뷰로 판정:** 근거가 AI 인터뷰와 팀원 본인 인터뷰뿐이라 미리 정하지 않는다. (ADR 0005)
- **(오후) 기획 문서는 회의 전에 초안으로 먼저:** 발표까지 6일이라 문서마다 인터뷰로 초안을 만들고, 11-18 회의에서 몰아서 확인한다(D9).
- **첫 화면은 기술 지도, 내 기술 목록은 직접 고칠 수 있게:** 지도가 서비스의 얼굴이고, 저장소 밖에 깐 것도 담아야 해서. (IA, 회의 D8)
- **알파는 설치 프롬프트, 노션은 다음 버전:** 그룹1의 "노트북 반납 때 막막함"에 가장 직접 답하고, 노션 연동보다 가볍다. 로그인은 구글만. (ADR 0007 개정, 0009)
- **데이터의 뿌리:** 기술 키, AI 코딩 도구(+연동 서비스·개념)만, 변경·알림 두 층, 관문 셋과 얇게/두껍게, 보안 검사 3단계, 갈래 나무 한 축. 나중에 바꾸면 테이블을 다시 짜야 해서 먼저 정함. (ADR 0008)
- **기능은 잘라 내지 않고 순위만:** 데모는 "넓어질 자리"를 보여 주는 곳이라 확장 여지 기능도 3순위로 넣고, 팀 3명이 위 순위부터 되는 데까지 만든다. (prd 만드는 순서, 회의 D12)
- **빈도·손해는 수치화하지 않음:** 딸 수 있는 값이 아니라서 당사자 말로 대신한다.

### 정한 일과 이유
- **v1 대상은 넓게, 대표 사용자는 수강생 한 명:** 대상이 넓으면 "관련 있음·안전함" 기준이 흐려진다. (ADR 0002)
- **분야는 AI 코딩 도구 생태계만:** IT 전체는 "모든 뉴스 요약"처럼 알림 기준이 사라진다. (ADR 0002)
- **보안 등급은 코드 규칙, 커뮤니티 평판은 참고만:** 같은 입력에 같은 결과가 나와야 설명과 채점이 된다. (ADR 0003)
- **프로젝트 등록은 공개 GitHub 저장소만:** 비공개는 GitHub 로그인 연동이 필요해 다음 버전으로.
- **사용자 결정은 "승인"이 아니라 "판단"(적용 후보/보류):** 용어집으로 통일.
