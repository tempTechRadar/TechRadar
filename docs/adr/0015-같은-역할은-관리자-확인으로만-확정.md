# 0015. "같은 역할"은 관리자 확인으로만 확정한다

- 날짜: 2026-11-18
- 상태: **채택** (2026-11-18, 기본 문서 점검 D-4를 사용자가 추천안으로 정함. 다른 팀원은 PR 리뷰에서 확인)

기본 문서 점검(`docs/문서점검-20261118.md` D-4)에서 "같은 역할" 확정 조건이 문서마다 다른 것이 나왔다. spec 4.4는 관리자가 확인해야 확정되고 문장 인용으로 자동 확정하는 것은 3순위라고 했다. prd F24, 데이터설계 원칙 15번, ADR 0008 9번은 "근거 인용 **또는** 관리자 확인"이라고 했다. 적용 기회 알림은 확정된 관계에서만 생기므로(SPEC-3.2), 조각마다 확정 조건이 달라지면 P-14(적용 기회)와 P-18(분류 확인 화면)이 서로 다른 일을 만든다.

## 정한 것
- **확정은 관리자 확인만 한다.** 확정에는 담당자·시각·사유가 남는다(`tech_relations.confirmed_by`·`confirmed_at`).
- **후보는 기계가 만든다:** 같은 작은 갈래에 있으면 후보이고, Claude가 제안한 관계는 **근거 인용이 원문에 그대로 있을 때만** 후보로 저장한다(데이터설계 2절 C). 인용은 후보를 저장하는 조건이지, 확정이 아니다.
- **처음 짝 목록(20쌍 정도)은 팀이 만들어 시드로 넣는다**(SPEC-4.4, SQ2, erd `made_by = seed`). 적용 기회가 시드에서 나오려면 확정이어야 하므로(plan P-14) 시드는 확정으로 넣는 것으로 읽는다. **확인하지 못함:** 시드의 확정자·확정 시각 칸을 어떻게 채울지(P-14 때 정한다).
- Claude가 인용만으로 자동 확정하는 것은 하지 않는다. 3순위에서 다시 본다.
- 관리자 확인을 거치지 않는 예외는 둘이다: 처음 짝 목록(시드)과 시뮬레이터가 넣는 가짜 관계(가짜 표시, SPEC-3.5).
- 알림·두껍게는 확정된 관계만 쓴다(데이터설계 원칙 15번 그대로).

## 이유
- 이전 프로젝트에서 AI가 만든 관계의 정확도가 눈대중 70–75%였다(ADR 0008 6번). 적용 기회는 "더 나은 것이 나왔다"고 사람에게 알리는 사건이라 틀린 짝이면 곧바로 거짓 알림이 된다.
- 데이터설계 2절 C(85줄)는 이미 "AI가 제안한 관계는 관리자 확인 전에는 '확인 전'"이라고 해서, "인용으로 확정"이라는 문구(원칙 15번, prd F24, ADR 0008 9번)와 같은 문서 안에서도 달랐다.

## 결과
- spec 4.4는 뜻 그대로(이 ADR을 가리키고 후보 저장 조건만 적음). prd F12·F24, 데이터설계 원칙 15번·2절 C, ADR 0008 9번(개정 줄)을 고친다. ia IA-17(분류 확인)에 "같은 역할 후보 확정"을 더한다. 데이터설계·erd 권한 표에는 관리자의 관계 확정이 있는데 화면 표에는 빠져 있었다. GLOSSARY "같은 역할"에 후보 → 확정 규칙을 적는다.
- plan P-14는 확정된 관계만 읽고, P-18의 분류 확인 화면이 확정을 맡는다.
- "인용이 원문에 있을 때만 후보로 저장"은 DB가 검사하지 않는다(`tech_relations.quote`는 비워 둘 수 있고 check도 없다). 서버 코드(P-14·P-18)가 지킨다.

## 고르지 않은 것
- 인용이 있으면 자동 확정: 정확도가 낮고, 틀린 확정이 적용 기회 알림으로 번진다.
- 후보도 알림에 쓰기: 틀린 후보가 곧바로 적용 기회 알림이 되고, "알림·두껍게는 확정된 관계만"이라는 원칙 15번과 어긋난다.
