# 0017. 기록 문서는 합쳐도 충돌하지 않게 하고, 작업 번호는 매기지 않는다

- 날짜: 2026-11-18
- 상태: **채택** (2026-11-18, 사용자가 "intent·worklog가 자꾸 충돌난다, 재발 막고 팀에 적용"을 요청해 정함. 다른 팀원은 PR 리뷰에서 확인)

PR을 합칠 때마다 `docs/intent.md`·`docs/worklog.md`가 충돌했다. 지금까지 병합 커밋 59개를 다시 합쳐 보니(내 컴퓨터에서 시뮬레이션) 8개가 충돌했고, 충돌 20곳은 **전부** "두 브랜치가 같은 자리에 새 줄을 덧붙인" 모양이었다. 파일별로는 intent 8번, worklog 8곳(6개 병합), agents 2, connectors 1, spec 1(바뀐 기록 덧붙임). 해결은 매번 "양쪽 모두 남기기 + 내 번호 다시 매기기"였고, 이 한 가지 작업(PR #44·#50)에서만 번호를 네 번 바꿨다.

원인은 둘이다.
1. **같은 자리에 덧붙임.** intent는 맨 위에 새 항목을, worklog·agents·connectors는 표 끝에 새 행을 넣는다. 동시에 열린 PR은 모두 같은 자리를 건드린다.
2. **순번 ID.** `I-043`·로그 `86`처럼 각자 "다음 번호"를 매기니 두 PR이 같은 번호를 고른다. 사람이 충돌 표시를 보고 다시 매겨 왔다.

## 정한 것
- **`.gitattributes`에 `merge=union`**(git 기본 기능, 설정 없이 쓸 수 있음)을 덧붙이기만 하는 기록 문서 5개에 건다: `intent`·`worklog`·`agents`·`connectors`·`debug-note`. 같은 자리에 둘이 덧붙이면 충돌 표시 없이 양쪽 줄이 모두 남는다. 과거 충돌 병합 9개를 다시 합치면 기록 문서의 충돌이 모두 없어지고 줄이 하나도 빠지지 않았다.
- **작업 ID에서 순번을 없앤다.** 작업 ID = `I-` + 브랜치 이름에서 `feat/`·`fix/`·`docs/`·`chore/`를 뺀 것(예: `fix/P-3-collect-errors` → `I-P-3-collect-errors`). 브랜치 이름은 이미 겹치지 않으니 서로 맞출 일이 없다. worklog 행의 첫 칸에도 같은 작업 ID를 쓴다. 옛 번호(I-001~I-043, 로그 번호)는 그대로 둔다.
- **`lib/records/records.test.ts`**(`npm test`에 포함)가 합친 뒤의 기록을 본다: 충돌 표시가 남았나, intent의 작업 ID나 worklog 표의 첫 칸이 겹치나, 기록 표의 열 수가 맞나, 표 밖에 떨어진 행이 있나, `.gitattributes` 줄이 지워지지 않았나. union은 충돌 표시를 없애는 대신 "같은 번호가 조용히 두 번 생기는 것"을 가릴 수 있어서 이 검사가 함께 필요하다.
- **main은 내 컴퓨터에서 `git merge origin/main`으로 받는다.** GitHub 웹의 "Resolve conflicts"·"Update branch"는 `.gitattributes` 설정을 따르지 않는 것으로 알려져 있다(GitHub 커뮤니티에 지원 요청이 열려 있음).
- 표가 파일 끝에 오게 한다. `agents.md`는 표 뒤에 문단이 있어서 파일 끝에 덧붙인 행이 표 밖으로 떨어져 있었다(PR #50). 문단을 표 앞으로 옮기고 떨어진 행을 표 안으로 넣었다.

## 결과
- `CLAUDE.md` 9·10절, `docs/plan.md` 2절(합치기·충돌·기록), intent·worklog 머리말에 규칙을 적는다.
- 이 설정은 main에 합쳐진 뒤 각자 main을 한 번 받으면 적용된다. 이미 열린 PR(#47·#48·#49·#52)도 main을 합칠 때부터 적용된다.
- **남는 것:** 기획 문서(spec·prd 등)의 "바뀐 기록" 끝에 둘이 덧붙이는 충돌은 그대로 남는다(과거 1/59). 일부러 뺐다: 같은 문단을 둘이 고쳤을 때는 충돌 표시가 있어야 사람이 본다. 이때는 양쪽 줄을 모두 남긴다.
- **확인하지 못한 것:** GitHub 웹 병합 화면이 `merge=union`을 따르는지는 직접 시험하지 않았다(따르지 않는다고 보고 흐름을 짰다). 열린 PR이 이 설정을 받은 뒤의 첫 병합은 아직 겪어 보지 않았다. (→ 개정 2026-11-18, PR #57·#58 뒤: GitHub 화면은 union을 따르지 않는 것으로 재현함)
- 되돌리려면 `.gitattributes`의 줄을 지우면 된다(기록 검사 시험도 함께 고친다).

## 고르지 않은 것
- **기록을 작업마다 파일 하나로 쪼개기**(`docs/intent/I-….md`): 충돌이 아예 없어 가장 확실하지만 `intent.md`·`worklog.md`를 읽는 `stage-check` 요건, `abbs-log`, `CLAUDE.md` 9절, 안내서 제출물 구조를 모두 바꿔야 한다. 코드 동결(11-20 21:00) 전 사흘 동안 하기엔 크다. 충돌이 계속되면 다음에 다시 본다.
- **번호를 서버나 스크립트로 나눠 주기:** 나눠 주는 곳이 하나 더 생기고, 오프라인 작업에서는 쓸 수 없다.
- **기획 문서까지 union:** 같은 문단을 둘이 고친 것이 조용히 두 번 남을 수 있다.

## 개정
- 2026-11-18(PR #55를 합친 뒤): **`.gitattributes`가 없는 브랜치는 처음 main을 받을 때 설정이 적용되지 않는다.** git은 합치는 쪽(내 브랜치)에 있는 설정만 쓰기 때문이다. 열린 PR 4개(#47·#52·#53·#54)와 작업 중이던 브랜치 하나가 모두 첫 병합에서 `docs/worklog.md`(와 agents·debug-note·plan)가 충돌했다. PR #55 때 이 첫 병합을 시험하지 않은 빈틈이다.
- 해결(임시 폴더에서 시험으로 확인): 설정을 먼저 **커밋으로** 받고 합친다. `git fetch origin && git checkout origin/main -- .gitattributes && git commit -m "chore: .gitattributes 받기" && git merge origin/main`. 열린 PR 4개 모두 충돌 없이 병합됐다. 파일만 그냥 놓고 합치면 "untracked 파일을 덮어쓴다"며 병합이 실패한다(rc=2). 새 브랜치는 main에서 따니 이미 설정이 있어 이 절차가 필요 없다.
- 그래도 남는 것: `plan.md`·`spec.md` 같은 기획 문서의 "바뀐 기록" 끝에 둘이 덧붙인 줄이 겹치는 충돌은 설정을 받은 뒤에도 난다(작업 중이던 브랜치에서 바로 겪음). 양쪽 줄을 모두 남긴다. 이 문서들은 같은 문단을 둘이 고친 경우를 숨기지 않으려고 union에서 뺀 것이라 그대로 둔다.
- 2026-11-18(PR #57·#58을 합친 뒤): **GitHub의 PR 화면은 `merge=union`을 따르지 않는다고 봐야 한다.** 열린 PR 4개(#52·#53·#59·#60)가 GitHub에서 모두 `CONFLICTING`인데, 같은 4개를 내 컴퓨터(git 2.55)에서 `git merge origin/main` 하면 모두 충돌이 없다. 복사본에서 기록 문서를 `merge=text`로 덮어 일반 병합을 흉내 내면 #60·#59는 `worklog.md`, #53·#52는 `intent.md`·`worklog.md`가 충돌해 GitHub 표시와 같은 파일이 된다. 그래서 PR 화면의 충돌 표시는 union으로는 사라지지 않는다. 작성자가 내 컴퓨터에서 main을 합쳐 푸시해야 사라진다(합친 결과가 브랜치에 들어가므로). GitHub 화면이 보여 주는 충돌 파일 목록은 직접 보지 못했다.
- 4개 PR 브랜치에는 `.gitattributes`가 없는데도 git 2.55에서는 첫 병합이 충돌 없이 됐다. 위 첫 병합 충돌이 git 버전에 따라 다른지는 확인하지 못했다. 팀원 버전을 알 수 없으니 "설정을 먼저 커밋으로 받는" 절차는 그대로 둔다.
- 판단: 이 충돌이 계속되면 "작업마다 기록 파일 하나로 쪼개기"(위 "고르지 않은 것" 첫째)만 PR 화면의 충돌까지 없앤다. 코드 동결(11-20 21:00) 전이라 지금은 하지 않고, 4개 PR은 작성자가 각자 병합한다.
- 2026-11-18(PR #64·#68을 합친 뒤): **PR 올리기 전에 GitHub이 볼 충돌을 미리 본다: `npm run precheck`.** `git --attr-source=<빈 트리> merge-tree --write-tree --name-only origin/main HEAD`는 `.gitattributes`를 무시한 일반 병합을 읽기만으로 계산해 GitHub 표시와 같은 결과를 낸다. 열린 PR 4개와 모두 일치했다(#70·#69는 `MERGEABLE`이고 충돌 없음, #67·#66은 `CONFLICTING`이고 `docs/intent.md` 충돌). 충돌이면 종료 코드 1과 `CONFLICT` 줄이 나온다(옛 main에서 만든 시험 브랜치로 확인했고, 같은 상황을 union이 켜진 일반 병합은 통과시킨다). `--attr-source` 없이 돌리면 union이 적용돼 GitHub이 충돌이라 해도 "충돌 없음"으로 나와서 쓸모가 없다.
- 한계: "지금 main" 기준이라 승인을 기다리는 동안 main이 움직이면 다시 돌려야 한다. git 2.40 이상이 필요하다(팀원 버전은 확인하지 못함). 근본 해결은 위 "고르지 않은 것" 첫째(기록을 작업마다 파일 하나로)이고 코드 동결 뒤에 다시 본다.
- 2026-11-18(옛 브랜치를 실제로 합친 뒤): **다른 PR이 기록 문서의 구조를 옮겼으면 union이 양쪽을 모두 남겨 중복이 생긴다.** `agents.md`의 표 뒤 문단을 표 앞으로 옮긴 PR #55와 옛 구조의 브랜치를 합쳤더니 문단이 두 번 나오고 표 밖에 떨어진 행이 다시 생겼다(두 브랜치에서 같은 모양). 충돌 표시는 없지만 기록 검사의 "표 밖에 떨어진 행"이 잡았다. 이때는 중복 문단과 떨어진 행을 지우고, 빠진 행은 양쪽에서 표 안으로 모은다. 문서의 구조(문단·표 위치)를 옮기는 PR은 드물게 하고, 옮기면 PR 설명에 적는다.
- 같은 날: 기록 검사의 열 수 계산이 GitHub 표 규칙과 달라 정상 행(맨 끝 세로선 없음)을 실패로 보았다. 규칙대로 고쳤다(`I-doc-fixes-2`).
- 2026-11-18(열린 PR 둘이 같은 번호의 새 ADR을 만들려 함): **ADR 번호도 같은 번호가 둘 생길 수 있다.** 두 PR이 `0019-…`로 서로 다른 이름의 파일을 만들면 git은 충돌로 보지 않고 그대로 합쳐, 같은 번호의 ADR이 둘 남는다(합치기 리허설에서 확인, 시험도 못 잡았다). 기록 검사에 "ADR 번호가 겹치지 않는다"를 더했다. 새 ADR 번호는 PR을 올리기 직전에 최신 main의 마지막 번호 다음으로 정하고, 합치기 직전에 `git merge origin/main` 뒤 `npm test`가 통과하는지 본다.
- 2026-11-19(열린 PR 5개로 다시 측정, `I-auto-sync-main`): **GitHub 화면 충돌은 여전히 사람이 `git merge origin/main`과 푸시를 PR마다 해 줘야 풀렸다.** 읽기로 합쳐 보니 GitHub 화면 충돌은 #103(`agents`·`intent`·`qa`)·#104(`intent`)·#105(`intent`·`worklog`)인데, 내 컴퓨터에서(union 적용) 합치면 #103의 `qa.md` 하나뿐이었다. 원인은 그대로 GitHub 화면의 `merge=union` 무시다.
- **정한 것: 열린 PR 브랜치에 main을 자동으로 합친다.** `.github/workflows/sync-pr-branches.yml`이 main에 푸시될 때마다(그리고 수동 실행으로) 열린 PR(같은 저장소, `feat/`·`fix/`·`docs/`·`chore/` 브랜치만)에 진짜 git으로 main을 합쳐 푸시한다. 사람이 하던 `git merge origin/main`과 같은 일이라 union이 적용된다. 방법 A(`npm run sync` 명령)는 이미 열려 기다리는 PR의 충돌을 못 풀고, C(기록 쪼개기)는 규칙 세 곳을 바꿔야 해서 고르지 않았다.
  - `main`의 `.gitattributes`를 러너의 `.git/info/attributes`에 복사해 쓴다: 설정이 없는 옛 브랜치도 union이 걸린다(위 첫 개정의 "처음 한 번" 문제가 사라진다).
  - 강제 푸시는 하지 않는다: 합치는 사이 작성자가 푸시했으면 거절된다(시험으로 확인). 진짜 충돌은 푸시하지 않고 Actions 실행 요약에 파일 이름만 적는다.
  - `vercel.json`이 미리보기 배포를 꺼 둔 이름(`feat/`·`fix/`·`docs/`·`chore/`)만 건드린다: 다른 이름에 푸시하면 배포 한도(ADR 0018)를 쓴다.
  - 승인은 유지된다: 저장소 규칙(ruleset)의 "푸시하면 승인 취소"가 꺼져 있다(11-19 확인).
- **작성자가 알아야 할 것:** 내 브랜치가 모르는 새 앞서갈 수 있다. 푸시가 거절되면 `git pull --no-rebase`(기록 문서 5개는 union)로 받고 다시 푸시한다. 자동 합치기는 시험을 돌리지 않으니 병합 전 `npm test`와 `npm run precheck`는 그대로 한다.
- **확인하지 못한 것:** Action은 합쳐진 뒤에야 돌려 볼 수 있어 합치는 규칙만 임시 저장소로 시험했다(`lib/records/sync-pr-branches.test.ts`, 핵심 줄을 빼면 실패하는 것도 확인). `GITHUB_TOKEN`은 워크플로 파일을 만들거나 바꾸는 푸시를 못 할 수 있다: 이 PR이 합쳐진 직후, 브랜치에 워크플로 파일이 처음 들어가는 병합은 거절될 수 있고 그때는 작성자가 한 번 `git merge origin/main`을 한다. 합친 뒤 `workflow_dispatch`(dry_run)로 먼저 돌려 본다. 되돌리려면 워크플로 파일을 지운다.
