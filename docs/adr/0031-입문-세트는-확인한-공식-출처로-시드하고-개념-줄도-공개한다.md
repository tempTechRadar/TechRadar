# 0031. 입문 세트는 확인한 공식 출처로 시드하고, 저장소에서 처음 본 개념 줄도 공개한다

- 날짜: 2026-11-21
- 상태: **제안 (사용자 승인 전)**. 운영 적용은 승인 뒤. 팀은 PR 리뷰에서 확인한다
- 관련: ADR 0029 4항(공개 목록 = 소개 출처가 있는 것), ADR 0030 6~8항(기본 보기 · 개발 분야 먼저), ADR 0008 2항(개념 노드), `lib/domain/services.ts` `fixedNote` 주석, `docs/starter-set.md`, 작업 `I-P-12d-starter-set`

## 배경
기본 지도를 교육생 · 나 같은 사용자에게 맞게(스킬 · 개념 · 새 개발 도구) 보이기로 했다(11-21 사용자 "자동 + 입문 세트"). 그런데 운영 공개 목록에는 MCP밖에 없다(11-21 다른 세션의 운영 읽기: mcp 공개 15,701 · skill 0/9 · concept 0/1). 스킬 · 개념 줄은 사용자 저장소를 읽을 때 생겨서 소개 출처가 비어 있고, ADR 0029 4항에 따라 공개 목록에서 빠진다. `services.ts`의 `fixedNote` 주석도 "카탈로그 줄에 글을 쓰면 사용자 저장소에서 생긴 줄이 공개 목록에 나간다"며 쓰지 않는다고 적었다.

## 결정
1. **입문 세트 45개를 시드 마이그레이션으로 넣는다**(개념 14 · 공식 스킬 10 · 공식 플러그인 6 · 개발 도구 15). 한 줄 설명의 근거(`one_liner_source`)는 2026-11-21에 직접 열어 확인한 공식 주소다. 새 값 체계("curated" 등)는 만들지 않는다: 레지스트리 줄이 레지스트리 주소를 쓰는 것과 같은 규칙(관문 3: 근거 링크 없는 정보는 저장하지 않는다).
2. **이미 있는 같은 키의 줄은 비어 있는 칸만 채운다.** 그래서 사용자 저장소에서 처음 본 `concept:harness` 같은 줄도 근거가 생겨 공개된다. 괜찮은 이유: 개념 줄은 키 · 이름이 코드(`services.ts` CONCEPTS)에 고정된 일반 개념이라 사용자 저장소의 정보(내부 주소 · 비공개 패키지 이름)가 들어 있지 않다. ADR 0029 4항이 막으려던 것은 그런 정보가 든 줄이다. 공식 스킬 키(`skill:anthropics/skills/…`)도 공개 저장소의 것이다. **이 예외는 이 목록의 키에만** 적용하고, 저장소 읽기가 만든 다른 줄은 그대로 공개하지 않는다.
3. **NEW · 적용 기회에서 뺀다**(`signals.registry_backfill = true`): 오래된 도구라 들어온 날이 새로 나온 날이 아니다. 단, 이미 있던 줄의 표시가 이긴다(이번 주 사용자 저장소로 들어온 줄의 NEW를 덮지 않음).
4. **플러그인 키 규칙을 새로 정한다**: `plugin:<owner>/<repo>/<이름>`(스킬 `skill:<owner>/<repo>/<이름>`과 같은 모양). 지금까지 플러그인 키가 없었다.
5. 이름 · 종류 · 상태 · 등급은 시드가 바꾸지 않는다.

## 대가
- 공식 문서 주소가 옮겨 가면(이미 docs.claude.com → code.claude.com로 한 번 옮김) 근거 링크가 낡는다. 지금은 다시 확인하는 수집기가 없다.
- 입문 세트는 얇은 줄이고 별 신호가 없어, 지도 500개 고르기(두꺼운 것 → 별 많은 순)에서 밀릴 수 있다. 지도에 늘 오르게 하려면 고르기 규칙에 몫을 따로 둬야 한다(`docs/starter-set.md` 열린 질문 4, 고르기 규칙 담당 작업에서).
- `concept:harness`의 운영 이름 "하네스(에이전트 지시 파일)"는 공식 용어("harness = Claude Code 자체")와 다르다. 이름은 이 시드가 바꾸지 않고 따로 정한다(열린 질문 1).
