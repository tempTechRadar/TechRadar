# 0007. 로그인은 Supabase Auth로 한다 (v1 구글, 노션 로그인과 노션 보내기는 다음 버전)

- 날짜: 2026-11-17
- 상태: **채택** (2026-11-18 회의). 처음: 제안, **2026-11-17 개정** (팀원 1명이 정함. 2026-11-18 회의 D2와 함께 팀 확인)

> **개정 (2026-11-17):** 알파를 노션 보내기에서 **설치 프롬프트**로 바꿨다(ADR 0009). 그래서 노션 로그인을 할 이유가 사라졌다. **v1 로그인은 구글만** 쓰고(이메일 테스트 계정은 개발·QA 환경만), **노션 로그인과 노션으로 보내기는 다음 버전**에 함께 넣는다. 아래 원래 결정은 다음 버전의 설계로 남긴다.

안내서는 로그인·DB·권한에 Supabase나 Appwrite를 반드시 쓰게 한다. 우리는 Supabase를 고른다(`docs/prd.md` 4절). 그 위에서 **노션 계정 로그인**을 더한다. 이유는 **쌓인 내 기술 목록을 사용자의 노션 데이터베이스로 보내기 위해서**다. 그룹1 인터뷰의 "깐 것 목록이 없어서 노트북을 반납할 때 옮기기 막막하다"는 장면이 근거다. 노션 로그인은 Supabase Auth가 지원하므로 "로그인은 Supabase로"라는 안내서 요건을 그대로 지킨다.

## 정한 것
- 로그인은 **노션 또는 구글**이다(2026-11-17 바꿈: 처음엔 노션 또는 이메일). 비밀번호 재설정·가입 확인 메일 흐름을 만들지 않아도 되고, 메일 발송 한도 문제도 없다. **이메일 테스트 계정은 개발·QA 환경에서만** 환경변수로 켠다. 실제 구글·노션 로그인 화면은 Claude가 대신 들어갈 수 없어서, 이것이 없으면 권한 QA가 모두 사람 몫이 된다. 구글로 가입한 사용자는 설정에서 노션을 연결할 수 있다.
- 노션에는 **우리 → 노션 한 방향**으로만 쓴다. 보내는 것은 내 기술 목록(숨긴 기술 제외)이다.
- 사용자가 **버튼을 누르고 미리보기를 확인한 뒤에만** 보낸다. 사용자의 노션에 쓰는 것은 바깥을 바꾸는 조치라서 불변 규칙 1을 따른다.
- 처음 연결할 때 고른 페이지 아래에 데이터베이스를 하나 만들고, 그다음부터는 기술마다 같은 행을 고친다. 여러 번 보내도 행이 두 번 생기지 않는다(불변 3).
- 사용자의 노션 토큰은 **서버 쪽에 암호화해 보관**하고, 브라우저와 관리자에게 보이지 않는다. 연결을 끊으면 지운다.

## 결과
- IA에 "설정·노션 연결" 화면(IA-19)과 IA-3의 "노션으로 보내기" 버튼이 생긴다.
- 회의 D2(알파)는 "ⓐ 목록 내보내기 = 노션 데이터베이스로 보내기"로 올라간다. D2가 ⓐ가 아니면 이 ADR도 다시 정한다.
- 바깥 서비스(노션)에 쓰고 사용자 토큰을 보관하게 되므로 보안 요구(`docs/prd.md` PRD-NF2)와 사람 QA(실계정 노션 로그인)가 늘어난다.
- **확인하지 못한 것:** Supabase가 노션 토큰을 보관·갱신해 주는지, 노션 토큰이 만료되는지, 노션 API 요청 한도, 동의 화면의 페이지 고르기가 헷갈리지 않는지. 모두 뼈대 단계에서 확인한다. 구글 로그인에 앱 심사가 필요 없는지(이름·이메일만), 운영 모드 전환 조건도 확인 전이다.

## 고르지 않은 것
- 노션 로그인 없이 파일로 내보내기: 사용자가 이미 노션을 쓰는 흐름을 살리지 못한다.
- 자동 동기화·양방향: 불변 규칙 1과 충돌하고, 6일 안에 충돌 규칙까지 만들기 어렵다.
- 운영에서 이메일·비밀번호 로그인: 비밀번호 재설정·메일 확인 흐름과 메일 발송 설정이 필요해 부담이 크다(2026-11-17).
