# 0030. 두껍게 들이는 기준: 별 개수 하나가 아니라 "관문 + 점수 + 의심 거르기", 그리고 Hacker News를 이번에 읽는다

- 날짜: 2026-11-21
- 상태: **채택** (2026-11-21, 사용자가 계획을 승인했다. 다른 팀원은 PR 리뷰에서 확인)

데이터설계 8절의 "인기" 경로(갈래 안 점수 상위 20개)는 재료(HF·HN·skills.sh 수집)와 갈래 목록이 없어서 코드가 없었다(P-21, 3순위). 그래서 지금 두꺼워지는 기술은 "공식 조직"과 "사용자가 쓰는 것"뿐이다. 사용자가 "별이 있으면 시도해볼 만하다는 신호이니 별로 뽑자, 소스도 더 다양하게"를 제안했다. 11-21에 GitHub 검색으로 재어 보니 별 1만 이상은 태그 다섯 개를 합쳐 수백 곳이라 다룰 수 있었고(`mcp-server` 51 · `mcp` 163 · `claude-code` 145 · `agent-skills` 64 · `claude-skills` 33, 태그끼리 겹침), 지난 7일에 새로 생긴 `mcp-server` 저장소 상위에는 **같은 이름 복제본이 낯선 계정 5곳에서 별 472~474개**로 줄지어 있었다(열어서 확인하지는 않았다). 이 서비스는 "써도 되는지 판단"을 돕는 보안 서비스라, 가짜 별 저장소가 "뜨는 기술"로 올라오면 신뢰가 깨진다.

## 정한 것
1. **별을 쓰되 별 하나로 자르지 않는다: 관문 → 의심 거르기 → 점수 순.** 갈래 안 점수(상위 20개)를 기다리지 않고, **별 후보**라는 경로를 1순위 흐름에 앞당긴다(ADR 0020 4번 "GitHub 주제 태그 탐색은 3순위"를 개정).
   - **후보 풀:** 주제 태그 `mcp-server`·`mcp`·`agent-skills`·`claude-skills`에 맞고 별 ≥ 1,000인 저장소. `claude-code` 태그는 앱·가이드가 섞여 종류를 못 정해서 이번에는 뺀다.
   - **관문(모두 통과):** 보관 아님 · 마지막 푸시 12개월 이내 · 포크 저장소 아님 · 의심 표시 없음.
   - **의심 표시(시험으로 고정):** ① 생성 30일 미만인데 별 ≥ 500 → `new_spike` ② 같은 저장소 이름이 다른 소유자 2곳 이상이고 별 차이 ≤ 5% → `clone_cluster`. 의심은 두껍게도 알림에도 쓰지 않고 "NEW 후보(얇게, 관리자 확인)"로만 둔다. 의심 표시는 "확인 필요"일 뿐 증명이 아니다.
   - **점수:** 같은 태그 안 백분위 평균. 규모(별) 30 · 성장(별÷나이일, 나이는 최소 30일) 25 · 사용 증거(포크) 15 · 활동(푸시 최근성) 15 · 신뢰 15(조직 소유 · 라이선스 있음 · 공식 레지스트리 줄과 합쳐짐). 성장은 가짜 급증에 상을 주기 쉬워서 나이 하한과 의심 거르기를 먼저 둔다.
   - **두껍게 들이는 것:** 점수 상위, 합쳐 **최대 100곳**. 이유 `thick_reasons`에 `stars`를 더하고 `signals.candidate_score`·`candidate_flags`·`stars`를 저장한다(`category_score`와 칸을 섞지 않음). 이번 구현은 "들어오기"만 한다: 한 번 들어온 줄을 순위 밖이라고 빼는 완충(데이터설계 8절 "순위 완충")은 첫 수집 뒤로 미루고, 대신 **별 이유로 두꺼워진 줄 누적 상한 150곳**을 둔다(상한에 닿으면 더 올리지 않고 실행 요약에 "상한"을 적는다).
   - 검색 결과 한 건에 별·포크·푸시·생성일·소유자 종류·라이선스·보관·설명이 같이 와서 저장소마다 따로 부르지 않는다. 새 줄은 `github:<소유자>/<저장소>` 키이고, **이미 같은 저장소(`repo_url`)를 가진 줄(공식 레지스트리·사용자가 만든 줄)이 있으면 새 줄 대신 그 줄을 두껍게·신호만 갱신**한다(같은 기술이 여러 줄이 되지 않게).
2. **Hacker News를 이번에 읽는다**(PRD-F8에 이미 적혀 있었는데 v1이 안 읽던 것을 맞춘다). `search_by_date`(키 없음, 간격 1초)로 키워드(`mcp`·`model context protocol`·`claude code`·`agent skills`)에 맞는 글을 읽고, **글이 GitHub 저장소나 npm 패키지로 이어질 때만** 쓴다(데이터설계 8절 관문 1의 기존 규칙). 알려진 기술에는 `signals.hn`(점수·댓글·글 링크)만 붙이고, 모르는 저장소는 이름에 mcp·skill이 맞을 때만 **얇게** 추가한다. 이번에는 점수 계산에 넣지 않고 "화제" 표시와 근거 링크로만 쓴다. GeekNews·Hugging Face·skills.sh·블로그 RSS는 제출 뒤(P-21 본 계산)로 둔다.
3. **적용 기회 알림 조건 4를 다시 넣는다**(ADR 0014 개정): 새 기술의 별 수가 **알려져 있고 100 미만이면** 알림을 만들지 않는다. **별 수를 모르면 제외하지 않는다**(못 읽은 것을 낮다고 단정하지 않음, 불변 2). **시뮬레이터가 만든 변경(`is_simulated`)에는 적용하지 않는다**(가짜 기술은 별 정보가 없고, ADR 0014가 조건 4를 미룬 이유가 이것이었다).
4. **별 후보 검색은 `sources`에 새 줄 `github_search`(priority 3)를 둬서 관리자가 따로 끌 수 있게 한다.** `github` 줄을 같이 쓰면 저장소 정보 수집까지 꺼지고 관찰 기록의 출처가 섞인다. HN은 이미 있는 `hn` 줄을 쓴다. 추가형 마이그레이션 1줄이라 운영에 먼저 적용한 뒤 합친다.

## 결과
- 데이터설계 8절(관문 1의 GitHub·HN 행, 관문 2의 인기 행, "별 후보" 절), data-sources(0절 아래 "추가 예정" 표), prd F8, spec 3.2(조건 4)·11절(추정 숫자), plan(P-21을 P-21a·b·c로 쪼갬, P-22에서 "주제 태그 탐색" 이동), ADR 0014·0020 개정 줄. 구현과 시험은 P-21a(별 후보)·P-21b(HN)·P-21c(알림 조건 4).
- 흐름 화면은 새 상자 `fetch_stars`를 더하고 이미 있는 `fetch_popularity`를 켜서 소스를 `["hn"]`으로 둔다(불변 6: 실제 실행 기록으로 그림).
- **확인하지 못한 것:** 풀 하한 1,000 · 상한 100 · 누적 상한 150 · 알림 100 · 점수 가중치 · 의심 두 규칙의 숫자는 모두 **팀 추정**이다. 첫 수집 뒤 실제 개수·분포를 세어 고친다. 의심 두 규칙은 가짜 별을 다 못 막는다.
- **11-21 운영 DB 읽기로 잰 것:** 오늘 06:07 정기 실행은 **63초**(레지스트리 61초, 나머지 세 단계는 각각 1초 미만)라서 묶음 예산 240초·`maxDuration` 300초 안에 새 수집기 두 개(몫 20초씩)가 들어간다. 저장소 정보 수집기(`fetch_github`)는 그 실행에서 "0개 읽음"으로 끝났다(두꺼운 기술 12개는 모두 "쓰는 중"이고 `repo_url`이 있는 두꺼운 줄이 0개). 코드가 토큰을 먼저 검사하므로 `GITHUB_TOKEN`은 운영에 있는 것으로 보인다(값은 보지 않았다).
- **알려진 한계(이중 줄):** 레지스트리 첫 전체 읽기가 아직 끝나지 않았다(오늘 `technologies` 15,736줄, 하루 4,200개씩 읽어 12월 초까지 계속). 별 후보·HN이 먼저 만든 `github:` 줄과, 나중에 레지스트리가 같은 `repo_url`로 만드는 `mcp:` 줄이 이중이 될 수 있다. 별 후보 쪽에서 합치기만으로는 못 막으므로 레지스트리의 `applyDrafts`가 같은 저장소의 `github:` 줄을 찾아 합치는 후속 조각(P-21d)을 제안한다. 사용자 결정 전까지는 이중 줄을 알려진 한계로 둔다.

## 고르지 않은 것
- **별 1만 이상 같은 개수 컷만 쓰기:** 가짜 별과 오래된 저장소 유리함을 못 거른다. 다만 1만 이상은 점수에서 거의 다 들어온다.
- **"최근 며칠 별 증가 상위 10" 그대로 쓰기:** 새로 생긴 가짜·미끼 저장소가 가장 위로 올라오고, GitHub에는 "최근 N일 별 증가" API가 없어서 Trending 화면 읽기(공식 API 없음, 구조가 바뀌면 깨짐)나 우리 쪽 일별 저장이 필요하다. 성장은 "별÷나이일"로 대신하고, 우리 쪽 7일 증가는 값이 쌓인 뒤에 더한다.
- **조건 4를 갈래 안 상위 절반으로 두기:** 갈래 목록과 점수가 아직 없다(ADR 0014 그대로). 별 수만 아는 만큼 쓰는 절대 하한으로 먼저 넣고, 갈래 안 점수가 생기면 바꿀지 다시 본다.
- **GeekNews를 이번에 읽기:** robots가 "요약·링크 표시는 되고 학습용 수집은 금지"라 제목·링크만 쓸 수 있고, 글에 딸린 저장소 링크 모양을 확인하지 못했다. 제출 뒤로 둔다.
