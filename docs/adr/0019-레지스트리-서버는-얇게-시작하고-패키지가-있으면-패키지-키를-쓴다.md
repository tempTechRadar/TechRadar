# 0019. 공식 MCP 레지스트리 서버는 얇게 시작하고, 패키지가 있으면 패키지 키를 쓴다

- 날짜: 2026-11-18
- 상태: **채택** (2026-11-18, 사용자가 두 질문에 추천안을 골랐다: "얇게 시작, 쓰거나 공식 조직이면만 두껍게", "패키지가 있으면 npm:·pypi: 키, 없으면 mcp:<이름>"). 같은 날 코드 검토(읽기 전용 검토자)를 반영해 "쓰기 시작하면 두껍게"를 DB 트리거 한 곳으로, 공식 조직 목록의 값을 이름공간 전체로 고쳤다(아래 "코드 검토 반영").

## 배경
P-9c(공식 MCP 레지스트리 수집기)를 만들려는데 `docs/데이터설계.md`가 두 곳에서 서로 어긋났다.

1. **얇게냐 두껍게냐.** 8절 관문 1 표는 "공식 MCP 레지스트리: 모든 서버 → 얇게"인데, 관문 2 표는 "공식: 공식 조직이 냈거나 공식 MCP 레지스트리에 등재 → 바로 통과(두껍게)"다. 둘을 글자 그대로 따르면 레지스트리에 등재된 서버 전부가 두꺼워진다.
2. **기술 키.** 7절 표는 레지스트리 서버의 키를 `mcp:<레지스트리 이름>`으로 적었는데, 같은 절 마지막 줄은 "한 기술이 패키지와 저장소를 둘 다 가지면 패키지 키를 신분증으로 쓴다"고 한다.

실제 레지스트리(2026-11-17 샘플 100건, 2026-11-18 API 확인)에서 본 것:
- 서버마다 **모든 버전**이 목록에 나오고 `isLatest`가 참인 것만 최신이다(`version=latest`를 달면 최신만 나온다. 삭제된 최신도 나온다). 목록은 서버 이름순이다(커서가 `이름:버전`).
- 서버의 약 82%는 패키지 없이 원격 주소(`remotes`)만 있다. npm 8·PyPI 8·mcpb 2(100건 중).
- 항목마다 붙은 `_meta["io.modelcontextprotocol.registry/official"]`은 레지스트리 자신의 메타 이름이라 **모든 항목에 있다**. "공식 레지스트리에 등재"를 "공식"으로 읽으면 전부 공식이 된다.
- 13시간에 100건 넘게 바뀐다(새 85·중단 7·삭제 8).

## 정한 것
- **얇게 시작한다.** 레지스트리에서 들어온 서버는 얇은 줄(이름·설명·링크·저장소)로만 저장한다. 두꺼워지는 경우는 둘이다.
  - **쓰는 사람이 생김:** 누군가 내 기술로 두면(`my_technologies` 줄이 생기면) 두껍게 올린다(`thick_reasons`에 `used`). 올리는 곳은 **DB 트리거 한 곳**이다(`thicken_used_tech`, 아래 "코드 검토 반영").
  - **공식 조직:** 서버 이름의 **이름공간 전체**(`/` 앞쪽)가 `rule_lists`의 `official_org` 목록의 값과 같으면 두껍게 둔다(`official`). 값은 `io.github.openai`·`com.openai`처럼 이름공간 전체다. 레지스트리가 이름공간을 검증한다(`io.github.<소유자>`는 GitHub 인증, 도메인 이름은 DNS). **게시자가 적는 저장소 주소는 증거로 쓰지 않는다**(레지스트리가 이름공간과 맞는지 검증하지 않아, `io.github.남/x`가 `https://github.com/openai/…`를 적어도 공식이 되면 안 된다). 일부만 맞는 이름(`com.example.openai`, `dev.openai`)과 서버 이름(`/` 뒤쪽)도 보지 않는다(보안 검토 반영). 처음 목록은 문서의 예(modelcontextprotocol·anthropics·openai)를 `io.github.` 아래로 옮긴 것이고 관리자가 고친다.
  "공식 MCP 레지스트리에 등재"만으로는 두껍게 만들지 않는다. 관문 2 표의 "공식" 줄은 이 뜻으로 읽는다.
- **기술 키:** 최신 버전의 패키지에 npm이 있으면 `npm:<이름>`, 없고 PyPI가 있으면 `pypi:<이름>`, 둘 다 없으면(mcpb·nuget·oci·원격 주소만) `mcp:<레지스트리 이름>`. 사용자의 `.mcp.json`(`npx …`)이 만드는 `npm:` 키와 같은 기술이 한 줄로 합쳐지고, OSV·다운로드 확인과 적용 기회가 이미 쓰는 키를 그대로 쓴다. 레지스트리 이름은 설명의 출처 링크에 남는다.
- **상태:** 레지스트리 `active` → `active`, `deprecated` → `deprecated`(중단), `deleted` → `gone`(출처에서 사라짐). 데이터설계 8절의 "출처가 직접 사용 중단이라고 함"에 해당하므로 두 번 읽기를 기다리지 않는다. 다른 출처가 정한 상태(`dormant` 등)는 바꾸지 않는다.

## 코드 검토 반영 (2026-11-18)
검토자가 코드·실제 레지스트리 응답으로 찾은 것 중 고친 것:
- **쓰기 시작하면 두껍게 → DB 트리거.** 처음에는 첫 읽기 코드(`first-read.ts`)에서만 올렸는데, 직접 추가(`addTech`)·가져오기(`saveLocalImport`)는 사용자 연결로 `my_technologies`에 넣고 그 연결은 `technologies`를 못 고친다. 그러면 얇은 레지스트리 줄을 쓰는데도 OSV·다운로드 확인에서 빠져 등급이 `unknown`으로 남는다. `my_technologies` insert 뒤 트리거 한 곳이 모든 길을 덮는다(마이그레이션 `202611190901`). 이미 두꺼운 공식 줄에도 `used` 이유를 더한다. `first-read.ts`는 원래대로 둔다.
- **공식 조직 값은 이름공간 전체.** 낱말(`openai`)만 맞추면 `dev.openai`·`net.modelcontextprotocol` 같은 아무 최상위 도메인이나 통과했다. 또 값이 GitHub 조직 이름이라 도메인 이름과 철자가 다를 수 있다(`anthropics` ↔ `com.anthropic`).
- **같은 패키지를 쓰는 서버가 여럿이면** 한 쪽 안에서는 쓰는 중인(active) 서버가 이긴다(중단된 서버가 먼저 나와 active 서버를 가리면 그 서버는 줄이 안 생기고 바뀐 것만 읽을 때도 다시 안 읽혔다).
- **상태를 고치면 바로 수집 자료도 남긴다.** 수집 자료 저장이 실패하면 상태를 되돌리고 던진다(안 되돌리면 다음 실행은 "이미 바뀜"으로 보고 기록이 영영 안 남았다. downloads와 같은 규칙).
- 요청에 `version=latest`를 달아 쪽 수를 줄였다. `isLatest`가 없거나 참·거짓이 아니면 "최신 아님"이 아니라 못 읽은 항목으로 센다. 보이는 이름은 공백을 정리하고 100자로 자르며, 저장소 주소는 https만 저장한다(게시자가 적는 글).
- 설명은 이 서버가 직접 적은 것(출처 링크가 같음)만 바뀐 값으로 새로 고친다. 관리자 분류 목록은 얇은 줄을 빼고, 규칙 목록에 `official_org`를 더했다.

## 결과
- `docs/데이터설계.md` 7절 표·8절 관문 2 표를 이 뜻으로 고친다. `docs/erd.md`에 `sources` 칸 3개와 `rule_lists` 종류를 적는다.
- 마이그레이션 `202611190900_P-9c_registry_sync.sql`: `sources.last_synced_at`·`sync_started_at`·`sync_cursor`, `rule_lists` 종류에 `official_org`와 처음 값 3개. `202611190901_P-9c_thicken_on_use.sql`: 쓰기 시작하면 두껍게 올리는 트리거, 공식 조직 값을 이름공간 전체로.
- 되돌리려면 이 ADR을 고치고 수집기의 `techFromEntry`(키)·`isOfficialOrg`(두껍게)를 바꾼다. 이미 저장된 키는 바뀌지 않으므로 키 규칙을 뒤집으면 저장된 줄을 옮겨야 한다(그래서 ADR로 남긴다).

## 고르지 않은 것
- **등재된 것 전부 두껍게:** 6만 개가 넘는 서버가 매일 OSV·GitHub 확인 대상이 되어 시간 예산(240초)을 넘고, 66%는 패키지가 없어 OSV로 확인할 수도 없다.
- **항상 `mcp:<이름>`:** 같은 기술이 `npm:`(사용자 저장소)과 `mcp:`(레지스트리) 두 줄이 되어, 사용자가 쓰는 기술이 새 기술로 알림이 오거나 확인이 어긋날 수 있다.
- **쓰는 곳마다 코드로 두껍게 올리기:** 첫 읽기·직접 추가·가져오기·나중에 생길 길마다 서비스 키 코드가 필요하고 하나만 빠뜨려도 확인에서 빠진다. 트리거 한 곳이 낫다.

## 알려진 한계 (고치지 않고 남긴 것, 검토 반영 때 확인)
- **원격 주소만 있는 서버(대부분)는 사용자의 `.mcp.json`이 만드는 `url:<호스트>` 줄과 합쳐지지 않는다.** 키가 `mcp:<이름>`이라 레지스트리가 그 서버를 중단·삭제해도 사용자의 기술 줄은 안 바뀐다. 데이터설계 7절의 합치기 약속은 npm·PyPI 패키지가 있는 서버(전체의 34%, 22,668개)에만 지켜진다. 호스트로 합칠지는 한 호스트에 서버가 여럿일 수 있어 따로 정해야 한다(열린 질문).
- **같은 패키지를 가리키는 서버가 쪽을 건너 여럿이면** 줄 하나를 나눠 쓰고 마지막으로 읽은 서버의 상태가 이긴다. 런처 패키지가 그렇다(예: ECS·EKS 서버가 `pypi:mcp-proxy-for-aws` 공유). 그 줄의 설명은 먼저 읽은 서버 것이다.
- **상태의 주인이 없다.** 레지스트리 `active`는 중단·사라짐을 되돌린다. 나중에 npm·저장소 확인(P-9b)이 `deprecated`·`gone`을 정하면 레지스트리가 다시 `active`로 되돌릴 수 있다. P-9b를 만들 때 "누가 정한 상태인지"를 정한다.
- **한 쪽이 계속 실패하면(응답 모양·크기) 그 자리에서 멈춘다.** `collect_error`로 보이고 오류가 이어지면 관리자 강조가 켜진다. 건너뛰는 규칙은 없다.
- **겹쳐 도는 실행은 막지 않는다**(`runBatch`에 잠금이 없다, 이미 열린 질문). 겹치면 같은 상태 기록이 두 번 남거나 `thick_reasons`를 낡은 값으로 덮을 수 있다.
- **수집 자료 저장 실패 뒤 되돌리기도 실패하면** 상태는 바뀐 채 기록이 없다(오류 문구에 그렇게 적힌다).

## 확인하지 못한 것
- **레지스트리 전체 크기(2026-11-18, `version=latest`로 끝까지 읽기 전용 확인):** 최신 서버 66,788개·668쪽(active 65,710·deprecated 1,078, 전체 읽기 목록에는 deleted가 없다: 삭제된 것은 `updated_since`로 읽을 때만 나온다). npm·PyPI 패키지가 있는 것 22,668개(34%), 서로 다른 패키지 키 22,108개, 같은 패키지 키를 쓰는 서버 쌍 507개.
- **첫 전체 읽기는 약 33일**(668쪽 ÷ 한 실행 20쪽 안팎, 쪽마다 1초 간격과 DB 호출 5번 안팎·하루 몫 60초에서 어림한 값, 실제 속도는 첫 실행을 본 뒤에 안다). 그동안 바뀐 것만 읽기로 넘어가지 않아 이미 읽은 서버의 중단·삭제 반영도 늦다. 고르는 길(팀 결정, intent 열린 질문 ④): 하루 몫 늘리기, 원격 주소만 있는 서버(약 4만 4천 개)는 안 들이기, 긴 전체 읽기 중에도 바뀐 것만 따로 읽기.
- **패키지 소유 검증을 이 조각에서 확인하지 못했다.** 게시자가 남의 npm·PyPI 패키지 이름을 자기 서버에 적어 그 패키지 줄의 상태를 중단·사라짐으로 바꿀 수 있는지는 레지스트리가 게시할 때 패키지 소유를 검증하는지에 기댄다(npm `mcpName` 같은 것). 검증 여부를 직접 확인하지 못했고, 수집기는 이 검증 신호를 읽지 않는다. 상태는 줄 하나에 하나뿐이라 위 "상태의 주인이 없다"와 같은 문제다.
- **사용자 한 명이 얇은 줄을 두껍게 만드는 것(트리거)은 의도다**("쓰는 사람이 생기면 두껍게"). 여러 사람 확인 같은 문턱은 두지 않았다. 직접 추가·가져오기·첫 읽기로 아무 기술이나 두껍게 만들 수 있는 것은 이미 있던 일이고(첫 읽기는 한 번에 `MAX_TECHS`개까지), 비용은 OSV 몫(150초)이 막는다. 입력 한도는 intent의 열린 질문과 같은 문제다.
- 공식 조직 목록의 값은 문서의 예를 옮긴 팀 추정이다. 2026-11-18 레지스트리에서 `io.github.modelcontextprotocol`·`io.github.anthropics`·`io.github.openai`·`com.anthropic`·`com.openai` 이름공간으로 등록된 서버는 **없었다**(같은 날 읽어 확인, 없는 것을 확인한 것이라 나중에 생길 수 있다). 실제로 있는 이름공간의 예: `com.microsoft`, `io.github.github`. 어떤 조직을 공식으로 볼지는 관리자·팀이 정한다.
- 게시자가 적는 이름·설명이 AI 초안 입력에 `techName`으로 그대로 들어가는 길(`draft.ts` → `build-draft-prompt.ts`)은 이 조각의 파일이 아니라 고치지 않았다. 이름을 100자로 자른 것까지만 했다.
