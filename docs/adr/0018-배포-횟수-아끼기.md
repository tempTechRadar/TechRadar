# 0018. 무료 Vercel에서는 배포 횟수를 아낀다: PR 브랜치는 배포하지 않고 main만 배포한다

- 날짜: 2026-11-18
- 상태: **채택** (2026-11-18, 사용자가 "무료에서 진행하되 배포 횟수를 최대한 아끼는 방향으로 스타일을 정해서 팀과 공유"를 요청해 정함. 다른 팀원은 PR 리뷰에서 확인)

## 배경
PR #64의 Vercel 검사가 "Deployment rate limited — retry in 24 hours"로 실패했다. 이후 새 PR의 Vercel 검사가 모두 실패한다. 프로젝트 `techradar`의 최근 24시간 배포를 세어 보니(목록이 100개에서 잘려 실제는 더 많다) 약 5시간(UTC 01:53~06:52)에 100개가 생겼다.
- production(main에 합칠 때마다) 31개, preview(PR 브랜치에 푸시할 때마다) 69개
- preview 중 `docs/`·`chore/` 브랜치 11개(문서만 고친 PR도 배포가 생김). 한 브랜치에 7번 푸시한 곳도 있다
- 무료(Hobby)는 하루 100번 안팎으로 알고 있다. 오늘 에러와 숫자가 맞지만 문서로 확인하지는 못했다

## 병합을 막지는 않는다 (규칙을 바꾸지 않은 이유)
- GitHub ruleset "main 보호"(27512725)에는 삭제 금지·강제 푸시 금지·PR 승인 1개만 있고 **필수 검사 규칙이 없다**. 옛 방식 보호 설정도 없다(404).
- 실제로 승인된 #59는 Vercel 검사가 실패인데도 병합 가능(`UNSTABLE`)이었다. 승인 대기인 PR이 `BLOCKED`인 것은 검사 때문이 아니라 승인 때문이다.
- 그래서 병합을 위해 규칙을 완화하지 않았다.

## 정한 것
- **`vercel.json`의 `git.deploymentEnabled`로 `feat/*`·`fix/*`·`docs/*`·`chore/*` 브랜치의 배포를 끈다.** 배포가 아예 만들어지지 않아 한도에 들지 않고, PR에 빨간 Vercel 검사도 뜨지 않는다. main에 합칠 때만 production 배포가 생긴다.
- **푸시를 모은다.** 브랜치는 로컬에서 `npm run build`·`npm test`를 통과한 뒤 PR을 올릴 때 한 번만 푸시하고, 리뷰 반영도 모아서 푸시한다. 미리보기를 끄지 못한 옛 브랜치와, 앞으로 미리보기를 다시 켜는 경우에 푸시 횟수가 곧 배포 횟수다.
- **화면은 로컬(`npm run dev`)이나 내장 브라우저로 본다.** 리뷰어도 PR 화면 대신 브랜치를 받아 본다.
- **main 배포는 계속한다.** 병합할 때마다 배포 상태와 주소를 확인한다. 구글 로그인 주소·환경변수·매일 06:00 예약 실행·DB 권한(RLS)처럼 배포 주소에서만 나는 문제를 마감 직전에 처음 만나지 않으려는 것이다(`CLAUDE.md` 10절).

## 결과
- `CLAUDE.md` 10절에 규칙을 적고 `vercel.json`에 설정을 넣는다.
- 설정은 브랜치가 main을 합친 뒤부터 그 브랜치에 적용된다고 본다. 옛 브랜치는 합치기 전까지 미리보기가 계속 생길 수 있다.
- **확인함(2026-11-18):** 이 설정이 든 `chore/vercel-deploy-limit` 브랜치는 푸시 3번을 해도 Vercel 검사가 생기지 않았다(`gh pr checks`: no checks reported). 설정이 없는 #64는 같은 시각 "Deployment rate limited" 검사가 떴다. 즉 설정은 브랜치 자기 `vercel.json`에서 읽힌다.
- 되돌리려면 `vercel.json`의 `git` 블록을 지운다. 한 PR만 미리보기가 필요하면 그 브랜치에서만 해당 줄을 빼면 된다.
- **확인하지 못한 것:** 무료 한도 숫자(문서 확인 못함), 계정이 Hobby인지 직접 확인하지 못함, 건너뛴 배포가 한도에서 빠지는지, 한도가 언제 다시 열리는지.

## 고르지 않은 것
- **막판에 몰아서 배포:** 배포 주소에서만 나는 문제를 코드 동결(11-20 21:00)·발표(11-23) 직전에 처음 만난다.
- **Pro로 업그레이드:** 비용이라 팀이 정할 일이다. 이 방식으로도 모자라면 다시 본다.
- **한도 때문에 병합 규칙 완화:** 검사는 병합 조건이 아니므로 필요 없다.
- **`feat/`·`fix/` 미리보기는 남기기:** 가장 많은 배포가 여기서 생겼다(preview 69개 중 58개). 최대한 아끼기로 해서 끈다. 리뷰에서 화면 확인이 꼭 필요해지면 다시 본다.

## 개정
- 2026-11-18(PR #68·#74 뒤): **한도가 main 병합으로 옮겨 갔다.** 미리보기를 끈 뒤(16:21)에도 main 병합 배포가 "Deployment rate limited"로 실패한다(#69·#70·#71·#73 실패, #72·#74 성공이 섞임). 16시 이후 배포 4개가 모두 main 병합이고, 그중 하나는 문서만 바꾼 #74였다.
- 정한 것: `vercel.json`에 `ignoreCommand`를 넣어 **문서만 바뀐 병합은 빌드를 건너뛴다.** 병합 앞 main(`HEAD^`)과 비교해 `docs/`·`interviews/`·`rules/`·`.claude/`·루트 `*.md` 밖에 바뀐 파일이 없으면 건너뛴다(종료 코드 0). 바뀐 파일이 있거나 비교가 안 되면(`|| exit 1`) 빌드한다.
- 일부러 제외 목록에 넣지 않은 것: `wiki/`(P-26 챗봇이 서버에서 `wiki/`를 읽음, PRD-F31), `sim/skills/`·`eval/`(관리자 채점 버튼이 런타임에 `sim/skills/*/SKILL.md`·`eval/gold.json`을 읽음), `slides/`(발표 슬라이드를 Vercel로 보여 줌). `*.md`는 루트 것만 제외한다(모든 깊이에서 제외하면 시험용 `SKILL.md`가 빠진다). P-26이 `docs/`나 `interviews/`를 서버에서 읽게 되면 그 폴더를 제외 목록에서 뺀다(담당자 확인).
- 시험(실제 문자열 그대로): 실제 병합 4개는 #74만 건너뜀, #72·#71·#73은 빌드. 한 파일만 바꾼 가상 커밋 6개는 `docs/`·`interviews/`·`README.md`가 건너뜀, `wiki/index.md`·`sim/skills/…/SKILL.md`·`app/page.tsx`가 빌드.
- **확인하지 못한 것:** 건너뛴 배포가 Vercel 하루 한도에서 빠지는지, 건너뛴 병합이 GitHub 커밋 상태에 어떻게 표시되는지(실패처럼 보일 수 있음), Vercel 빌드 환경에서 `HEAD^`가 항상 있는지(없으면 빌드로 감).
- 되돌리려면 `ignoreCommand` 줄을 지운다.
- 2026-11-19(#150·#151·#152 배포 실패 뒤): 한도가 다시 찼다(지난 24시간 기록 77개 중 문서만 바뀌어 건너뛴 것 30개). **main 배포를 Vercel Git 자동 배포 대신 GitHub Actions가 부르도록 바꾼다 → ADR 0023.** 이 문서의 `ignoreCommand`는 지운다(0023 "정한 것" 참고).
