## 1. 한 문장
바깥 세상의 변화를 지켜보다가, 중요한 변화가 생기면 알리고, **사람이 승인해야** 처리하고, 기록으로 남기는 웹서비스. 가장 크게 보는 것은 **문제 정의**.

## 3. 진행 순서(권장, 순서는 팀이 정함)
1. **문제 정의 + 인터뷰** ← 지금 여기. 후보 2~3개 비교, 접은 후보와 이유 기록
2. 뼈대 저장소(비공개) + README + 팀 CLAUDE.md + `docs/`
3. 기획 문서: IA → uj → prd → 데이터설계 → erd → spec → plan → intent (문서마다 팀 승인, `grill-with-docs` 사용)
4. 공개 자료 1건 직접 읽어 샘플 저장 → 수집 코드
5. Supabase 또는 Appwrite(하나 필수): 로그인, DB, 권한
6. 사건 → 알림 → 승인 → 기록, 시뮬레이터, 채점
7. 정기 실행(배포 앱에서도 돎) + "지금 한 번 실행" 버튼
8. 흐름 화면, 위키·챗봇
9. QA, 발표 슬라이드(Vercel), 개인 포트폴리오·이력서

중간 점검: 문제를 근거로 좁힌 과정, 반대 사례, 사건 기준과 조치 연결, 샘플 데이터 1곳. 마무리: 시뮬레이터로 사건 1건이 끝까지 돌고, 배포 주소에서 시연 가능.

## 4. 문제 정의 규칙
- 문장: `[누가]는 [어떤 상황]에서 [무엇이 바뀐 것]을 늦게 알아서 [손해]를 본다. 지금은 [방법]으로 버틴다.`
- 인터뷰는 **실제 사람 2명 이상**(가능하면). 질문은 "마지막으로 놓친 때가 언제였나요?"처럼 **겪은 일**을 묻는다. "이 앱 필요하죠?"는 금지. 이름·연락처는 적지 않고, 기록 허락을 먼저 받는다.
- 사람이 어려우면 AI 인터뷰(서로 다른 사용자 3명 이상). **사람/AI 구분 표시.** AI 인터뷰·가짜 데이터는 실제 수요의 증거가 아니다.
- 반대 근거와 "아직 모르는 것"을 적는다. 숫자는 잰 것/당사자 말/팀 추정으로 나눈다.
- 근거 → 요구사항 → 사건 기준 → 조치 → 확인 방법이 끊기지 않게 잇는다.

## 5. 데이터 수집 규칙
- 방법 3가지(공공 API / 직접 만든 크롤러 / Firecrawl) 중 **1가지 이상 직접 구현**, 출처는 서로 다른 **2곳 이상**.
- 크롤러: **공개 페이지만**, 로그인·개인정보·유료 글 제외, 약관·robots 확인, 요청 사이 간격. Firecrawl은 무료 한도 안에서만.
- 읽기 실패는 "변화 없음"이 아니라 **수집 오류**로 기록. 막히면 저장 샘플 + 시뮬레이터로 이어간다.
- `docs/data-sources.md`: 어디를, 방법, 간격, 한도·약관 확인, 실패 처리. 실수집/가상 구분 표시.
- 공공 API 키는 승인이 오래 걸리니 **일찍 신청**.

## 6. 승인·권한·보안(절대 규칙)
- 일정 수정·메시지 발송 등 실제로 바꾸는 일은 **사람이 승인한 뒤에만**. 관리자도 승인 건너뛰기 금지.
- 사용자는 **내 데이터만**. 권한 검사는 화면뿐 아니라 서버·DB에서도.
- **비밀키·비밀번호·인터뷰 대상 신원을 저장소, 화면, 로그, vibelog, 슬랙, 발표 자료에 올리지 않는다.** 키는 서버 환경변수에만.
- 팀 저장소는 **비공개 유지**. 팀원 전원 + 강사를 collaborator로 초대하고 수락 확인.
- 개인정보·개인 연락처는 제출 문서에서 가린다. 위키에도 넣지 않는다.
- 외부 일정 만들기·알림 발송은 대상·내용 확인 후, 수업에서는 **테스트 자료만**.

## 7. 협업(GitHub) 규칙
- 한 명이 뼈대를 main에 올리고 팀원을 초대 → 모두 README대로 실행해 본다.
- `docs/plan.md` 조각 표(조각, 담당, 브랜치, 끝났다는 기준). 조각 = 한 사람이 한 브랜치에서 **하루 안에** 끝낼 크기.
- **main에 바로 푸시하지 않는다.** 브랜치 → PR(설명에 "어느 문서의 어느 요구"를 한 줄) → **팀원 리뷰 1명 이상** → 합치기.
- **모든 팀원이 PR 1개 이상 + 리뷰 1개 이상.**
- 충돌은 혼자 지우지 않고 그 코드를 쓴 팀원과 같이 푼다. 합친 뒤에는 최신 main을 받는다. 오류는 `docs/debug-note.md`.
- 같은 파일을 두 사람이 동시에 고치지 않는다.

## 8. 하네스·AI 사용 규칙
- 팀 `CLAUDE.md`: 작업 전 읽을 문서, 고칠 범위, 승인 규칙, 검사 방법. "요구마다 어느 문서에서 왔는지 적는다" 포함.
- 서브에이전트는 `docs/agents.md`에 (역할, 맡긴 일, 받은 결과, 사람이 확인한 것, 잘 안 된 점, 근거) 기록. **만드는 쪽과 검토하는 쪽을 나눈다.** 결과를 확인 없이 합치지 않는다. 안 쓴 큰 일은 이유 한 줄.
- 커넥터는 **서로 다른 서비스 2개 이상을 실제로 사용**하고 `docs/connectors.md`에 기록(토큰 금지). 설치만 한 것은 사용이 아니다.
- 위키(`wiki/`): Claude가 정리, **원본 문서는 Claude가 읽기만**. 반영 전에 계획을 보여 주고 사람이 확인. 문서끼리 어긋나면 한쪽으로 정리하지 않고 `충돌`로 둘 다 적는다.
- 챗봇: 팀·관리자 전용, 서버에서 Claude API 호출(키는 강사 제공, 서버 환경변수), 질문 5개 정답표(위키에 있음 3 / 없음 1 / 어긋남 찾기 1) 결과를 `docs/wiki-chat.md`에.
- AI 결과를 사실처럼 쓰지 않는다. 인터뷰·통계·성과를 지어내지 않는다.

## 9. 기록·QA 규칙
- **vibelog: 각자 프로젝트 기간 내내 기록(의무).** 하루 끝에 날짜·제목·한 줄 메모·화면 하나. 막힌 일/푼 방법/정한 이유. 자동 기록도 읽고 내 판단을 덧붙인다.
- QA 상태는 **Pass / Fail / No Run** 3가지. 근거 없이 Pass 금지. 안 한 것은 No Run. Fail은 고친 뒤 재검사하고 전/후 증거를 남긴다.
- 정상 흐름 외에 변화 없음, 수집 실패, 승인 거절, 조치 실패, 권한 없는 접근, 같은 변경 두 번 입력(중복 방지)을 검사.
- 기여는 커밋 수가 아니라 한 일의 무게. GitHub에 안 남는 일(인터뷰 참여, 시나리오 작성, 팀원 도움)은 발표 기여 표에 적는다. **팀의 일을 혼자 한 것처럼 쓰지 않는다.**
