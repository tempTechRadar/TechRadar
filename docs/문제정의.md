## 1. 문제 한 문장

**AI 코딩 도구(Claude Code·Cursor·Codex 등)로 직접 무언가를 만드는 사람**(v1 대표: 바이브코딩 부트캠프 수강생)은 스킬·MCP·플러그인을 소식(쇼츠·유튜브)이나 그때그때의 필요로 하나씩 깔다 보니, **내가 무엇을 깔았는지, 그게 안전한지, 더 나은 것이 나왔는지를 한눈에 볼 수 없다.** 그래서 유명세만 보고 검증 안 된 도구를 쓰고, 컴퓨터를 바꿀 때는 쌓은 세팅을 옮기지 못해 처음부터 다시 쌓는다.

> **1차 목적 (2026-11-20, ADR 0028 확정):** 위 문제는 그대로 두고, 서비스의 1차 목적은 **날마다 쏟아지는 기술을 분야별로 한눈에 보고, 사용자가 스스로 판단해 내 프로젝트에 쓸지 정하게 돕는 것**으로 넓힌다. 보안 확인은 그 과정에서 곁들인다(지도 색이 아니라 기호). 화면 흐름은 탐색 → 이해 → 판단 → 기억(`docs/uj.md` 짧은 여정 C). **근거 구분:** 위 문제(목록·보안·변화)는 사람 인터뷰 근거가 있고(3절), 1차 목적을 넓힌 것은 팀원 한 명의 말과 팀 승인(ADR 0028)이다. 인터뷰로 새로 확인하지 않았다.
지금은 휴대폰 캡처, "생각나면 다시 보기", "유명한가"·사례 확인으로 버틴다.

## 2. 서비스가 하는 일

```
공개 저장소 등록 → 내 기술 목록 만들기 → 보안 점검(등급 + 쉬운 이유) → 기술 지도에 내 기술 표시
→ 기술 소식 수집 → 내 기술 목록과 맞춰 보기 → 알림 → 사용자 판단(적용 후보 / 보류) → 판단 저장(적용 후보 기록 / 보류 사유 기록, ADR 0010). 적용 시나리오는 요청할 때 만드는 참고 자료
```

| 단계 | v1에서 정한 것 |
|---|---|
| 내 프로젝트 | **공개 GitHub 저장소 주소만** 등록. `package.json`, `.mcp.json`, `.claude/skills/`를 읽어 **내 기술 목록**을 만든다(`requirements.txt`는 3순위, ADR 0020) (ADR 0002). 첫 화면은 **기술 지도**(회의 D8, IA-Q1)이고 내 기술 목록은 메뉴에서 연다 |
| 보안 점검 | 코드 규칙으로 **통과 / 주의 / 위험 / 찾지 못함**: 라이선스, 최근 활동, 알려진 취약점, 스킬·MCP 코드의 위험 패턴. 등급마다 **이유를 쉬운 말로** 붙인다(사용자가 지금은 유명세로 판단하므로). 커뮤니티 평판 요약·사고 제보는 v1에서 하지 않음 (ADR 0003 개정) |
| 기술 지도 | 2단계 분류 나무(ADR 0008) + 갈래를 가로지르는 연결선(v1은 **같은 역할** 하나, 나머지 종류는 다음 버전. GLOSSARY). **"내 기술이 어디에 있고 무엇과 같은 역할인가"를 먼저** 보여 주고, 생태계 전체는 그 둘레로 펼친다. 분류는 규칙 먼저, 애매하면 Claude API 제안, 확신 낮으면 관리자 확인 |
| 지켜볼 분야 | AI 코딩 도구 생태계: LLM 모델, Claude Code 확장(스킬·MCP·플러그인·훅), 하네스 패턴, 개발 도구 (ADR 0002) |
| 수집 출처 | 1순위: **OSV**(취약점), **공식 MCP 레지스트리**(새 서버), **GitHub 저장소 정보**(최근 활동·라이선스), **npm·PyPI 다운로드 수**(사용량). 3순위: Hugging Face, Hacker News, Firecrawl로 skills.sh 1곳(`docs/spec.md` 8절, ADR 0008). 처음 후보 목록은 `docs/data-sources.md`이고, 그 밖의 후보(deps.dev, GitHub Advisories, GeekNews, OpenAI 뉴스 등)는 v1에서 쓰지 않는다 |
| 알림 (2종류) | **보안 경고:** 내 기술 목록의 기술이 "위험"으로 바뀜 / **적용 기회:** 새 기술이 내 기술과 같은 역할임("프로젝트 목표와 맞음"은 v1에서 하지 않음, prd 5-2). 둘 다 바깥 변화로 생긴다 |
| 사용자 판단 | **적용 후보** → 판단 기록(보안 경고에서는 "고친 버전으로 올리기", ADR 0012). 적용 시나리오(비교표, 적용 단계, 위험과 되돌리기)는 **요청할 때만** 만드는 참고 자료(ADR 0010) / **보류** → 이유 기록, 비슷한 기술이 나오면 과거 판단을 함께 보여 줌 |
| 규칙 [팀원] | 모든 추천·비교에 출처 링크. 출처가 없으면 "찾지 못함" (v5) |
| 도구 정보 (후보) | 무료/유료 표시(MCP 없이 유료 API뿐인지) — [대표1] |

**가장 가까운 기존 서비스 Glama(MCP 목록)와 다른 점:** Glama는 MCP 서버마다 보안·라이선스·품질 등급을 공개 신호로 매긴다. 우리는 **내 목록을 기준으로** 바뀐 것을 알리고, 판단을 기록하고, 다른 컴퓨터로 옮길 프롬프트를 만든다(2026-11-17 추가, 출처: glama.ai/mcp).

**Claude에게 "찾아봐"라고 시키기와 다른 점:** 묻지 않아도 내 기술에 맞는 변화가 생기면 먼저 알린다 / 보안 등급과 이유가 있다 / 내 기술 목록과 판단 기록이 쌓인다. (팀 밖 인터뷰에서 Q5를 묻지 못해 아직 확인 전)

## 3. 어떻게 여기에 왔나

### 판정: 가설과 인터뷰를 하나로 (2026-11-17)
처음 세운 가설 A(소식 지켜보기, [우리])·B(필요 → 검색·추천, [팀원] v5)·C(둘을 합친 안, ADR 0005)를 주장 단위로 쪼개, 팀 밖 사람 인터뷰에서 나온 말과 나란히 놓고 하나씩 판정했다.
**규칙:** 팀 밖 사람 **2명 이상**에게서 나온 주장을 중심에 둔다. 팀원 본인(인터뷰 A)과 AI 인터뷰는 세지 않는다. **한계:** 그룹1은 전사 끝부분만 있고 발화자는 추정 · 초심자 근거는 그룹1뿐 · 대표1은 숙련자이고 주제를 미리 알았으며 전사에 "일부러 삐딱하게 답변"이 있다.

|---|---|---|---|---|---|

**한 줄 결론:** 가설 A의 "보안·큰 그림"과 C의 "공개 저장소 등록"은 남기고, 큰 그림을 **"내가 깐 것"**으로 좁혀 중심에 둔다. B의 "몰라서 포기"는 팀 밖 근거가 없어 보조로 내린다. 이것이 1절의 문제 한 문장이다. (v5 중단 기준 중 "팀 밖 확인된 사람 3명 미만"은 3명(대표1, P1, P3 추정)이라 걸리지 않는다. "새 기능 10개 중 쓸 것 1개 미만", "출처 읽기·약관 불가"는 인터뷰로 판정하는 기준이 아니라 이번엔 점검하지 않았다.)

## 7. 잴 숫자

- **주 숫자 (회의 D4에서 확정):** 내 기술 목록 가운데 **보안 등급과 이유를 확인한 기술의 비율.** 지금 값은 [대표1] 기준 "확인 안 함(유명세만)". 앱에서는 등록한 저장소의 기술 수 대비 등급을 열어 본 수로 잰다.
- **보조 숫자:** 알림 받은 시각부터 판단(적용 후보 / 보류)까지 걸린 시간. 원래 주 숫자였으나 인터뷰에서 지금 값을 얻지 못했다([대표1]: 필요하면 "바로", 아니면 "생각나면 다시").
- **보조 숫자:** 설치 전에 보안을 확인한 비율.

## 8. 강사 피드백

사용자 인터뷰 근거가 아니라 **평가자 요구·제안**으로 읽는다. 날짜마다 따로 적고, 승인된 결정과 섞지 않는다.

## 11. 열린 질문 (다음에 정함)

- **발표에서 설명할 연결 (2026-11-18 안내서 재검토):** 안내서는 "[무엇이 바뀐 것]을 늦게 알아서"(552줄), "'무엇이 바뀌었을 때' 생기는 문제인가"(834줄)를 본다. 우리 인터뷰의 가장 강한 근거는 "깐 것 목록이 없어 옮기기 막막하다"로, **목록이 없는 문제**에 가깝다. 연결: 목록이 없으니 그 목록 위의 기술이 **바뀌어도(위험해져도) 알 길이 없다** → 목록을 만들고(내 기술 목록), 바뀌면 알리고(보안 경고), 옮길 수 있게 한다(설치 프롬프트). 보안 상태가 바뀌어 실제로 손해 본 장면은 팀 밖 인터뷰에 없다는 한계(6절)는 그대로 말한다
