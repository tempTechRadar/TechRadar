## 두 가설과 합친 안

### 가설 A — 소식 지켜보기형 [우리]

**AI 코딩 도구로 직접 무언가를 만드는 사람**(v1 대표: 바이브코딩 부트캠프 수강생)은, 매일 쏟아지는 LLM·스킬·MCP·플러그인·하네스 소식 가운데 **무엇이 내 프로젝트에 필요하고 안전한지** 판단할 기준과 큰 그림이 없어서, **검증 안 된 도구를 깔아 보안 위험과 시간 낭비를 겪거나, 필요한 것을 늦게 알아 덜 좋은 방법으로 버틴다.**
지금은 [아직 모름 → 인터뷰로 확인: 유튜브·GeekNews·지인 추천을 보고 바로 설치? 북마크만?]으로 버틴다.

### 가설 B — 필요 → 검색·추천형 [팀원]

**실전 프로젝트 단계의 비전공 초심자**는 작업이 느리거나, 막히거나, 결과물이 마음에 안 드는 순간에 **"분명히 있을 텐데" 싶은 기능의 이름과 위치를 몰라서**, 검색하고 기다리는 데 시간을 쓰거나 원하는 결과물을 포기한다.
지금은 Claude Code에 "이 작업에 도움이 되는 스킬이 있는지 GitHub나 웹검색으로 찾아봐"라고 시켜서 버틴다. (인터뷰 A)

- **계기:** 새 소식이 아니라 작업 중 막힘·불만
- **손해:** 검색 시간 + 기다린 시간 + 결과물 포기 (인터뷰 A 장면 ②: 업무 마인드맵을 만들고 싶었지만 방법을 몰라 포기, 나중에 알고 "그때 알았으면")
- **사건 후보:** ⓐ 새로 나온 도구가 내 필요에 맞음 / ⓑ 원래 있었지만 내가 처음 발견한 도구가 내 필요에 맞음
- **가장 큰 경쟁 상대:** Claude 자신에게 찾아 달라고 시키기
- **방향:** 검색·추천형 (팀원 결정, 팀 의논 대기)

### 합친 안 C (제안, 팀 합의 전)

사용자는 **내 프로젝트(공개 저장소)**와 함께 **필요**(막혔거나 포기한 일을 한 문장으로)를 등록한다. 서비스는 소식을 지켜보다가 보안 점검을 통과한 기술이 그 필요나 프로젝트에 맞으면 알린다(B의 ⓐ). 필요를 처음 등록할 때는 이미 있는 도구 중에서도 찾아 준다(B의 ⓑ). 기술 지도는 "내 필요와 기술이 어떻게 이어지는지"를 보여 주는 화면이 된다.

| | 내용 |
|---|---|
| A에서 가져옴 | 소식 수집, 보안 점검, 기술 지도, 공개 저장소 등록, 판단(적용 후보 / 보류) |
| B에서 가져옴 | 필요 등록, 알림 ⓐⓑ, 초심자 대상, "Claude에게 찾아 달라고 시키기"와 다른 점 |
| 좋은 점 | 안내서의 "직접 입력 화면" 요건이 자연스럽게 채워진다. 알림 기준이 "내 필요"로 좁아져 알림 피로가 줄어든다 |
| 위험 | 범위가 넓어진다 → v1은 필요 등록 1종류 + 출처 2곳 + 알림 2종류로 제한한다 |
| Claude에게 시키기와 다른 점 (확인 필요) | 내가 묻지 않아도 맞는 것이 나오면 알려 줌, 보안 등급과 근거, 내 프로젝트·필요 기록이 쌓임 |

### 인터뷰로 판정하는 기준

| 인터뷰에서 이런 장면이 나오면 | 가리키는 쪽 |
|---|---|
| 작업하다 막혀서 도구를 찾았다 / 몰라서 포기했다 / "그때 알았으면" | B (C의 필요 등록) |
| 소식을 보고 깔았다 / 확인 없이 깔았다가 문제가 생겼다 / 저장해 두고 다시 못 찾는다 | A |
| "Claude에게 찾아 달라고 하면 충분하다" | B의 반대 근거 → C의 다른 점이 실제로 필요한지 확인 |
| "강사·CTO가 정해 줘서 충분하다" | A·B 모두의 반대 근거 → 대상 다시 보기 |
| "보안은 신경 안 쓴다" / "무엇을 볼지 모른다" | A의 보안 점검 비중 결정 |

**판정 규칙:** 팀 밖 사람 인터뷰 중 **2명 이상**에게서 같은 쪽 장면이 나오면 그쪽을 중심으로 C를 고친다. 결과가 갈리면 한쪽으로 정리하지 않고 둘 다 적은 채 C로 간다. 팀원 본인 인터뷰(인터뷰 A)는 판정 인원에 세지 않는다.

> 아래 "누구"부터 "근거 표"까지는 가설 A를 바탕으로 쓴 것이고, B에서 온 내용은 **[팀원]**으로 표시했다.

## 놓치면 잃는 것 (가설, 인터뷰로 확인)

- **안전:** 위험한 스킬·MCP를 확인 없이 설치 → 비밀값 유출, 의도치 않은 명령 실행
- **시간:** 비슷한 도구를 여러 개 깔아 보고 지우기를 반복 / 더 나은 도구가 나온 걸 늦게 알아 손으로 버팀
- **기회:** 내 프로젝트에 바로 쓸 수 있는 개선을 모르고 지나감
- **결과물 포기 [팀원]:** 있는 줄 몰라서 원하는 결과물(시각화, 영상, 디자인)을 만들지 못하고 끝냄 (인터뷰 A 장면 ①②)

## 서비스가 하는 일 (가설 A 상세, 합친 안 C의 바탕)

```
소식 감지 → 수집 → 보안 점검 → 분류해 지도에 배치 → 내 프로젝트와 맞춰 보기
→ 알림 → 사용자 판단(적용 후보 / 보류) → 적용 시나리오 제공 또는 보류 사유 기록
```

| 단계 | v1에서 정한 것 |
|---|---|
| 지켜볼 분야 | AI 코딩 도구 생태계: LLM 모델, Claude Code 확장(스킬·MCP·플러그인·훅), 하네스 패턴, 개발 도구 (ADR 0002) |
| 소식 출처 | 소식: GitHub 릴리스 피드, HF 블로그, OpenAI 뉴스, GeekNews / 인기: GitHub 검색, HF 인기 순위, HN 점수 / 레지스트리: 공식 MCP 레지스트리 / 보안: OSV, deps.dev, GitHub Advisories. 2순위: Anthropic 뉴스(크롤링). 전체 후보는 `docs/data-sources.md` |
| 보안 점검 | 코드 규칙으로 **통과 / 주의 / 위험**: 라이선스, 최근 활동, 알려진 취약점, 스킬·MCP 코드의 위험 패턴. 커뮤니티 평판 요약은 참고만, 보안 사고 제보는 "주의" (ADR 0003) |
| 기술 지도 | 깊이 제한 없는 분류 나무(마인드맵) + 갈래를 가로지르는 연결선(대체 · 함께 씀 · 의존 · 같은 역할). 분류는 규칙 먼저, 애매하면 Claude API 제안, 확신 낮으면 관리자 확인 |
| 내 프로젝트 | **공개 GitHub 저장소 주소만** 등록. `package.json`, `requirements.txt`, `CLAUDE.md`, `.mcp.json`, `.claude/skills/`를 읽음 (ADR 0002) |
| 알림 (2종류) | **적용 기회:** 새 기술이 내 프로젝트의 기술과 같은 역할이거나 목표 키워드와 맞음 / **보안 경고:** 내 프로젝트가 쓰는 기술이 "위험"으로 바뀜. 맞춰 보기를 통과한 사람에게만 보냄 |
| 사용자 판단 | **적용 후보** → Claude API가 근거와 함께 적용 시나리오(비교표, 적용 단계, 위험과 되돌리기) 생성·저장 / **보류** → 이유 기록, 비슷한 기술이 나오면 과거 판단을 함께 보여 줌. 누르기 전에는 아무것도 바꾸지 않음 |

## 근거 표 (사람 인터뷰 후 다시 채움)

AI 인터뷰(`interviews/*-AI.md`)는 가설이라 "확인한 근거"에 넣지 않고 "AI 인터뷰 가설" 칸에만 적는다.

| 주장이나 결정 | 확인한 근거 | AI 인터뷰 가설 | 한계와 반대 사례 | 이번에 만들 것 | 확인 방법 |
|---|---|---|---|---|---|
| 새 도구에 실제 보안 위험이 있다 | P1–P5 (실제 공격 사례와 검사 연구) | 수강생A가 토큰을 설정 파일에 그냥 붙여넣음, 대표C가 드라이브 전체 권한 MCP를 깔았다 지움 | 학술 연구 기준 문제 비율은 5~7%(P5), 업체 자료는 더 높음 | 보안 점검 + 등급 표시 | Q8 |
| 사용자는 무엇을 확인할지 몰라 확인 없이 설치한다 | P9 (81% 보안 걱정) — 설치 행동 자체의 근거는 아직 없음 | 세 명 모두 "공식" 표시·별 수·강사에 의존, 급하면 `npx -y` | 회사는 허용 목록으로 이미 관리(개발자B) | 등급의 "이유"를 쉬운 말로 | Q8, Q10 |
| 소식과 도구가 너무 빠르게 늘어난다 | P6, P7(2차), P8, P10 | 하루 15~30분, 주 2~3시간을 소식에 씀 | 사용자는 소수 인기 도구로 몰린다(P12) | 수집·분류 자동화 | Q6 |
