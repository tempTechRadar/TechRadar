## 두 가설과 합친 안

### 가설 A — 소식 지켜보기형 [우리]

**AI 코딩 도구로 직접 무언가를 만드는 사람**(v1 대표: 바이브코딩 부트캠프 수강생)은, 매일 쏟아지는 LLM·스킬·MCP·플러그인·하네스 소식 가운데 **무엇이 내 프로젝트에 필요하고 안전한지** 판단할 기준과 큰 그림이 없어서, **검증 안 된 도구를 깔아 보안 위험과 시간 낭비를 겪거나, 필요한 것을 늦게 알아 덜 좋은 방법으로 버틴다.**
지금은 [아직 모름 → 인터뷰로 확인: 유튜브·GeekNews·지인 추천을 보고 바로 설치? 북마크만?]으로 버틴다.

### 가설 B — 필요 → 검색·추천형 [팀원 v5]

**생성형 AI·LLM 실전 프로젝트를 하는 비전공 부트캠프 초심자**는 작업이 오래 걸리거나, 막히거나, 결과물이 마음에 안 드는 순간에 **"분명 쓸 수 있는 기능이 있을 텐데" 이름도 위치도 몰라서**, 검색에 시간을 쓰거나 원하는 결과물을 포기한다.
지금은 Claude Code에 "도움이 되는 스킬을 찾아봐"라고 시키기, 검색, 동기·강사에게 묻기로 버틴다. (v5 §1)

| 항목 | 내용 (v5 §2, §5) | 상태 |
|---|---|---|
| 누가 | 실전 프로젝트 단계(강사 개입이 줄어든 시기)의 비전공 초심자 | 가설 |
| 언제 | 작업 중 막힘·지연·결과물 불만의 순간(새 소식을 받는 순간이 아님) | 인터뷰 A |
| 잃는 것 | 검색 시간, 기다린 시간, 원하는 결과물을 만들지 못하고 포기 | 인터뷰 A(1명) |
| 사람이 입력 | "불편한 상황"을 자연어 문장으로 등록(기능 이름이 아님). 예: "기다리는 동안 다른 일을 하고 싶다" | 제안 |
| 지켜보기 | 서로 다른 공개 출처 2곳 이상에서 새 스킬·커넥터·플러그인 수집 | 제안 |
| 사건 | ⓐ 새로 나온 도구가 내 필요에 맞음 / ⓑ 이미 있었지만 내가 처음 발견한 도구가 내 필요에 맞음, 저장한 도구의 변경 | 제안 |
| 승인·조치 | "내 도구함에 추가할까요?" → 사용자가 승인해야 저장 | 제안 |
| 기록 | 어떤 도구를 왜 골랐는지 남기고, 비슷한 필요에서 과거 기록을 보여 줌 | 제안 |
| 규칙 | 모든 추천에 출처 링크. 출처가 없으면 "찾지 못함" | 제안 |
| 카테고리 | 과정 개선(효율·진단·병렬) / 결과 개선(피드백·표현·시각화). 근거가 가장 강한 쪽은 **결과 개선(표현·시각화)** | 인터뷰 A |
| 가장 큰 경쟁 상대 | Claude 자신("스킬 찾아봐"로 이미 해결될 수 있음) | 반대 근거 |

**v5의 반대 근거 (꼭 유지, v5 §4):** 프로젝트는 쓸 도구가 정해져 있는 경우가 많아 새 도구를 찾을 이유가 적을 수 있다 / 호기심이 높은 사용자는 스스로 찾아 우리 가치가 적을 수 있다 / 숙련되면 가치가 줄어든다(초반 초심자에게 가장 큼).

### 합친 안 C (제안, 팀 합의 전)

사용자는 **내 프로젝트(공개 저장소)**와 함께 **필요**(막혔거나 포기한 일을 한 문장으로)를 등록한다. 서비스는 소식을 지켜보다가 보안 점검을 통과한 기술이 그 필요나 프로젝트에 맞으면 알린다(B의 ⓐ). 필요를 처음 등록할 때는 이미 있는 도구 중에서도 찾아 준다(B의 ⓑ). 기술 지도는 "내 필요와 기술이 어떻게 이어지는지"를 보여 주는 화면이 된다.

| | 내용 |
|---|---|
| A에서 가져옴 | 소식 수집, 보안 점검, 기술 지도, 공개 저장소 등록, 판단(적용 후보 / 보류) |
| B(v5)에서 가져옴 | 필요 등록(자연어 문장), 알림 ⓐⓑ, 초심자 대상, 모든 추천에 출처·없으면 "찾지 못함", 결과 개선(표현·시각화) 카테고리 우선, "Claude에게 찾아 달라고 시키기"와 다른 점 |
| 좋은 점 | 안내서의 "직접 입력 화면" 요건이 자연스럽게 채워진다. 알림 기준이 "내 필요"로 좁아져 알림 피로가 줄어든다 |
| 위험 | 범위가 넓어진다 → v1은 필요 등록 1종류 + 출처 2곳 + 알림 2종류로 제한한다 |
| Claude에게 시키기와 다른 점 (확인 필요) | 내가 묻지 않아도 맞는 것이 나오면 알려 줌, 보안 등급과 근거, 내 프로젝트·필요 기록이 쌓임 |

### 인터뷰로 판정하는 기준

| 인터뷰에서 이런 장면이 나오면 | 가리키는 쪽 |
|---|---|
| 작업하다 막혀서 도구를 찾았다 / 몰라서 포기했다 / "그때 알았으면" | B (C의 필요 등록) |
| 소식을 보고 깔았다 / 확인 없이 깔았다가 문제가 생겼다 / 저장해 두고 다시 못 찾는다 | A |
| "Claude에게 찾아 달라고 하면 충분하다" | B의 반대 근거 → C의 다른 점이 실제로 필요한지 확인 |
| "강사·CTO가 정해 줘서 충분하다" | A·B 모두의 반대 근거 → 대상 다시 보기 |
| "보안은 신경 안 쓴다" / "무엇을 볼지 모른다" | A의 보안 점검 비중 결정 |
| 종류(스킬·MCP·플러그인) 차이를 몰라 막혔다 / 같은 역할인 줄 몰라 둘 다 깔았다 / 직접 정리표·그림을 만들었거나 정리 글을 찾아봤다 (M1–M4) | 기술 지도가 필요함 (A·C) |
| "지금 필요한 것 하나만 알면 된다" / 정리하다 금방 그만뒀다 (M3, Q13) | 지도의 반대 근거 → 지도를 C의 중심에서 보조 화면으로 내릴지 검토 |

**판정 규칙:** 팀 밖 사람 인터뷰 중 **2명 이상**에게서 같은 쪽 장면이 나오면 그쪽을 중심으로 C를 고친다. 결과가 갈리면 한쪽으로 정리하지 않고 둘 다 적은 채 C로 간다. 팀원 본인 인터뷰(인터뷰 A)는 판정 인원에 세지 않는다.

**중단·변경 기준 [팀원 v5 §8, 레드팀]:** 판정 규칙과 함께 쓴다.
- 인터뷰 5명 중 구체 사례 **2명 미만** → 사용자 그룹·문제 재정의
- 새 기능 10개 중 "쓸 것" 평균 **1개 미만** → 알림 기준을 "내 프로젝트 주제에 맞는 것"으로 좁힘
- 팀 밖 확인된 사람 **3명 미만** → 사용자 범위 확대 검토
- 출처 2곳 중 한 곳이라도 읽기·약관 불가 → 수집 계획 재설계

### 후보 비교 (안내서 5장의 6질문, 2026-11-17)

답은 **예 / 아니오 / 아직 모름**과 이유. "아직 모름"은 AI가 추측하지 않고 확인할 방법(인터뷰 질문 번호, 샘플 수집)을 적었다. 근거가 AI 인터뷰뿐인 칸은 "아직 모름"으로 둔다.

| 질문 | 가설 A 소식 지켜보기 | 가설 B 필요 → 추천 (v5) | 합친 안 C |
|---|---|---|---|
| 1. 실제로 물어볼 사용자가 떠오르나? | **예.** 부트캠프 수강생, 스타트업 대표를 섭외해 둠(인터뷰 계획) | **예.** 비전공 수강생. 인터뷰 A가 이미 있음 | **예.** A·B와 같은 사람들 |
| 2. 무엇을 놓쳐 어떤 손해를 보는지 구체적인가? | **아직 모름.** 보안 위험 자체는 공개 근거로 확인(P1–P5)했지만, 우리 사용자가 실제로 손해를 봤다는 말은 AI 인터뷰(가설)뿐 → Q8, Q9 | **예(힌트 수준).** 업무 마인드맵을 몰라서 포기, 발표 영상 품질 미달(인터뷰 A, 팀원 본인 n=1) → 팀 밖 확인 Q3, Q4 | **아직 모름.** A·B 중 확인되는 쪽의 손해를 따름 |
| 3. 변경 전후를 비교할 자료를 실제로 한 건 구했나? | **예.** 같은 출처를 13시간 간격으로 두 번 수집해 비교함(`watch/samples/README.md`): Claude Code 새 릴리스 1건, MCP 레지스트리 새 서버 85·사용 중단 7·삭제 8, 첫 페이지는 변화 없음 | ⓐ는 A와 같은 자료. **ⓑ는 아니오.** "필요 ↔ 기존 도구" 맞춤은 바뀐 것이 아니라 검색이라, 비교할 전후 자료가 없음 | **예.** A와 같은 자료 |
| 4. 발견하면 사용자가 할 행동과 승인할 대상이 있나? | **예.** 설치 전에 "적용 후보 / 보류"를 판단하고 적용 시나리오 저장. 보안 등급이 있어 승인할 이유가 분명함 | **예, 다만 약함.** "내 도구함에 추가" 승인. 안내서는 "승인이 필요한 이유가 없는 주제에 승인 버튼만 붙이지 않는다"고 함 → 추가만으로는 승인 이유가 약함 | **예.** 판단 + 보안 등급 + 적용 시나리오 |
| 5. "변화 없음"과 "사건 발생"을 가짜 데이터로 각각 보일 수 있나? | **예.** 같은 릴리스를 다시 읽으면 변화 없음, 새 릴리스가 내 프로젝트와 맞으면 적용 기회, 내 의존성에 새 취약점(OSV)이 뜨면 보안 경고 | ⓐ는 **예.** ⓑ는 **애매.** 이미 있던 도구를 처음 찾는 것은 바깥 변화가 아니라서, "무엇이 바뀌었을 때 생기는 문제"라는 안내서 기준에 맞추기 어려움 | **예.** ⓐ(새 도구가 내 필요·프로젝트에 맞음) + 보안 경고 |
| 6. 기간(11/23) 안에 한 흐름을 끝까지 만들 수 있나? | **아직 모름.** 보안 점검·지도·프로젝트 맞춤까지 하면 범위가 큼. 출처 1곳, 알림 1종류로 시작하면 가능해 보임 | **아직 모름.** 필요 문장과 도구를 맞추는 일(Claude API)의 정확도를 정답표로 채점해야 하는데, 정답표를 만드는 데 시간이 듦 | **아직 모름.** 범위가 가장 큼. v1은 필요 1종류 + 출처 2곳 + 알림 2종류로 제한해야 함 |

**지금까지 보이는 것 (팀 결정 전, 인터뷰로 바뀔 수 있음)**
- C가 6질문에서 가장 덜 막힌다. 다만 "손해(2번)"와 "기간(6번)"은 셋 다 아직 모름이다.
- B의 **ⓑ "이미 있던 도구 발견"은 바깥 변화가 아니라서 사건으로 쓰기 어렵다.** 대신 필요를 처음 등록할 때 보여 주는 **검색 기능**으로 두고, 사건은 ⓐ와 보안 경고 두 종류로 하는 방법이 있다. (팀 제안, 결정 전)
- A의 보안 점검은 "왜 사람이 승인해야 하는지"를 가장 분명하게 만든다(4번). B만으로는 승인 이유가 약하다.
- 3번은 두 번째 수집(2026-11-17)으로 A·C가 "예"가 됐다. 13시간 동안 레지스트리에서만 100건 넘게 바뀌어, 알림을 "내 것에 맞는 것"으로 좁혀야 한다는 근거도 생겼다(v5의 소음 걱정과 같은 방향).

| **v1 대표 사용자** | 바이브코딩 수강생 (초·중급) | 직접 설치하고 반복하며, 판단 기준이 약함. 인터뷰 가능 |
| v1 대표 사용자 후보 [팀원] | 실전 프로젝트 단계의 **비전공** 초심자 | 이름을 몰라 못 찾는 문제가 가장 크게 보임(인터뷰 A). 숙련되면 가치가 줄 수 있음 |
| 비교 사용자 | 스타트업 대표 | 팀 단위 도입 판단 관점, 반대 근거 확보. 인터뷰 가능 |

## 놓치면 잃는 것 (가설, 인터뷰로 확인)

- **안전:** 위험한 스킬·MCP를 확인 없이 설치 → 비밀값 유출, 의도치 않은 명령 실행
- **시간:** 비슷한 도구를 여러 개 깔아 보고 지우기를 반복 / 더 나은 도구가 나온 걸 늦게 알아 손으로 버팀
- **기회:** 내 프로젝트에 바로 쓸 수 있는 개선을 모르고 지나감
- **결과물 포기 [팀원]:** 있는 줄 몰라서 원하는 결과물(시각화, 영상, 디자인)을 만들지 못하고 끝냄 (인터뷰 A 장면 ①②)

## 서비스가 하는 일 (가설 A 상세, 합친 안 C의 바탕)

```
소식 감지 → 수집 → 보안 점검 → 분류해 지도에 배치 → 내 프로젝트와 맞춰 보기
→ 알림 → 사용자 판단(적용 후보 / 보류) → 적용 시나리오 제공 또는 보류 사유 기록
```

|---|---|

## 강사 피드백 (주제 컨펌, 2026-11-16 오전)

주제·페인포인트·사용할 API를 설명하고 **주제 확정 허가**를 받았다. 아래는 그때 들은 말을 팀원이 옮겨 적은 것(당사자 말, 녹음 아님, 2026-11-17 기록)이다. 사용자 인터뷰 근거가 아니라 **평가자 요구**로 읽는다.

| 강사 말 | 이 문서에서 닿는 곳 | 아직 정할 것 |
|---|---|---|
| 기술을 누적해서 보여 주는 데서 그치면 안 된다 | 가설 A·C의 "판단 도움". v5가 접은 "뉴스형"과 같은 경계 | 지도에 "쌓인 것"이 아니라 "판단 근거"가 보이는 화면 구성 → IA |
| 위험·보안 요소를 판단해 줘야 한다 | 보안 점검(통과 / 주의 / 위험, ADR 0003), 알림 "보안 경고" | 없음. 이미 있는 방향을 확인받음 |
| 비슷한 기능의 기존 기술과 비교해 우위를 따질 근거를 제시해야 한다 | 근거 표 "비슷한 도구 중 고르기가 어렵다"(Q10), 적용 시나리오의 비교표, B의 ⓑ(이미 있는 도구 찾기) | 비교 기준(관리 상태, 보안 등급, 같은 역할, 인기)을 무엇으로 할지 → PRD |
| 정보를 빨리 불러오고 지도를 빨리 펼쳐 주는 것이 중요해 보인다 | 지도 화면 | 성능 기준을 숫자로(예: 지도 첫 화면 몇 초 안) → PRD 비기능 요구 |
