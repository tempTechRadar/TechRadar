## 1부. 팀 토론 (20분)

**토론 규칙 (안내서 5장):** 모르는 것은 "아직 모름"이라고 적는다. 답이 "아마도"로 끝나면 **누가 언제 확인할지** 정하고 넘어간다. 팀원의 답이 서로 다르면 하나로 고르지 말고 **둘 다** 적는다.

"문서에 이미 있는 것" 칸은 Claude가 문서에서 옮겨 둔 **참고**다. 팀의 답이 아니다. 팀이 말로 확인하거나 바로잡은 뒤 "팀 답" 칸에 적는다.

### 1. 누구의 문제인가
| 질문 | 문서에 이미 있는 것 (참고) | 팀 답 | 다른 의견 | 아마도 → 누가·언제 확인 |
|---|---|---|---|---|
| 우리 각자 아는 사람 중에 이런 일로 불평한 사람이 있나요? | 그룹1 4명, 대표1 (`interviews/2026-11-17-*`) | | | |
| 그 사람은 지금 이 문제를 어떻게 버티고 있나요? | 캡처 → 생각나면 다시 봄, 유명세·사례 확인, 막히면 검색 (문제정의 1절) | | | |
| 그 사람을 이번 주 안에 만나서 물어볼 수 있나요? | 그룹1은 노트북 반납 뒤 다시 묻기로 함(6절 확인 방법) | | | |

### 2. 놓치면 무엇을 잃나
| 질문 | 문서에 이미 있는 것 (참고) | 팀 답 | 다른 의견 | 아마도 → 누가·언제 확인 |
|---|---|---|---|---|
| 잃는 것은 돈, 시간, 기회 중 어느 쪽인가요? | 쌓은 세팅(시간), 안전(보안 사고), 더 나은 기술(기회, 가설) (5절) | | | |
| 지난 한 달에 실제로 몇 번 놓쳤나요? 숫자로 말할 수 있나요? | **없음.** 빈도(Q14)를 인터뷰에서 얻지 못함 (11절) | | | |
| 늦게 알았을 때와 일찍 알았을 때 결과가 어떻게 달라지나요? | 보안: 깐 뒤 업데이트가 악성이 된 사례(P2). 사용자 말은 없음 | | | |

### 3. 무엇을 어디서 지켜보나
| 질문 | 문서에 이미 있는 것 (참고) | 팀 답 | 다른 의견 | 아마도 → 누가·언제 확인 |
|---|---|---|---|---|
| 바뀌는 것이 어디에 공개돼 있나요? | GitHub 릴리스, MCP 레지스트리, OSV 등 (2절, `docs/data-sources.md`) | | | |
| 오늘 샘플 한 건을 직접 저장해 볼 수 있나요? | 저장함: `watch/samples/` (13시간 간격 두 번) | | | |
| 그곳은 얼마나 자주 바뀌나요? 얼마 간격으로 확인해야 하나요? | 레지스트리 13시간에 100건 넘게(P13), Claude Code 릴리스 주 약 5.5개(P6). **확인 간격은 아직 안 정함** | | | |
| 그 사이트의 이용 약관과 robots 안내를 읽어 봤나요? | `docs/data-sources.md`에 후보별 정리 (간격·실패 처리는 미정) | | | |

### 4. 무엇을 사건으로 보나
| 질문 | 문서에 이미 있는 것 (참고) | 팀 답 | 다른 의견 | 아마도 → 누가·언제 확인 |
|---|---|---|---|---|
| '바뀌었다'를 숫자나 문구로 어떻게 적을까요? | 보안 경고: 내 기술이 "위험"으로 바뀜 / 적용 기회: 같은 역할의 새 기술. **숫자 기준은 아직 없음** (11절) | | | |
| 사건이 너무 자주 나오면 사용자가 알림을 꺼 버릴 텐데 기준을 어디에 둘까요? | "내 기술 목록에 맞는 것만" (v5의 소음 걱정과 같은 방향) | | | |
| 사건이 아닌 것을 가짜 데이터로 어떻게 보여 줄까요? | 같은 릴리스를 다시 읽으면 변화 없음 (3절 5번) | | | |

### 5. 사람이 무엇을 승인하나
| 질문 | 문서에 이미 있는 것 (참고) | 팀 답 | 다른 의견 | 아마도 → 누가·언제 확인 |
|---|---|---|---|---|
| 알림을 받은 사람이 실제로 할 행동은 무엇인가요? | 판단: 적용 후보 / 보류 | | | |
| AI가 혼자 해도 되는 일과 사람이 꼭 눌러야 하는 일의 경계는 어디인가요? | AI: 분류 제안, 적용 시나리오 초안. 사람: 판단. 대신 설치는 안 함 (9절, 불변 규칙 1) | | | |
| 승인한 결과를 어디에 저장하고 어떻게 보여 줄까요? | 적용 시나리오 또는 보류 사유 기록, 비슷한 기술이 나오면 과거 판단을 함께 보여 줌 (2절) | | | |

| 우리만의 알파는 무엇이고 그것이 문제를 더 잘 풀어 주나요? | 후보 ⓐ–ⓒ (6절), 아래 2부에서 정함 | | | |

## 2부. 정할 것 (20분)

추천은 Claude의 제안이다. 팀이 다르게 정하면 "정한 것"에 이유와 함께 적는다.

| # | 정할 것 | 선택지 | 추천과 이유 | 정한 것 · 이유 |
|---|---|---|---|---|
| D1 | 통합안(`docs/문제정의.md`) 승인 | 승인 / 고쳐서 승인 / 보류 | **고칠 곳만 적고 승인.** 발표까지 6일이라 IA로 넘어가야 함. 그룹1 발화자 확인은 승인을 막지 않음(한계로 이미 적혀 있음) | |
| D2 | 알파 | ⓐ 목록 내보내기 = **노션 데이터베이스로 보내기**(11-17 prd 인터뷰에서 구체화) / ⓑ 무료·유료 표시 / ⓒ 비슷한 사람이 쓰는 기술 | **ⓐ(노션으로 보내기).** 팀 밖 2명의 말(노트북 반납 전 정리)이 근거. 안내서 알파 예시("외부 캘린더 반영")와 같은 모양. 사용자가 버튼을 누르고 미리보기를 확인한 뒤에만 보냄(불변 1). 노션 로그인(Supabase Auth)과 한 묶음이라 ⓐ가 아니면 노션 연동도 다시 정함(`docs/prd.md`, ADR 0007). ⓒ는 권한 규칙과 부딪힘 | |
| D3 | 만드는 순서 (6절 우선순위) | 그대로 / 바꿈 | **그대로.** 내 기술 목록 → 보안 등급 → 보안 경고 → 적용 기회 → 지도. 근거가 많은 것부터. 단 D8을 받아들이면 지도만 앞으로 옴 | |
| D4 | 잴 숫자 하나 | 등급과 이유를 확인한 기술의 비율 / 알림부터 판단까지 시간 / 필요한 도구를 찾기까지 시간(v5) | **등급과 이유를 확인한 기술의 비율.** 지금 값("확인 안 함")이 인터뷰에 있고, 앱에서 바로 잴 수 있음 | |
| D5 | v5 원본(`docs/문제정의-차세일-v5.md`) | 그대로 / 맨 위에 "통합본으로 대체됨" 표시 / 삭제 | **표시만 추가.** 원본은 과정 기록이라 남김. 표시는 작성자가 직접 | |
| D6 | 가입 때 취향 조사 → **추천** (필요 등록에서 바뀜, 11-17 데이터설계 인터뷰) | 가입 질문 3개 + "추천" 목록(알림·판단과 따로, 3순위) / v1에서 뺌 | **넣되 3순위.** 팀원 의견으로 다시 올림. 단 팀 밖 인터뷰 근거는 0명(문제정의 3·10절)이라 핵심 길(등록→목록→등급→경고→판단→기록)과 알파 다음에 만든다. 추천은 바깥 변화가 아니라 사건·알림이 아님(문제정의 9절). 근거는 HN·HF·GitHub 인기 신호 | |
| D7 | 사용자 결정의 용어 | 판단 / 도구함에 추가 | **판단.** 적용 후보 / 보류 둘 다 담음 | |
| D8 | 로그인 뒤 첫 화면 (11-17 IA 인터뷰에서 나옴, `docs/ia.md` IA-Q1) | 기술 지도 / 대시보드 / 내 기술 목록 | **기술 지도, 대신 작게(내 기술 + 같은 역할 한 단계).** IA 인터뷰에서 팀원 1명이 답한 것. 강사 11-16 피드백 "지도가 빨리 펼쳐져야 함"과 맞음. 그러면 D3의 지도 순서가 마지막에서 앞으로 와야 하고, 근거가 가장 약한 화면(문제정의 6절)을 먼저 만드는 셈이라 팀이 함께 정해야 함 | |
