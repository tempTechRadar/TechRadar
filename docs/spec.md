## 1. 보안 등급 규칙 (SPEC-1, 규칙 버전 v1)

**위에서부터 먼저 걸리는 등급을 매긴다.** 같은 입력에는 늘 같은 등급이 나온다(ADR 0003). 등급마다 "쉬운 이유"와 근거 링크(어느 취약점, 어느 파일 몇째 줄)를 붙인다.

| 등급 | 조건 (하나라도 맞으면) | 쉬운 이유 예 |
|---|---|---|
| **위험** | ① 지금 쓰는 버전에 OSV 심각도 **HIGH·CRITICAL** 취약점이 있고, 그 버전이 고친 버전보다 낮음 ② 위험 패턴 P1(원격 실행)을 찾음, 또는 P2(비밀값 밖으로 보냄)의 가까운 짝(읽는 곳과 15줄 안)을 찾음 | "이 버전에는 다른 프로그램이 내 컴퓨터에서 명령을 실행할 수 있는 알려진 문제가 있어요(CVE-2025-6514). 0.1.16 이상으로 올리면 고쳐져요" |
| **주의** | ① OSV 심각도 **MODERATE·LOW** 취약점 ② 12개월 넘게 커밋·릴리스 없음 ③ 라이선스 없음 ④ 출처에서 **중단**·**사라짐**(데이터설계 8절) ⑤ 위험 패턴 P3(넓은 권한), 또는 P2의 먼 짝(같은 파일에 읽는 곳과 보내는 곳이 있지만 15줄보다 멀 때) | "1년 넘게 고쳐지지 않았어요. 문제가 생겨도 고쳐 줄 사람이 없을 수 있어요" |
| **통과** | 위에 해당하지 않고, **OSV 조회와 저장소 정보 확인을 실제로 마침** | "알려진 문제가 없고, 최근 3개월 안에 고쳐지고 있어요" |
| **찾지 못함** | 근거를 하나도 확인하지 못함(이름만 직접 추가, 패키지가 없는 스킬인데 파일을 못 읽음 등) | "확인할 수 있는 자료를 찾지 못했어요" |

- 심각도는 **OSV가 주는 값을 그대로** 쓴다. 팀이 판단하지 않는다.
- 버전을 모르면(설정에 버전이 없음) 그 패키지에 HIGH·CRITICAL이 하나라도 **아직 열려 있으면 위험**, 모두 고쳐졌으면 **주의**("버전을 확인할 수 없어요, 최신으로 쓰세요")로 본다.
- 수집에 실패하면 등급을 바꾸지 않고, 등급 옆에 **"수집 오류 (마지막 확인 {날짜})"**를 함께 보여 준다. "마지막 확인 성공 시각"은 상태와 따로 저장한다(불변 2). 예전 "통과"가 확인 없이 그대로 보이지 않게 한다.
- **개념**(하네스 등)에는 등급이 없다.
- **고친 버전**(보안 경고의 "고친 버전으로 올리기", ADR 0012): 지금 버전의 HIGH·CRITICAL 문제를 **모두** 고치는 가장 낮은 버전이다. 문제마다 내 버전보다 높은 가장 낮은 고친 버전(백포트 줄 포함)을 고르고 그중 가장 높은 것. 하나라도 고친 버전이 없으면 "아직 고친 버전이 없어요". 첫 문제의 고친 버전만 보면 올린 뒤에도 위험이 남는다(G2·G4).

## 2. 위험 패턴 (SPEC-2, v1)

스킬 폴더의 파일(`SKILL.md`, 스크립트)과 MCP 저장소의 코드에서 **문구로 찾는다**. 찾으면 파일과 줄 번호를 이유로 보여 준다.

| ID | 이름 | 찾는 것 (예) | 등급 |
|---|---|---|---|
| P1 | 원격 실행 | `curl … \| sh`, `curl … \| bash`, `wget … \| sh`, `iex (iwr …)`, 내려받은 글을 `eval`·`exec`로 바로 실행 | 위험 |
| P2 | 비밀값 밖으로 보내기 | `.env`, `~/.ssh`, `id_rsa`, `API_KEY`·`TOKEN`·`SECRET`을 읽는 코드와 바깥 주소로 보내는 코드(`fetch`·`curl -d`·`requests.post`)가 **15줄 안**에 함께 있음(같은 파일이라는 이유만으로는 '위험'으로 걸지 않는다. 멀면 '주의'). 또는 지시문에 "키·토큰·.env 내용을 (주소)로 보내라" | 위험(15줄 안), 주의(같은 파일에 있지만 더 멀 때) |
| P3 | 넓은 권한 | 모든 셸 명령 허용(`Bash(*)`, `allowed-tools` 전체), 홈 폴더 전체 읽기·쓰기 | 주의 |

- **한계(화면에 적는다):** "검사가 찾은 것만 표시해요. 찾지 못했다고 안전하다는 뜻은 아니에요." 문구 찾기는 돌려 쓴 코드를 놓칠 수 있다.
- **v1 구현이 아직 못 찾는 것(P-10):** 비밀값을 GET 주소에 붙여 보내기, `session.post`처럼 다른 이름의 요청 객체, 문장으로 쓴 "키·토큰을 (주소)로 보내라"(P2 둘째 줄), `allowed-tools`를 여러 줄 목록으로 적은 것. 이름만 비슷한 `MAX_TOKENS`는 비밀값을 읽는 것이 아니다(환경변수를 읽는 모양일 때만 이름을 본다). 키를 읽는 줄 바로 옆에서 정상 API를 부르면(머리글에 키를 넣는 보통 호출) 여전히 걸린다: 15줄은 제안값이고 키가 요청 본문·다른 주소로 가는지는 보지 않는다. 반대로 읽는 곳과 보내는 곳이 15줄보다 멀면 '위험'이 아니라 '주의'(P2의 먼 짝)로 나온다: 다른 함수에 나눠 쓴 유출 코드나 주석으로 거리를 벌린 코드도 '통과'가 되지는 않지만, 멀리서 정상 API를 부르는 보통 서버도 '주의'가 된다.
- **검사하지 못한 줄:** 2000자가 넘는 줄(압축 파일)은 검사하지 않고 따로 센다. 그런 줄이 있으면 발견이 없어도 "통과"가 아니라 **"찾지 못함"**으로 둔다. 읽은 파일이 하나도 없을 때도 같다.
- 패턴 목록은 관리자가 더할 수 있다(`audit_logs`에 남음). 패턴을 바꾸면 규칙 버전을 올린다.
- 검사 주기는 데이터설계 8절: 새 버전·커밋이 생겼을 때 + 주 1회.

## 3. 사건(변경) 기준 (SPEC-3)

### SPEC-3.1 보안 경고
| 변경 종류 | 언제 | 중복 막기 키 |
|---|---|---|
| 보안 등급 바뀜 | 두꺼운 기술의 등급이 **위험이 아닌 것 → 위험**으로 바뀜 | 기술 키 + 버전 + 원인(취약점 id 또는 패턴 id) + **위험이 된 회차** (위험 → 고쳐짐 → 다시 위험이면 회차가 올라가 새 변경이 됨) |
| 처음 확인한 위험 | 처음 읽기·다시 읽기에서 **새로 들어온 내 기술이 이미 위험** | 공용 변경은 위와 같은 키로 하나만(이미 있으면 그것에 잇는다). **알림 키는 사람 + 기술 키 + 버전 + 원인** — 두 번째 사용자가 등록해도 그 사람에게 알림이 생기고, 같은 사람이 다시 읽어도 두 번 생기지 않는다 |

그 기술을 쓰는 사람마다 알림 1개(사람 + 변경은 한 줄).

**정기 OSV 재확인(P-9d)이 위험 회차를 정하는 법:** 같은 (기술, 버전)을 쓰는 줄의 등급 시각과 변경이 만들어진 시각으로 판단한다. 같은 원인의 변경이 있고 그 뒤로 "위험이 아니다"라고 등급을 매긴 적이 없으면 위험이 **이어지는 중**이라 새로 만들지 않고 그 변경에 알림을 잇는다(회차 2 이상이어도, 앞 실행이 중간에 멈췄어도 같다). 변경 뒤에 위험이 아니라고 매긴 기록이 있으면 고쳐졌다 다시 위험해진 것이라 가장 큰 회차에서 하나 올린 새 변경을 만든다. 같은 취약점의 별칭(CVE·GHSA·PYSEC)은 같은 원인으로 본다. 첫 읽기도 위험이 이어지는 중이면 가장 최근 변경에 알림을 잇는다.

### SPEC-3.2 적용 기회
아래 셋이 **모두** 맞을 때만:
1. 내 기술과 같은 역할로 **확정**됨(SPEC-4.4, 관리자 확인으로만, ADR 0015)
2. 새 기술이 내가 **등록한 시각 이후에** 카탈로그에 들어옴(또는 그 이후에 같은 역할로 확정됨)
3. 새 기술의 등급이 **위험이 아님**

v1에서는 "갈래 안 점수가 상위 절반"을 조건에 넣지 않는다. 점수는 3순위 P-21에서 만들어져서, 1순위 P-14와 시뮬레이터의 두 번째 알림이 쓸 수 없다(ADR 0014). 점수가 만들어지면 **조건 4로 다시 넣고** 이 절과 5.3을 고친다.

중복 막기 키: 내 기술 키 + 새 기술 키.

### SPEC-3.3 (3순위) 모델 지원 종료
내 저장소 코드에 그 모델 이름이 있고, 공식 출처가 지원 종료 날짜를 발표함. 첫 시연에는 넣지 않는다.

### SPEC-3.4 사건이 아닌 것
| 상황 | 처리 |
|---|---|
| 같은 값을 다시 읽음 | 수집 기록만 남기고 아무것도 안 만듦 |
| 등급이 통과 ↔ 주의로 오감 | 목록·지도의 등급만 바꿈. 알림 없음(v1은 위험만 알림) |
| 등급이 위험 → 위험 아님(고쳐짐) | 알림 없음. 기존 알림 상세에 "지금은 고쳐졌어요(날짜)" 표시. 기존 판단은 그대로 |
| 수집 실패 | "수집 오류". 사건 아님, "변화 없음"·"사라짐"으로 단정하지 않음 |
| 일반 소식(새 버전, 모델 출시) | 소식판에만(3순위). 내 기술과 직접 이어질 때만 위 규칙으로 알림 |
| 추천 | 알림이 아님 |

### SPEC-3.5 시뮬레이터의 가짜 변경
- 가짜 변경과 가짜 수집 자료에는 "시뮬레이터" 표시를 단다.
- 가짜 변경의 알림은 **시연 계정에만** 만든다. 실제 사용자에게는 가지 않는다.
- 시뮬레이터는 적용 기회를 보여 주기 위해 **확정된 같은 역할 관계**도 함께 넣는다(가짜 표시).
- "시뮬레이터 지우기" 명령은 **시뮬레이터 표시가 있는 줄만** 지운다(관리자, `audit_logs`에 남음).

## 4. 판단(승인) 규칙 (SPEC-4)

### SPEC-4.1 상태
| 지금 상태 | 할 수 있는 일 | 다음 상태 |
|---|---|---|
| 판단 대기 | 적용 후보 / 보류(이유 필수) | 완료 |
| 판단 대기 · 완료 | 적용 시나리오 만들기(요청) | 그대로 |
| 완료 | 기록 보기 | 그대로 |

- 판단과 상태 바꾸기는 **한 거래**로 저장한다. 실패하면 둘 다 그대로이고 "저장하지 못했어요. 다시 시도해 주세요"(불변 4).
- 불변 4의 "승인 거절"은 우리 말로 **보류**다. 보류해도 설치 프롬프트 목록과 그 버전은 그대로 두고(고친 버전으로 바꾸지 않음), 알림은 "완료"가 된다. 알림 "완료"는 **판단을 마쳤다**는 뜻이지 조치를 실행했다는 뜻이 아니다(조치는 판단 저장, ADR 0010).
- 보류 이유는 **5자 이상**.
- v1에서는 **판단을 고칠 수 없다**(구현 기준으로 닫음, 데이터설계 DQ1·SQ1). 같은 기술에 새 변경이 오면 새 알림으로 다시 판단한다.
- **관리자도 남의 알림에는 판단을 만들거나 건너뛸 수 없다**(화면·서버·DB, 불변 1·5). 관리자 본인 알림에는 다른 사용자와 같은 규칙으로 판단할 수 있다(DB 함수 `save_judgment`는 "본인 알림인가"만 확인한다, ADR 0016).

### SPEC-4.2 적용 시나리오
- 알림 상세의 "적용 시나리오 만들기"를 누를 때만 만든다. **사용자당 하루 5번**.
- 들어가는 것: 대체 기술과의 비교표(SPEC-5.3과 같은 항목), 적용 단계, 위험과 되돌리는 방법, 출처. 출처가 없으면 "찾지 못함".
- **적용 단계의 설치 명령은 카탈로그에 있는 공식 설치 명령만** 쓴다. 바깥 글에서 읽은 명령은 넣지 않고 "공식 문서에서 직접 확인하세요"로 바꾼다(ADR 0009의 안전장치를 시나리오에도 적용).
- 시나리오는 **참고 자료**라 판단 전후 언제든 만들 수 있다. 조치는 판단 저장이다(ADR 0010, SQ6).
- 실패하면 "만들지 못했어요"와 다시 요청 버튼. "완료"로 보이지 않는다.

### SPEC-4.3 설치 프롬프트 · 목록 가져오기
넣을 수 있는 것은 세 출처뿐이다(SQ8): ① 사용자 저장소에서 **실제로 읽은** 것은 그대로 ② 내 컴퓨터 목록 가져오기로 받은 것은 **값 검사(SPEC-6.3)를 통과한 것만** ③ 적용 후보로 판단한 카탈로그 기술은 **공식 레지스트리 이름과 정확히 일치하는 것만**(비슷한 이름은 넣지 않음).
6절 템플릿 그대로만 만든다. **위험한 버전은 어떤 경우에도 넣지 않는다**(사용자가 직접 넣는 길도 없음, ADR 0012). 빠진 것은 "[넣지 않은 것 (위험)]"에 이유와 함께 적고, 고친 버전이 있으면 그 버전으로 바꾸면 넣을 수 있다고 알려 준다. 보안 경고에서 적용 후보(고친 버전으로 올리기)로 판단한 것은 **고친 버전으로 고정**해 넣는다.

### SPEC-4.4 같은 역할 확정
- **처음 짝 목록**(20쌍 정도)은 팀이 만든다. 그 뒤 새 짝은 같은 작은 갈래에서 **후보**가 되고(Claude가 제안한 짝은 근거 인용이 원문에 그대로 있을 때만 후보로 저장), **관리자가 확인**해야 확정된다(담당자·시각·사유, ADR 0015).
- Claude가 문장 인용만으로 자동 확정하는 것은 3순위다(v1은 하지 않음, ADR 0015).
- 예외: 시뮬레이터가 넣는 가짜 관계는 확정으로 들어가며 가짜 표시가 붙는다(SPEC-3.5).
- 처음 짝 예(팀이 고친다): `@modelcontextprotocol/server-filesystem` ↔ 다른 파일 시스템 MCP, `mcp-remote` ↔ 다른 원격 연결 MCP 프록시, 디자인 스킬 ↔ 디자인 MCP

### SPEC-4.5 비슷한 과거 판단 찾기 (PRD-F21)
- **규칙으로 찾는다**(검색·임베딩 아님): 내 지난 판단 중 ① **같은 기술 키** ② 확정된 **같은 역할** 기술 ③ **같은 작은 갈래** 순으로, 각 순서 안에서는 최근 것부터 **3개까지**.
- 보여 주는 것: 날짜, 기술, 판단 결과, 이유, 그때의 등급.
- 안내서가 과거 사건 찾기를 RAG·LLM 위키 수업과 연결하는 것(94–96·163–164줄)은 **위키 챗봇(F31)** 쪽에서 쓴다. 제품 안의 과거 판단 찾기는 같은 입력에 같은 결과가 나와야 해서 규칙으로 한다.

## 5. 알림 내용 (SPEC-5)

알림은 **앱 안에서만** 보인다. `{ }`는 실제 값으로 채운다. 값이 없으면 "찾지 못함".

### SPEC-5.1 보안 경고
```
[보안 경고] {기술 이름} — {이전 등급} → 위험
무엇이 바뀌었나: {원인 한 줄} ({출처}, {발견 시각})
쉬운 이유: {SPEC-1 쉬운 이유}
내 프로젝트: {프로젝트 이름} · {어느 파일}
대응안 초안 (Claude): {고친 버전으로 올리기 / 같은 역할의 다른 기술 / 빼기} — 출처 {링크}
비슷한 지난 판단: {있으면 날짜·결과·이유}
[고친 버전으로 올리기(적용 후보)]  [보류(이유)]  [적용 시나리오 만들기]
```

### SPEC-5.2 처음 확인한 위험
```
[첫 점검] {기술 이름}은 지금 위험이에요
이유: {SPEC-1 쉬운 이유} ({출처})
고친 버전: {있으면 버전, 없으면 "아직 없음"}
[고친 버전으로 올리기(적용 후보)]  [보류(이유)]  [적용 시나리오 만들기]
```
지도 띠: `첫 점검: 위험 {n} · 주의 {n}`

보안 경고(5.1·5.2)의 **적용 후보는 "고친 버전으로 올리기"**다. 고친 버전 번호를 판단과 함께 저장하고(`judgments.fixed_version`), 설치 프롬프트에는 그 버전으로 고정해 넣는다. 고친 버전이 없으면 판단 버튼은 [보류]만 보인다([적용 시나리오 만들기]는 참고 자료라 그대로, SPEC-4.2). 위험한 버전은 적용 후보가 될 수 없다(ADR 0003 개정·0012).

### SPEC-5.3 적용 기회
```
[적용 기회] {내 기술}과 같은 역할의 {새 기술}이 나왔어요
비교: 하는 일 / 보안 등급과 이유 / 최근 업데이트 / 사용량 / 라이선스 (항목마다 출처)
나오게 된 이유: 같은 역할 확정({확정한 날})
[적용 후보]  [보류(이유)]  [적용 시나리오 만들기]
```

## 6. 설치 · 가져오기 프롬프트 템플릿 (SPEC-6)

**정해진 틀 그대로만** 채운다. 바깥 README 글은 넣지 않는다. 이름·버전·위치·링크는 **SPEC-4.3의 세 출처에서 온 값**이다(저장소에서 읽음 / 값 검사를 통과한 가져오기 / 공식 이름과 같은 카탈로그 적용 후보). 보안 경고에서 고른 것은 **고친 버전**을 쓴다(ADR 0012).

### SPEC-6.1 설치 프롬프트
```
이 컴퓨터에 아래 AI 코딩 도구를 설치해 줘. 꼭 지킬 것:
1. 하나씩, 설치하기 전에 무엇을 어디에 설치하는지 보여 주고 나에게 확인받아.
2. 아래에 적힌 이름과 버전 그대로만 설치해. 비슷한 이름을 찾아 바꾸지 마.
3. <여기에 직접 입력> 칸은 추측하지 말고 나에게 물어봐.
4. 실패하면 멈추고 이유를 알려 줘.

[MCP 서버]
- {이름} | {생태계} {패키지}@{버전} | 설정 위치: {.mcp.json 또는 사용자 설정} | 출처: {공식 링크}
  환경변수: {키 이름}=<여기에 직접 입력>
[스킬]
- {이름} | 가져올 곳: {github.com/owner/repo/경로} | 넣을 곳: {~/.claude/skills/ 또는 프로젝트 .claude/skills/}
[플러그인 · SDK]
- {이름} | {설치 명령의 패키지 이름}@{버전} | 출처: {링크}

[넣지 않은 것 (위험)]
- {이름}@{버전} — 위험: {이유}. {고친 버전}으로 바꾸면 넣을 수 있어요.
```
- "[넣지 않은 것 (위험)]" 줄의 "{고친 버전}으로 바꾸면 넣을 수 있어요"는 고친 버전이 있을 때만 쓰고, 없으면 그 문장을 뺀다.

### SPEC-6.2 내 컴퓨터 목록 가져오기
```
내 컴퓨터에 설치된 AI 코딩 도구 목록을 아래 형식으로만 출력해 줘.
파일 내용, 환경변수 값, 키, 토큰은 절대 출력하지 마.
확인할 곳: 사용자 범위 MCP 설정, 사용자 스킬 폴더, 플러그인 폴더
형식(한 줄에 하나, 다른 말 없이). 패키지 앞에는 생태계를 붙여(npm: 또는 pypi:), 스킬은 경로 그대로:
종류|이름|npm:패키지 또는 pypi:패키지 또는 경로|버전
```
- 붙여 넣은 줄은 형식이 맞는 것만 받는다. 패키지에 `npm:`·`pypi:` 접두어가 없으면 생태계를 짐작하지 않고 "생태계를 알 수 없어 뺐어요"로 보여 준다(같은 이름의 남의 패키지를 설치하는 생태계 혼동 방지). 키·토큰처럼 보이는 값(`sk-`, `ghp_`, 긴 무작위 문자열)이 있는 줄은 **저장하지 않고** "비밀값처럼 보여서 뺐어요"라고 보여 준다.
- Claude Code의 사용자 범위 설정 파일 위치는 **구현 때 공식 문서로 확인한다**(확인하지 못함).

### SPEC-6.3 값 검사 (설치 프롬프트에 넣기 전, 가져오기로 받을 때)
- 패키지 이름은 그 생태계의 이름 규칙(npm: 소문자·`@scope/이름`, PyPI: 영문·숫자·`-_.`)에 맞아야 한다.
- 이름·경로·버전은 **64자 이하**, 줄바꿈·백틱·꺾쇠가 있으면 뺀다.
- "무시", "ignore", "instead", "system" 같은 지시처럼 보이는 낱말이 이름·인자에 있으면 뺀다.
- 뺀 항목은 프롬프트의 "[넣지 않은 것]"에 이유와 함께 적는다. 이 칸은 이름을 쓰지 않고 "이름 형식이 맞지 않아 뺐어요"처럼만 적는다(빠진 값 자체를 다시 넣지 않음).

## 7. 내 기술 읽기 (SPEC-7)

### SPEC-7.1 읽는 파일
`package.json`, `requirements.txt`, `.mcp.json`, `.claude/skills/*/`(1순위). `.cursor/mcp.json`, `AGENTS.md`, `GEMINI.md` 등은 3순위. `CLAUDE.md`는 기술로 읽지 않는다.

### SPEC-7.2 허용 목록 (처음 버전, 관리자가 고침)
`package.json`·`requirements.txt`에서는 **아래에 맞는 패키지만** 내 기술로 넣는다. `.mcp.json`·스킬은 모두 넣는다.

| 생태계 | 패키지 (처음 목록) |
|---|---|
| npm | `@anthropic-ai/sdk`, `@anthropic-ai/claude-code`, `@anthropic-ai/claude-agent-sdk`, `openai`, `@openai/agents`, `ai`, `@ai-sdk/*`, `@modelcontextprotocol/*`, `mcp-remote`, `@google/genai`, `langchain`, `@langchain/*`, `llamaindex`, `@mastra/core` |
| PyPI | `anthropic`, `claude-agent-sdk`, `openai`, `openai-agents`, `mcp`, `fastmcp`, `langchain`, `langchain-*`, `langgraph`, `llama-index`, `crewai`, `autogen-agentchat`, `google-genai`, `litellm` |

패키지 이름이 실제로 있는지는 구현 때 레지스트리 조회로 확인한다.

### SPEC-7.3 기술 키 만드는 규칙
| 어디서 | 무엇을 보고 | 기술 키 |
|---|---|---|
| `package.json`, `requirements.txt` | 패키지 이름과 버전 | `npm:<이름>`, `pypi:<이름>` |
| `.mcp.json` | 실행 명령: `npx -y <패키지>[@버전]` | `npm:<패키지>` |
| `.mcp.json` | `uvx <패키지>`, `pipx run <패키지>` | `pypi:<패키지>` |
| `.mcp.json` | 원격 주소(`url`) | `url:<호스트>` — 등급은 "찾지 못함", 주소만 보여 줌 |
| `.mcp.json` | 위에 해당 없음(직접 만든 스크립트 등) | 키 없음, 서버 별명만 — "찾지 못함" |
| `.claude/skills/<이름>/` | 원본을 알 수 있음(폴더 안 README·메타의 GitHub 링크) | `skill:<원본 owner>/<repo>/<이름>` |
| `.claude/skills/<이름>/` | 원본을 모름 | `skill:<내 owner>/<내 repo>/<이름>` + **"출처 모름"** — 다른 사람의 같은 스킬과 묶이지 않는다(쓰고 있어요·카탈로그 공유 안 됨). 위험 패턴 검사는 한다 |
| 플러그인 | — | **v1은 읽지 않음**(읽을 파일이 정해지지 않음, 3순위, SQ7) |

`.mcp.json`의 서버 이름은 사용자가 붙인 **별명**이라 기술 키로 쓰지 않는다.

## 8. 수집 규칙 (SPEC-8)

**정기 실행: 매일 06:00(한국 시간)** + "지금 한 번 실행". 실행은 짧은 단위로 나눈다(Vercel 함수 시간 한도는 확인하지 못함).

| 출처 | 순위 | 무엇을 | 간격 | 한도·약관 | 실패하면 |
|---|---|---|---|---|---|
| OSV | 1 | 두꺼운 기술의 취약점(묶음 조회) | 매일 | 키 없음, 한도 확인 못 함 → 묶음 조회로 횟수 줄임 | 그 기술만 수집 오류 |
| 공식 MCP 레지스트리 | 1 | 새 서버, 중단 표시 | 매일 | 키 없음 | 출처 수집 오류 |
| GitHub (서버 토큰) | 1 | 사용자 저장소 파일, 기술 저장소 정보(새 커밋·릴리스·라이선스·별) | 매일 + 사용자 다시 읽기 | 시간당 5,000회(토큰) | 그 저장소만 수집 오류 |
| npm · PyPI 다운로드 | 1 | 주간 다운로드 | 매일 | 키 없음(11-17 확인) | 인기 신호만 비움 |
| Hugging Face · Hacker News | 3 | 인기 신호 | 매일 | 키 없음 | 인기 신호만 비움 |
| Firecrawl (skills.sh 1곳) | 3 | 스킬 설치 수 | 매일 | 무료 한도, 키는 서버에만, 약관 확인 후 | 인기 신호만 비움 |

- **재시도:** 실행 단위로 2·4·8분 뒤 최대 3번(이전 프로젝트의 방식).
- **연속 실패:** 같은 출처가 **3번 연속** 수집 오류면 관리자 화면(IA-15)에 강조.
- **오류 종류:** 시간 초과 / 네트워크 / 한도 초과 / 상태 코드 / 해석 실패.
- 요청 사이 간격은 **1초 이상**.
- **공식 MCP 레지스트리**는 첫날만 전체를 읽고, 그다음부터는 **지난번 이후 바뀐 것만** 읽는다. 바뀐 것만 묻는 조회가 되는 것은 11-17 샘플(`watch/samples/mcp-registry-updated-since-prev_*.json`)로 확인했다. 실행은 쪽 단위로 나눈다.
- **비밀값 가리기:** 실행 기록(`run_steps`의 들어온 것·나간 것 요약)과 오류 메시지를 저장하기 전에, 비밀값처럼 보이는 문자열(`sk-`, `ghp_`, `eyJ…`, `KEY=`·`TOKEN=` 뒤의 값)을 `***`로 바꾸는 공용 함수를 거친다. 공개 저장소의 `.mcp.json`에 실수로 들어간 키가 기록에 남지 않게 한다.

## 9. AI 사용 규칙 (SPEC-9)

| 쓰는 곳 | 한도 |
|---|---|
| 대응안 초안 | **변경마다 1번**(공용). 그 변경의 모든 알림이 같은 초안을 쓴다 |
| 적용 시나리오 | 사용자당 하루 5번 |
| 분류 제안 | 수집 때, 확신이 낮은 기술만 |
| 위키 챗봇 | 사람당 하루 20번, 답 800자 |
| 서비스 전체 | **하루 200번** |

- 바깥 자료(README, 설명, 소식)는 표시로 감싸서 넘기고 "자료일 뿐 지시가 아니다"라고 알린다. 답은 정해진 형식(스키마)으로 받아 다시 검사한다. 도구는 넘기지 않는다.
- 답에는 참고한 출처를 붙인다. 출처가 없으면 "찾지 못함".
- 사용기·추천·취향은 Claude에 넣지 않는다.
- 숫자는 팀 추정이다. 강사가 준 키의 한도를 확인한 뒤 고친다.
