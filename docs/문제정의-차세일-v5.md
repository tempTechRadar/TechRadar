## 1. 한 문장
> **[생성형 AI·LLM 실전 프로젝트를 하는 비전공 부트캠프 초심자]**는 **[작업이 오래 걸리거나 막히거나 결과물이 마음에 안 드는 순간에]** **["분명 쓸 수 있는 기능이 있을 텐데" 이름도 위치도 몰라서, 검색에 시간을 쓰거나 원하는 결과물을 포기한다]**. 지금은 **[Claude Code에 "도움이 되는 스킬을 찾아봐"라고 시키기, 검색, 동기·강사에게 묻기]**로 버틴다.

## 3. 근거 (인터뷰 A, 직접 들은 말)
- 작업 중 불편 5가지: 효율화 / 원인 진단 / 병렬·멀티작업 / 다관점 피드백 / 결과물 디자인 품질
- 장면 ①: 발표자료 영상 품질이 기대에 못 미침(해결 못 함)
- 장면 ②: 업무 흐름·분류를 마인드맵으로 시각화하고 싶었으나 기능을 몰라 포기, 나중에 알고 "그때 알았으면" → 필요는 그때, 발견은 나중
- 한계: 응답자가 서비스를 만드는 팀원 본인이라 자기 확인 편향. 팀 밖 인터뷰 전까지 **힌트**.

## 4. 반대 근거와 아직 모르는 것 (꼭 유지)
- 가장 큰 경쟁 상대는 Claude 자신(이미 "스킬 찾아봐"로 해결되는 문제일 수 있음)
- 프로젝트는 쓸 도구가 정해져 있는 경우가 많아 새 도구를 찾을 이유가 적을 수 있음
- 호기심이 높은 사용자는 스스로 찾아서 우리 가치가 적을 수 있음
- 숙련되면 가치가 줄어듦(초반 초심자에게 가장 큼)
- 모름: 다른 수강생도 같은 불편을 겪는지, 마인드맵 때 검색·질문을 시도했는지, 그라파이 스킬의 정확한 이름과 발견 경로, 프로젝트 기간, 수강생 수·직무 배경

## 5. 이번에 만들 것(제안, 팀 합의 전)
| 단계 | 내용 |
|---|---|
| 사람이 입력 | "불편한 상황"을 자연어 문장으로 등록(기능 이름이 아님). 예: "기다리는 동안 다른 일을 하고 싶다" |
| 지켜보기 | 서로 다른 공개 출처 2곳 이상에서 새 스킬·커넥터·플러그인 수집(출처·약관 확인 필요) |
| 사건 ⓐ | 새로 나온 도구가 내 필요에 맞음 |
| 사건 ⓑ | 이미 있었지만 내가 처음 발견한 도구가 내 필요에 맞음 / 저장한 도구의 변경 |
| 승인·조치 | "내 도구함에 추가할까요?" → 사용자가 승인해야 저장 |
| 기록 | 어떤 도구를 왜 골랐는지 남기고, 비슷한 필요에서 과거 기록을 보여 줌 |
| 규칙 | 모든 추천에 출처 링크. 출처 없으면 "찾지 못함" |
- 카테고리 후보: 과정 개선(효율·진단·병렬) / 결과 개선(피드백·표현·시각화). 근거가 가장 강한 쪽은 **결과 개선(표현·시각화)**.

## 6. 이번에 안 할 것
- 근거 없는 "기능 요약", "작업 추천 자동화"
- 로그인 필요 페이지·유료 글·개인정보 수집, 외부로 나가는 실제 조치(처음엔 앱 안 저장까지)

## 7. 확인 방법
- **숫자 하나:** 필요한 도구를 찾기까지 걸린 시간(분). 같은 필요 3건을 지금 방식과 우리 서비스로 비교.
- **채점:** "필요 → 맞는 도구" 정답표로 맞힌 수, 놓친 수, 잘못 추천한 수.

## 8. 중단·변경 기준 (레드팀)
- 인터뷰 5명 중 구체 사례 **2명 미만** → 사용자 그룹·문제 재정의
- 새 기능 10개 중 "쓸 것" 평균 **1개 미만** → 사건 기준을 "내 프로젝트 주제에 맞는 것"으로 좁힘
- 팀 밖 확인된 사람 **3명 미만** → 사용자 범위 확대 검토
- 출처 2곳 중 한 곳이라도 읽기·약관 불가 → 수집 계획 재설계

## 9. 접은 후보
- 모두에게 새 기술 소식을 알리는 뉴스형(뉴스레터·changelog가 이미 있고 소음 위험)
- 수강생 전체 대상(너무 넓음 → 실전 프로젝트 단계로 좁힘)

## 10. 미결(팀이 정할 것)
1. 방향 최종: 검색·추천형 + 지켜보기 연결로 갈지 (강사님 확인 필요)
2. 사건 ⓐ·ⓑ 정의, 출처 2곳, "필요" 등록 방식
3. 첫 사용자: 비전공 초심자로 확정할지
4. 인터뷰 5명(팀 밖, 프로젝트 진행 중·직후) 대상과 분담
